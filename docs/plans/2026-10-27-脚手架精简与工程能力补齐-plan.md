## 1. 目标、范围与验收

目标是让新项目能按文档创建、登录、双语开发、验证、按需启用监控及部署升级。先收敛脚本和测试，再补自动检查、安全边界、类型化调用与 Python 出站熔断；监控采用可选 Prometheus/Grafana 和管理后台嵌入。审计复用现有实现，性能和恢复用真实环境验证，不增加自研运维平台。

不新建 tools、internal、framework、testing 等抽象目录；不增加统一命令分发器、插件系统、测试平台或发布服务。服务单元测试留在所属服务，SDK 测试留在 SDK，根 tests 保留跨模块测试。仅按工具惯例增加 GitHub 的 `.github/workflows/` 和现有 infra 下的一层 `monitoring/` 配置目录，不增加常驻业务服务。

两层交付必须分开：A 层可编写全部本轮代码、配置、文档并运行不依赖 Docker 的定向检查；B 层在用户另行恢复 Docker 验收后执行真实监控、身份/业务端到端、压测、恢复演练。A 层完成不代表 B 层通过。单机真实验证也不代表多台 Linux 服务器或真实第三方登录已经验收。

### 3.3 新项目实际携带什么

生成器改为明确导出允许的脚本文件和两个共享 JSON，避免“整目录复制后不断补排除项”。清单直接写在现有 generation 中，不新建清单文件或可配置导出系统。部署包使用其独立运维文件清单，不复制整个项目 scripts。

新项目根 tests 只需要：

```text
tests/
├─ README.md
├─ fixtures/
│  ├─ introspection-v1.json
│  └─ gateway-routes-v1.json
└─ acceptance/
   └─ smoke.cjs
```

新项目 smoke 复用随 identity-service/admin 已有的 Playwright 开发依赖，不为单个测试增加根 npm 工程。框架的其他浏览器验收依赖是否仍需单独安装，以现有消费者为准，不能卸载其所需依赖。说明安装浏览器的前提；依赖缺失时清楚失败，不在运行中偷偷安装。

smoke 是随初始两个样例业务交付的测试，使用生成后的服务名称；只允许明确初始化了演示数据的 local 环境，测试前核对服务、演示账号材料和本地地址。它会创建测试数据并处理演示账号初始改密，文档必须说明副作用及本地状态保存，不输出秘密。业务团队替换 `/items` 等样例 API 时同步改自己的 smoke；不能包装成永远不用修改的全业务通用验收。

项目后续自己改了公共脚本，可在现有 tests 下增加对应回归；默认不为可能的定制复制全部框架维护测试。源码升级时先合并所改文件及相关测试，再运行受影响检查。

### 3.4 CI、依赖与秘密检查

复用 GitHub Actions，不做自研 CI。框架仓库和生成项目均提供一份可直接阅读的 workflow；生成项目 workflow 不引用不存在的框架维护测试或远程框架工作流。生成器移除维护专用 job；初始两语言样例使用固定定向用例，新增 submodule 服务由项目维护相应用例选择；不再写通用 CI 配置生成平台。

- 工具版本来自 Java 21、根工具锁、服务各自 uv.lock、管理页 pnpm-lock；安装使用 frozen 模式。Actions 固定已核实的 commit，默认只给 contents:read；不对不可信 PR 使用 pull_request_target 执行其代码，不向 fork PR 注入生产秘密。
- PR/push 的非纯文档变更运行固定核心定向集合：Java Spotless/编译和明确列出的单测；Python Ruff/SDK 类型检查和指定 SDK/样例测试；管理页 lint/typecheck/build/指定组件测试；框架另跑明确列出的维护纯测试。不增加自动依赖图或按符号推断测试的系统。纯文档变更跳过 Source checks 和依赖构建，秘密扫描仍执行；链接/格式由本地文档核对负责，不宣称已有线上链接检查器。不用裸 `mvn test` / `pytest` 掩盖测试范围选择。
- 维护仓库增加生成项目的离线导出检查；生成项目只运行其实际交付的模块测试。本轮不新增 Docker 工作流，真实集成仍按 B 层显式选择运行，不随普通 PR 启动；本轮写文件不代表已在 GitHub 跑过。
- 秘密扫描采用 Gitleaks CLI，输出脱敏；扫描取回的 Git 历史，发行前再次检查候选提交历史。只允许有具体位置和理由的误报豁免，不把整个 config/tests 或生成项目排除。
- 漏洞扫描采用生态已有工具：Java 的 OWASP Dependency-Check、Python 的 pip-audit（对锁定依赖导出，不直接审计未解析的本地路径依赖）、Node 的 pnpm audit。工具本身固定版本，不把扫描工具加入业务运行依赖。命中 High/Critical 或无法完成有效扫描时阻断相关安全检查；无严重性信息的 Python 漏洞须人工判定后才能放行，不默认为低风险。误报豁免必须列 CVE/包/理由/失效日期。
- Dependency-Check 缓存数据库并记录更新时间；NVD 不可用显示失败/未完成，不能绿色跳过。Dependabot 仅作依赖更新建议，与漏洞门禁不是二选一；是否启用仓库级告警/分支保护要记录实际配置状态，提交 YAML 本身不等于保护已生效。
- 私有 submodule 的取回权限由项目配置只读凭据；fork PR 无法取回时明确标记相关检查未完成，不能悄悄只测主仓。主仓记录固定 gitlink，构建不得跟随子仓浮动分支。

### 3.5 安全头、账号枚举和审计

先按真实 SecurityFilterChain 和入口路径建立覆盖矩阵，再补缺。身份的登录/初始改密/授权/外部登录回调/管理静态页、Gateway BFF、Nginx 错误及静态响应分别确认；现有 CSP 不能证明其他链也覆盖。

- 身份/管理页面以 self 为资源源，禁止 object，限定 base/form-action；管理页需要 frame-src 'self' 承载同源 Grafana，而页面自身仍禁止被其他页面框入。只有 Grafana 子路径按其要求允许同源嵌入；不全站关闭 X-Frame-Options，不全局加 unsafe-inline/unsafe-eval 解决问题。登录模板如有 inline 内容，迁成静态资源或用 nonce，验证 OAuth 重定向未被破坏。
- HSTS 由受控 TLS 入口统一设置，建议生产 max-age=31536000；不默认加 includeSubDomains/preload。本地 HTTP 不发送；核对 Nginx location 的 add_header 继承及错误响应，应用只信任既有受控代理头，不能靠客户端 X-Forwarded-Proto 决定安全状态。
- 未知账号、错误密码、停用账号/租户返回同一凭据错误类别；保留 dummy hash 和限速。登录锁定、语法错误、基础设施不可用可以有明确错误，但不能因“账号存在与否”出现不同的锁定提示、Cookie/跳转或错误正文。单测检查路径，HTTP 测试检查状态/头/稳定文案；耗时抽样只能发现明显泄漏，不宣称恒定时间。
- 审计核对复用 sys_auth_audit 与现有页面，覆盖角色创建/删除/权限变更/账号角色、平台及租户安全策略、客户端登记/修改/密钥轮换、会话撤销等实际管理入口。成功操作与事务提交对应，失败/越权尝试按现有独立事务记录；检查 request_id、actor、tenant、对象和结果及脱敏。只补确切遗漏；本轮不加新的日志平台或全业务自动审计。

### 3.9 性能、备份恢复与发行纪律

**性能基线：**用成熟 k6 和 PostgreSQL EXPLAIN/pgbench，材料放现有 tests/acceptance，不新建性能平台。三组分开测：完整浏览器会话/密码登录路径、预取 token 的网关转发路径、同数据/索引/查询下 RLS 查询。记录硬件、CPU/内存、镜像/锁版本、并发/到达率、数据量、预热与持续时间、p50/p95/p99、成功率、拒绝率及饱和点。登录保留真实密码哈希强度；保护触发的数据与成功处理吞吐分开报告。RLS 对照只在隔离克隆库使用 BYPASSRLS 测试角色，两组使用相同显式 tenant 条件及结果规模，记录执行计划与缓存条件，不能拿全表结果和单租户结果比较。不修改运行角色或生产安全设置。无实际数据前不填容量承诺，不自动据一次压测改限流阈值。

**恢复演练：**采用 pg_dump/pg_restore 及已有基础设施/迁移步骤。先创建独立演练项目/PG 实例或明确命名的隔离数据库，记录目标白名单；在这个可弃置目标模拟损坏并恢复，不损坏开发身份库。备份验证包含 schema/data、Flyway 历史、RLS 策略、角色与授权重建步骤；只靠单库 dump 不保证集群角色齐全。身份签名密钥、客户端/BFF secret 绑定及配置版本须由包外安全备份另行恢复。恢复后清理演练范围内旧会话/缓存并重新登录，不声称 Redis 会话也由 PG 备份恢复。核对管理员登录、角色/权限、两个租户隔离、审计和 OAuth 客户端绑定，记录实际 RPO/RTO 与限制。数据库卷、备份、运行秘密不入 Git/部署包。

**发行：**不把打 tag 当作验收。A 层只能产出未完成运行验收的开发检查点；B 层通过后才提交候选发行记录，记录本轮 AC 矩阵、未验证的多机/第三方场景、源码 SHA、工具锁和镜像摘要。tag 示例 `v1.0.0-rc.N`，具体 N 检查现有 tag 后确定，不覆盖旧 tag；正式版本另有完整验收要求。create 接受 tag 并解析记录 SHA，项目升级仍通过 Git 差异合并，不自动覆盖源码。本轮无提交、push、tag 或 GitHub 设置写入授权。

## 4. 使用流程与影响边界

1. 创建：在脚手架仓库使用 create.py，指定固定提交和项目名称。两个初始业务服务进入新项目主仓；create/create_service/generation 不随项目复制。
2. 开发：在新项目根使用 `uv sync --frozen` 准备工具；`uv run --frozen python scripts/init.py --env local --with-demo` 准备演示环境。日常 `uv run --frozen python scripts/dev.py equipment-service` / `inspection-service --reload`，或已有 VS Code F5；状态日志使用 compose.py。
3. 验证：先跑实际改动模块的测试。需要检查整个初始接入链时，在环境就绪且浏览器依赖已安装后，运行拟交付的 `node tests/acceptance/smoke.cjs . equipment-service inspection-service`。这里是未来交付命令，本轮不执行。
4. 新增服务：仍在脚手架仓库用 create_service.py 创建独立服务并提交其仓库；项目用 add_service.py 挂载固定提交、登记、初始化及授权。项目不必为了接入服务保留生成器。
5. 数据库、部署：服务迁移仍走 migrate.py；build 构建镜像，镜像入库后 package 以构建记录和摘要组包，Ansible 调用保留的运维脚本。此清理不新增发布器，也不合并构建/上传/部署为隐藏的一键命令。
6. 升级：已有项目对照来源提交合并源码与配置；本次脚本删除和移动要成组更新，包含 import、VS Code、Ansible、包清单、文档引用。保留项目修改、秘密、数据库迁移历史，不把重新生成当升级。

7. 监控按需开启：在环境文件中持久化 `COMPOSE_PROFILES=monitoring`，使用当前 local/部署环境文件；已有 init/Ansible 步骤生成实际所选服务的私网采集绑定并重启受影响服务。项目平台管理员重新授权取得监控权限后，从管理后台“服务监控”进入同源 Grafana。默认不必部署 Prometheus/Grafana，也不必手动编辑 dashboard 才能看到基础指标。具体可复制命令由确认后的 guides 与脚本实际参数一致生成，不提前虚构 `init --monitoring`。
8. Java/Python 开发：业务 PeerClient 使用类型化 SDK 入口和本服务 DTO；无需自己拼绝对地址、透传 token 或重复实现超时。需要熔断的 Python 依赖在该服务配置显式声明；业务仍负责领域错误和是否允许重试，框架不猜测幂等性。
9. 提交 PR 后运行固定核心定向 CI；纯文档变更跳过构建，秘密扫描仍执行；监控和脚本测试无需业务团队搭建另一套测试平台。数据库恢复演练/性能测试属于维护者及项目运维材料，默认生成项目不携带破坏性实验脚本；交付开发/运维说明及安全前提。

数据库模型、OAuth 协议和租户模型不重做；本次 API 增量仅 SDK 类型化入口、监控访问权限和受保护代理路径，保留 CRUD 路径与 JSON 字段。peer 演示改为保留合法上游 code（Python 原 PEER_REJECTED 改为如 SERVICE_BUSY）；项目若依赖旧演示错误码须同步客户端。这不是业务 CRUD 的接口改版。数据库仍复用 Flyway/Alembic；锁、历史校验、失败状态及恢复能力不因文件较长而删除。旧内部脚本入口调用统一迁走；正式 CLI 保持。数据库回滚不用于恢复本次源码整理。

## 7. 风险、恢复与交接自检

- 最大风险是把有用的运维代码/安全断言当作重复删除。通过所有消费者（包括 YAML、VS Code、文档）核对和覆盖迁移约束控制。
- 合并 local 时先确定 compose 函数归属，禁止 init↔compose 循环；create_service 复用 generation 时不得引入反向导入。
- 新项目和部署包是不同交付物，分别验证；不能为简化清单把维护者脚本、夹具或秘密加入部署包。
- SDK 夹具路径必须在新项目工作目录验证；当前路径已修正；实际定向验证与生成项目验证分别记于执行记录。
- Grafana 嵌入的主要风险是 iframe 可见但 API 越权、CSRF 不兼容或安全头互相覆盖。采用固定同源代理与真实浏览器矩阵，不通过关闭全局安全检查解决；若成熟组件版本差异需要扩大代理写方法，先记录具体路径/用途再评审。
- Python 候选熔断库的 async 支持不等于满足并发半开/取消合同。T-08 的组件验证是实施门槛；失败不能用宣传文档代替证据，也不把自研状态机当局部细节偷偷加入。
- 真实两台 Linux 机器、外部 OAuth 提供方和 GitHub 受保护设置均未由本轮提供。单机、mock、workflow 文件不能代替这些证明；外部缺失不阻塞已经能独立完成的 A 层任务。
- 旧验收删除前必须有替代证据。Docker 未授权恢复时保留未完成项，不为了“目录干净”先删除。
- 回退以本次独立变更提交为边界恢复代码/文档，保留已有 .local、秘密和数据库；不执行清库、清卷或覆盖已有项目。
- 自检：不增加抽象目录，只有工具要求的 workflows 和单层 monitoring；每项 AC 均对应任务及验证；与旧计划关系明确；共享夹具、生成器/项目/部署包所有权明确；运行验收没有冒充完成。
