## 1. 目标、范围与验收

### 1.1 本次交付与决策

交付可独立维护的源码微服务脚手架。公共 SDK、identity/gateway、初始 Java/Python 业务直接归主项目；以后新增业务按固定 Git submodule 接入。移除整个框架的 vendor 和 manage.py 路径，改用职责明确的 scripts。生成项目必须能让另一位开发者仅靠 README 和 VS Code 完成开发，不能依赖维护者 .local、旧容器、私服或聊天。

| 决策 | 来源/状态 | 本计划处理 |
| --- | --- | --- |
| 项目拥有公共源码和初始双语业务 | 用户已确认目录与改造方向 | 不再引用整个框架 submodule |
| 根目录可运行样例取代 template | 用户本轮明确确认 | 样例在 services，config/infra/deploy/web 归根；生成结果改名不留原样例；后续服务从框架生成 |
| scripts 代替 manage.py | 用户本轮提出，已纳入方向 | Python 跨平台脚本，复用 Maven/uv/Compose，不再构造总命令平台 |
| 后续新增服务用 submodule，初始两个保留主仓库 | 用户本轮明确选择 | 新服务生成独立仓库后由用户提交/push，主项目固定 gitlink |
| sdk/java、sdk/python | 用户授权按修订方案实施 | 仅目录聚合，artifactId/package 不重命名，不合并两语言环境 |
| VS Code 启动/断点/联合调试 | 用户明确要求 | 交付 tasks/launch/extensions/settings，新增服务自动追加 |
| Swagger、监控、按需部署 | 用户明确要求 | 开发 OpenAPI；默认日志/健康/指标；可选监控；服务名选择 |
| SQL 管理 | 用户要求评估增删改字段/删表 | 保留 Flyway/Alembic，明确作者流程、历史保护、兼容/停机两路径 |
| Docker 验收暂停 | 保留用户独立约束 | 允许代码实施和无容器定向验证；运行验收必须等解除暂停 |

不改变租户独立账号、角色/权限语义、OAuth/OIDC/BFF、RLS、Nacos、Sentinel/Python 保护；不增加聊天 Agent、任务平台、发布控制台、全功能后台或 CI 平台。无真实双机/外部 OAuth 环境，不以夹具替代这些验收。现有未发行迁移也不得在本次无实际数据库盘点的情况下重置/合并。

### 1.3 已知缺口：类型化服务间调用

现有 Java/Python 调用仍需手写路径及响应处理；Java 示例 PeerClient 返回 `ResponseEntity<byte[]>`，没有跨语言共享的类型化接口契约。对端字段发生不兼容变更时，当前流程不能保证在构建或契约检查阶段发现。本计划保留这一使用短板，不将 AC-08 通过表述为已具备类型化调用保障。

**类型化调用封装与本计划解耦，另行编制计划，尚未实现或验收。** 后续计划需明确契约来源、Java/Python 类型化客户端、与现有服务发现/鉴权/超时保护的衔接，以及接口变更的兼容性检查与调用方更新流程；本次不预选工具或增加实现任务。仅生成客户端也不能保证已部署对端与客户端契约一致。

T-07/AC-09 的 OpenAPI 工作只提供服务文档与 schema，不包括客户端生成或跨服务契约兼容性检查。后续编制与最终交接须保留本缺口，不能因 Swagger 可用而将其视为解决。

## 4. 使用者的完整操作路径

以下为目标流程，所有 scripts 命令在实现前不可视为现有能力。

1. 维护仓库执行 `uv sync --frozen`，再 `uv run --frozen python scripts/create.py --ref <固定提交> --output ../equipment-platform --project equipment-platform --java-service equipment-service --java-package com.acme.equipment --python-service inspection-service --python-package inspection --port-offset 0`。创建仅导出已提交源码与实例化骨架，不安装业务依赖、不启动 Docker。
2. 进入生成项目根，执行 `uv sync --frozen`；首次初始 Python 服务执行 `uv lock --project services/inspection-service`，随后同步依赖。运行 `uv run --frozen python scripts/init.py --env local --services all`；体验演示显式追加 `--with-demo`。init 从当前源码准备开发与迁移镜像、先发布配置再启动身份，输出 URL 和密码文件路径。保存锁与共享 IDE 配置，提交由用户执行。
3. 首次登录分演示/非演示路径，严格按设计 11 §5.1。非演示先平台管理员建租户/租户管理员、允许客户端租户，再租户管理员配置普通用户/角色权限。启动 Java/Python F5 后普通用户登录业务页面，不能把平台管理员当业务账号。Swagger 使用 Authorize→PKCE→普通用户登录同意→Try it out，无 token/无权限必须拒绝。
4. 新业务从兼容版本框架 create_service --project-root <目标项目> 在项目外生成→用户建立远程并提交/push→add_service --repo --ref 接入；已有兼容仓库可直接 add。init --services <新服务> 创建技术资源与权限目录；若已有 BFF 范围不足，按输出差异由管理员更新；租户管理员授权后退出旧业务会话重新登录。B 递归克隆，不取 A 的 .local，也能继续新增第四服务。
5. 开发在主项目根 VS Code 选择 Java/Python/compound，preLaunch 只准备受限环境；热重载单独 task。SQL 在服务内新增版本，`uv run --frozen python scripts/migrate.py --env local --service <name> --check`，核对后 `--apply`。不直接改已共享迁移。
6. 发布前提交所有构建输入，`uv run --frozen python scripts/build.py --release <版本> --services all --output dist/<版本>`；按生成镜像列表使用 Docker/CI push 并采集 digest，再 `scripts/package.py --build-record <构建记录> --images <digest映射> --output <新包目录>`。当前 SDK 公共源码直接随应用构建，不依赖私有 Maven/PyPI。
