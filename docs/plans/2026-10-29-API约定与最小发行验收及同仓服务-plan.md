## 1. 目标、范围与验收

让开发者使用一套分页约定，从固定脚手架提交得到可重复验收的新项目，并能将新增 Java/Python 服务直接保存在项目主仓。

包含：分页及相关响应/文档对齐、最小发行验收入口与手动 CI、同仓服务生成登记、必要的生成物和指南更新。保持认证授权、租户隔离、HTTP 调用预算、数据库所有权和既有 submodule 接入。

不包含：自动生成所有 OpenAPI 客户端、通用 API 兼容性扫描平台、任意业务仓库导入、已有 submodule 转本地、单语言项目生成选项、部门数据权限、文件/任务服务、生产部署、HA、容量压测和备份演练。不把最小验收通过称为生产验收或全面验收通过。

### 3.2 已确认方案：API统一的具体取舍

以下为已确认决策摘要；权威规则归设计07 HTTP正文，管理设计和指南引用它。

1. 本轮统一公共分页和既有通用响应的使用，不整体改名管理业务DTO，也不改变OAuth/OIDC、健康指标、OpenAPI、SSE或文件响应的原生格式。
2. 分页入参采用 `page`（默认0，范围0～10000）、`size`（默认25，范围1～100）。沿用后台0基页码，统一现有20/25两种默认页长，修改双语言样例及全部已定位消费者；现有身份列表入口若默认值或边界不一致，在本范围一并对齐。
3. 分页 `data` 必有 `items/page/size/has_more`；`size`为实际采用页长。保留样例已有`total`作为可选扩展，不强制身份查询增加COUNT；组织版本等业务扩展不删除。样例保留当前业务页长上限，有效size为请求值与业务上限的较小值，偏移和has_more均按有效size计算。
4. SQL偏移改为 `page*有效size`；排序保留已有稳定唯一ID排序；`has_more`按既有总数或多取一条的真实结果判定，不只凭本页恰好满页猜测。空页返回空数组及false，保持200。
5. 旧样例的`page_size`显式返回400（包括同时传size），避免静默忽略。0基页码变更不能靠参数别名兼容；这是样例API的有意破坏性更新，旧调用方必须与样例服务、PeerClient、前端一起升级，不提供自动猜测页码或双版本适配。
6. 继续使用 `{code,message,data,request_id}`、正确HTTP状态、现有稳定业务错误码、JSON snake_case、字符串ID、UTC时间；不为了此次分页调整改变既有身份错误码或创建资源201语义。写幂等、资源version和权限目录/组织version保持原模型，不将request_id全局改成幂等键。
7. OpenAPI随实现重新生成，精确反映范围、默认值、字段和错误。既有生成项目不会被自动升级；指南列出旧请求/新请求/响应变化，并要求应用方核对所有消费者。若需无停机兼容或已公开给未知调用方，停止该API切换并确认版本迁移方案。

### 3.3 已确认方案：同仓服务入口

沿用唯一标准样例和 `create_service.py`，增加显式 `--source local` 模式。命令仍在**固定兼容提交的脚手架仓库**执行；生成项目不复制模板/创建器，不从已有业务服务复制。使用样例创建时需要脚手架源码，创建完成后的构建、调试和部署不依赖脚手架磁盘位置。

```text
# 已确认用法；运行结果见第8节
uv run --frozen python scripts/create_service.py --source local --project-root <项目目录> --language java --name report-service --package com.acme.report --port 48084
uv run --frozen python scripts/create_service.py --source local --project-root <项目目录> --language python --name scoring-service --package scoring --port 48085
```

- local模式要求port，禁止output，目标固定为`services/<name>`；原独立生成方式保留，`--source`省略时保持原行为，显式`--source submodule`等价原方式。local不接受repo/ref，不触碰.gitmodules、gitlink或Git暂存区。
- 在同构暂存目录生成源码、Python锁及宿主候选变更；复用register/IDE/Compose生成器。新增服务无peer，运行配置归宿主；Python锁使用宿主SDK的相对路径，失败不能改兄弟锁或SDK锁。
- 写入前检查名称、目录、包、端口、路由、必要文件和CI矩阵结构；对计划修改文件记录原始摘要，应用前复核。冲突全部在宿主写入前拒绝；不要求无关本地改动全部提交。
- 同仓模式同时在checks对应语言矩阵追加从标准样例派生的定向用例，保留已有矩阵项及其他job；不支持的自定义矩阵在预检时失败并说明需人工适配，不重写整套workflow。
- 写入中途失败保留暂存材料和已写路径，报告非零；不做全仓reset/stash或自动删除服务目录。重跑遇已存在目录仍拒绝，用户核对恢复后才能重试。简单失败记录足够，不新建事务引擎。
- 新服务初始化仍只登记技术身份/发布权限；用户授权显式完成，不自动扩大既有客户端或角色。构建来源继续使用主仓提交；不建立第二份服务版本账本。

### 3.4 已确认方案：最小发行验收

框架维护入口 `scripts/verify_scaffold.py`，复用现有创建/初始化/运行脚本及浏览器冒烟，不复制其业务实现。入口不导出到生成项目；生成项目仍带可单独调用的smoke。

```text
# 拟新增用法；ref必须能解析到包含本轮实现的固定提交
uv run --frozen python scripts/verify_scaffold.py --ref <提交> --output <不存在的候选目录> --project <唯一项目名> --port-offset <端口偏移> --dev-host <容器可达宿主地址>
```

- 固定顺序：解析并记录提交→预检工具/路径/端口/Docker及网络条件→从提交快照生成→按生成README准备依赖/锁→隔离local初始化（显式with-demo）→启动两业务→等待真实就绪→运行smoke与分页断言→finally停止本次资源→输出报告。默认PG/Redis/Nacos，不启用MQ/监控；不操作生产环境。
- 唯一项目名、Compose项目/网络/卷及实际端口属于本候选；已有同名资源或端口冲突即拒绝。dev-host由执行环境提供并核对可达性，不自动改hosts、防火墙、全局Git或重启Docker。
- 使用独立local演示账号，首次改密凭据只存候选忽略目录；日志/报告不含密码、Cookie、token、完整环境文件及用户响应正文。正常日志只保留步骤、状态、脱敏错误和定位标识。
- `smoke.cjs`增加分页内容断言及未登录拒绝；按新合同请求。每轮创建带唯一marker的记录，以返回ID和精确字段断言，不只用整段响应字符串includes判断。新增服务真实链路作为本轮AC-07定向验收，基础发行入口固定只验证初始双语最小链，不每次创建额外服务。
- 每阶段有有限超时，整个运行上限60分钟；超时/取消也执行受限cleanup。先停止本次拥有的宿主业务进程树，再按本轮记录的应用和infra Compose项目标签停止容器，不能只调用当前compose.py stop；保留卷、候选和证据，不执行全局prune或down -v。cleanup失败也是验收失败，不覆盖原始错误。
- 报告位于候选`.local/release-check/report.json`：schema_version、run_id、确切source_commit、工具版本、生成参数（非秘密）、锁摘要、阶段起止/退出码、断言结果、清理结果及remaining_resources。整体状态仅passed/failed；未执行阶段标not_run；预检连候选都未创建时，向控制台输出同形脱敏失败摘要。
- 重跑使用新的不存在目录及独立项目名；不自动清除失败现场。固定提交可能需要首次解析业务依赖，报告必须记录所得锁摘要，不能只以相同ref宣称二进制依赖完全相同。
- 新增独立`workflow_dispatch`工作流（拟`scaffold-release-check.yml`），运行相同入口。默认使用一次性Ubuntu runner，安装与仓库一致的工具版本及Playwright Chromium，显式确定容器可达宿主地址；不可达必须失败，不改应用鉴权/网络合同。工作流只对可信维护提交手动触发，不从不可信PR启动特权环境。
- CI只上传脱敏report及允许的步骤日志，禁止整目录上传.local；设置任务超时略长于入口上限以留cleanup时间。无continue-on-error，失败报告缺失也不报通过。不自动打tag、push镜像或部署；维护者批准源码发行时必须检查该确切提交的成功报告，后续提交不得复用旧结论。
