## 1. 目标、范围与验收

让维护框架和使用框架开发业务的人都知道：代码放哪里、哪些规则必须遵守、哪些是可选建议、如何运行检查，以及框架升级时如何维护自己的规范。规范必须与可复制的 Java/Python 混合示例、检查配置和发行材料一致。

本次解决的是“开发基线不能完整交付”，不是再建设一个脚手架平台。保留 `services/` 中同时存在 Java/Python 服务的结构，保留 examples 为唯一业务起点，不新增 templates、项目生成 CLI、治理服务或发布控制台。

### 1.1 范围与保持项

- 包含：拆清通用/Java/Python 规范，补齐编辑器与现有质量工具配置；整理两个示例的用例边界、类型和测试；发行带出规范、协作入口与业务测试；写清新项目创建、开发、检查和规范升级流程。
- 框架维护者：公共 SDK/协议适配遵守职责、类型、资源生命周期、错误诊断和定向测试规则；不强迫基础库采用业务 Controller/Service/Repository 目录。
- 业务项目：直接继承框架 parent/SDK，复制并修改业务示例；必须遵守身份、租户和调用边界，自行定义业务规则、业务错误码及领域资料。
- 保持：URL、权限 code/scope、JSON 字段、HTTP 状态、tenant/SELF 过滤、迁移历史、BFF、安全校验、Sentinel/AnyIO 资源名及参数语义不变。
- 不包含：全仓重命名/格式化、整体改写 identity-service、切换 ORM、强制 DDD/CQRS、Service/ServiceImpl 成对生成、覆盖率硬指标、引入 Sonar/新的架构检查框架。
- 管理前端沿用已有 ESLint/Prettier/vue-tsc，不另建前端规范体系；业务前端尚未选型，不替以后项目指定 Vue/React 或提供菜单权限。
- 上轮 Sentinel 未执行的跨版本整体回退、独立项目熔断恢复和真实双机/外部 IdP 验收继续归原计划；本计划不得将其顺带标为完成，也不把它们变成本次纯工程整理的先决条件。

### 3.2 目录与编码约束

保持架构确定的“服务内按层组织，可在层内按领域扩展”，本次不改为 DDD 或按领域整套迁移。

- **Java：**启动/配置在根或 config；HTTP 在 controller，接口类型在 controller/dto；用例在 service；持久化在 dal，JDBC 具体 Repository 可直接放 dal；Client 放 client。SQL 查询结果用明确 record/类型，不将无边界 Map 从 DAL 传至 API。小范围复用的内部类型允许嵌套 record，不为每一个 record 拆独立文件。已有持久化方式继续使用，不为“Mapper 规范”强加 MyBatis。
- **Python：**main.py 保留 create_app/main 与装配；config.py 放本服务 typed 设置；api/items.py、schemas/items.py、services/items.py、repositories/items.py、clients/peer.py 各承载真实职责。保持 async SQLAlchemy/原生 SQL，不增加不用的 ORM models。需要的 sessions/runtime/client 通过应用装配和依赖传入，导入模块不能立即联网或读取本地秘密。
- **两语言：**API 做协议校验与 SDK 权限入口；Service 做可信主体、用例、数据范围和事务；Repository 只访问本服务数据，不反向依赖 API；Client 使用现有 SDK 发送已授权上下文。鉴权不移动到不受保护的内网默认信任模式。
- **类型与响应：**替换示例的任意 Map/dict 为 DTO/typed result，但 JSON code/message/data/request_id、列表字段和 peer 转发结果完全保持。DAO 结果与 API 不靠反射复制安全字段；不为了三层强制每层创建内容相同的对象。
- **异常：**禁止吞错返回空成功；对外返回稳定 code，内部保留脱敏的失败阶段和关联 ID，不打印 token/密码/完整参数。不能为了“保留 cause”重新暴露含凭据 URL；第三方异常仅在明确边界转换。
- **并发：**资源在 lifespan/close 管理，事务包围本地数据库操作，远程调用不持有长期数据库事务。基础库 Reactor 链不能 block，普通 Servlet 示例可在既有请求预算内等待；Python async 中禁止阻塞 IO。保留 runtime.install→security 安装顺序及实际完成后释放名额。
- **复杂度：**不设机械的函数行数、文件大小或接口比例；人工审查以是否混入多个职责、是否可测试及调用方向为准。不自建万能 BaseController/Repository/统一 DSL。

## 4. 新项目实际怎么用

以下操作路径已在本次本地候选中落地；此前 rc.3 历史发行不自动获得这些文件，必须取得包含本次开发基线的新候选材料。

1. **取得发行包并展开：**核对 manifest；建立自己的 Git 仓库；先看根 README，再看三份规范中的通用和对应语言部分。services 同时包含两语言，身份后台仍由 identity-service 镜像提供。
2. **安装开发依赖：**Java 继承固定 parent/foundation 制品；Python 在自身服务安装 frozen dev 组；根 uv 环境只用于配置/迁移等工具。前提是可访问依赖仓库或已有完整缓存，不宣称完全离线。
3. **先通过静态检查和服务内定向测试：**不必启动 PG/Redis/Nacos 就能运行 DTO/参数/用例单元测试。数据库与跨服务验证另按所改合同启动依赖，不把每次格式检查做成完整部署。
4. **改为自己的业务：**同步包/模块名、项目元数据、启动入口、权限文件、Nacos Data ID、audience、资源与 Compose；指南列出全部位置，不能只改文件夹名。沿用现有绑定/发布工具，不新增框架初始化命令。
5. **以新增一条业务记录为例：**先定义允许的请求/响应字段；涉及数据库则新增迁移（不改已应用 V1）；Repository 写本服务查询，Service 确定可信 tenant/owner、用例和事务，API 声明权限并完成协议转换。远程调用只在 Client 中使用 SDK，不在 Controller 手写重试。
6. **补充对应验证：**输入非法、正常用例、异常传播；涉及权限/数据范围时测无权限、跨租户和 SELF；涉及 SQL/RLS 时使用真实受限 PG 账号。测试文件跟业务源码提交并随示例交付。
7. **提交前按改动选择：**只执行相关服务的 formatter check、lint/type、点名测试和必要 build。改文档仅检查本地链接；改 Compose/入口才做配置展开或对应运行验证。失败只重跑关联部分。
8. **升级：**分别比较规范/工具配置、SDK/parent、部署材料；保留自己的补充规范。工具升级不等同于数据库升级，不执行隐式 DDL；版本/行为变更按对应发行说明验收。

## 7. 风险、恢复与交接自检

- **规范过重：**只定义真实职责，允许小型嵌套类型和 JDBC Repository；不新增空层、抽象工厂、项目生成器或强制工具平台。
- **改类型改变 JSON：**显式保留已有字段/状态并做协议断言；异常路径保持，禁止改变断言迁就输出。
- **Python 拆分造成循环依赖或重复资源：**main 单点装配；API 注入 Service，Service 注入 Repository/Client；底层不得 import main；pool/runtime 仍按进程一份。
- **发布漏文档/测试：**路径白名单与包内容测试；四份交付文档链接闭合；不为了方便复制整个仓库或历史计划。
- **开发工具进生产：**dev 与运行锁/安装命令分离；检查镜像构建输入，不能通过把 Ruff/pytest 放进 SDK runtime dependencies 解决缺包。
- **升级覆盖业务规则：**保留 baseline，项目补充文件不由框架生成；失败可还原本次规范、工具和示例提交，不需要数据库回退。本次不改已应用迁移。
- **验证无限扩大：**选择范围已在第 6 节给出；不使用全仓测试/全环境压力测试补偿不明确的验收，不重跑上轮无关长故障脚本。

交接自检：8 项 AC 均有任务/验证；T 依赖无环；现有与拟新增路径区分；设计的目录权威与规范分工不倒置；工具版本取自现有锁文件；当前运行语义明确保持；没有等执行者临时决定的 ORM/前端/生成器选型。实现时若事实偏离该基线，只报告具体冲突并修订受影响任务，不重新设计整套框架。
