# 实施计划

本目录只记录实施范围、任务和验证证据。长期行为合同在 [专题设计索引](../01-文档导航.md)；计划不再混写一整套设计。

## 何时建立计划

跨三个及以上逻辑模块，或改变架构、公共 API、数据库、认证授权、配置、构建部署、迁移兼容，以及用户明确要求时建立计划。普通局部改动按协作规则在对话中确认，不机械增加文档。

## 命名和使用

实施计划按 `ken-code-spec` 使用 `YYYY-MM-DD-主题-plan.md`，例如 `2026-10-27-限流熔断与并发保护-plan.md`。日期为首次编制日期；修订只更新正文版本、状态和记录，不更换文件名。同日不同工作使用不同主题。模板为 [_plan-template.md](_plan-template.md)，本目录说明保留 `README.md`。设计、指南和编码规范仍使用编号中文文件名。

1. 核实代码基线和影响，解决重要未决选择。尚待用户确认的行为修订可在计划中作为明确标注的提案，不能假装已生效设计；确认后先同步权威设计，再开始相关代码任务。
2. 记录设计文件、基线号、精确章节链接及实施边界，避免复制合同产生漂移。
3. 写明 AC 场景与预期，按独立行为拆 T 任务/依赖，列出入口、保持项、完成证据和停止条件。
4. 完成交接自检并确认后实施；本次文档编辑不等于批准代码/部署。
5. 开工只核对计划依赖的事实；实质偏差同步修订设计/计划并重新确认。
6. 完成当次代码后集中补写并运行相关测试，阶段完成时记录真实命令/报告/现场证据；未验证不标完成。

状态为：草稿 → 已确认 → 执行中 → 待验收 → 已完成。用户要求终止原范围或冻结时标记“已冻结”，保留原文证据与历史授权但禁止继续执行；未完成任务不标为完成。后续范围另建日期主题计划，经确认后实施。外部环境缺失时记录阻碍和未验证项，不将“无法测试”标为验收通过。

已完成计划是历史证据，保留对应设计基线；后续新任务使用新计划。[限流熔断与并发保护](2026-10-27-限流熔断与并发保护-plan.md)已完成实现和主要本地验证，仍有未验证子场景；编码规范改进已完成本计划范围的实现和本地验收，见下方计划。[混合项目接入与审查修正](2026-10-27-混合项目接入与审查修正-plan.md)与[通用微服务框架精简](2026-10-27-通用微服务框架精简-plan.md)保留本地候选证据，真实双机和外部提供方验收仍未完成；[旧微服务框架实施计划](2026-10-26-微服务框架-plan.md)已冻结。
