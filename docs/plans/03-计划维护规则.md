# 实施计划

本目录只记录实施范围、任务和验证证据。长期行为合同在 [专题设计索引](../01-文档导航.md)；计划不再混写一整套设计。

## 何时建立计划

跨三个及以上逻辑模块，或改变架构、公共 API、数据库、认证授权、配置、构建部署、迁移兼容，以及用户明确要求时建立计划。普通局部改动按协作规则在对话中确认，不机械增加文档。

## 命名和使用

文件采用 `NN-中文主题实施计划.md`，例如 `01-微服务框架实施计划.md`；日期记录在正文。按目录分配未使用编号，不随修改时间重排或复用历史编号；从 [实施计划模板](02-实施计划模板.md) 开始。

1. 核实代码基线和影响，解决重要未决选择；若改变既有设计，先同步修改权威设计。
2. 记录设计文件、基线号、精确章节链接及实施边界，避免复制合同产生漂移。
3. 写明 AC 场景与预期，按独立行为拆 T 任务/依赖，列出入口、保持项、完成证据和停止条件。
4. 完成交接自检并确认后实施；本次文档编辑不等于批准代码/部署。
5. 开工只核对计划依赖的事实；实质偏差同步修订设计/计划并重新确认。
6. 完成当次代码后集中补写并运行相关测试，阶段完成时记录真实命令/报告/现场证据；未验证不标完成。

状态为：草稿 → 已确认 → 执行中 → 待验收 → 已完成。用户要求终止原范围或冻结时标记“已冻结”，保留原文证据与历史授权但禁止继续执行；未完成任务不标为完成。后续范围另用新编号计划，经确认后实施。外部环境缺失时记录阻碍和未验证项，不将“无法测试”标为验收通过。

已完成计划是历史证据，保留对应设计基线；后续新任务使用新计划。当前入口：[通用微服务框架精简实施计划](04-通用微服务框架精简实施计划.md)（草稿，待确认）；[旧微服务框架实施计划](01-微服务框架实施计划.md)已冻结。
