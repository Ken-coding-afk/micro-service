### 3.2 校验归属：完成清单，不再批量删 if

建立“输入来源—入口校验—内部消费者—保留约束—测试”表，放在本计划执行记录中。上轮已删除项纳入表，不重新制造一套 Validator 框架。

- Controller 负责 HTTP 字段存在性、形状和可转换类型；Service 负责状态、授权、对象归属和持久化版本冲突；Repository/DB 保留参数化 SQL、约束及 RLS。
- 协议、消息、maintenance 和公共 SDK API 是不同入口，不能用某个 Controller 已检查作为其删除依据。
- 对多入口调用必须逐一列出来源；没有上游保证的检查保留。未来新增内部入口必须在该入口建立相同输入合同，不能恢复层层校验。

### 3.3 出站调用：共享预算与关联头，保留两个协议适配入口

**选择最小共享机制，不新增第二套 HTTP 客户端框架。** 在 Java SDK 的 `foundation/http` 下新增拟名 `OutboundCallBudget`，由 `ServiceHttpClient` 与 `BffIdentityClient` 实际共同使用。

共享对象只负责：

1. 从当前时间、响应预算、父 CallContext 计算唯一的有效 deadline，取父预算与本地预算较小者；过期返回零剩余预算。
2. 同时记录单调时间截止点；每次剩余时间取墙上时钟与单调时钟剩余值较小者，不因重试或读取 body 重新起算。
3. 将当前 request_id、traceparent、有效 `X-Request-Deadline` 写入请求头。只处理这三个头；不处理 Authorization、Cookie 或 Content-Type，也不把上次请求头留到下次请求。

SDK 在一次逻辑调用开始时创建对象，全部 GET 尝试共享；BFF 在 `Mono.deferContextual` 的每次实际订阅时创建。预算耗尽必须在选实例/发送请求前终止。构造器已有的 budget 校验仍留在公共入口，不逐次重验配置。

**已发现的实际差异要修正：**BFF 本地时限会取较小值，但下发的头目前仍用父 deadline；改为下发同一个有效 deadline。SDK/BFF 各自把耗尽映射为既有错误，不统一成一个新的错误码。

仍分别保留：

- ServiceHttpClient 的 Future API、JSON/类型化 API、GET 重试、发现失效策略、Sentinel、连接池及资源关闭。
- BFF 的 OAuth WebClient、Basic/form、URI 白名单、2 MiB 响应上限、状态转换、完整 body 的时限、授权码/刷新/撤销零重试。
- Reactor Netty 装配与池配置按使用场景保留；不为消除几行 builder 重复改变池上限或让内省/BFF 共享业务小并发桶。

`application()` 暂不单独改走 SDK Future API，因为保留统一 BFF WebClient 更容易维持取消、错误和 body 限额。两者继续使用现有 ServiceDiscovery，本轮不另造服务选择器。只在已有确切复用点提取方法，不暴露任意 URL/凭据透传 API。

### 3.4 身份服务租户上下文：集中实现，事务归属保持

在 identity 内部 `dal/support` 新增拟名 `IdentityTenantScope`，只被 LoginStore、UserTokenStore、ExternalIdentities 使用；不扩展为业务 SDK 的“任意切换租户”接口，不接受浏览器 tenant header。

建议入口 `within(UUID tenant, Supplier<T> operation)`，依赖现有同一数据源的 JdbcTemplate 和事务管理器，使用 `PROPAGATION_MANDATORY` 参与现有事务，不开启独立事务、不抢先提交。

明确行为：

1. 无事务拒绝；tenant 为 null 表示既有平台路径，写空字符串。租户值必须由调用方现有的服务端解析/身份验证取得。
2. 读取当前 LOCAL 值；已有非空租户与目标不同（含切回平台）时拒绝；同租户嵌套允许。
3. 设置 LOCAL 后执行数据操作；正常返回恢复原 LOCAL 值，不提交外层事务。
4. 数据操作或正常恢复 SQL 抛异常时，由参与事务标记回滚；直接传播原错误，不在已失败的 SQL 事务里再次恢复并覆盖原错误。即使外层捕获运行异常，也不能提交本应回滚的写入。
5. 预期的 OAuth 拒绝/重放撤销等由现有协议层 Outcome 机制决定提交，不能把该机制改为统一抛异常。共享 scope 包围数据访问，不能扩大到原本有意提交撤销的整个协议控制流程。
6. ExternalIdentities 的范围覆盖原 `scope()` 后到该事务内相关操作结束；租户有效性检查、catalog 锁、绑定唯一性、会话撤销和审计顺序保持。

现有三个调用点统一接入后删除各自的重复 set_config 包装。迁移前先检查是否有调用方依赖“捕获作用域内部运行错误后仍提交”：若发现，登记其现行业务合同并暂停 T-03，不静默改变。该检查是防止事实冲突，不将事务语义选择留给执行者。

真实 PG 验证是交付门槛：受限运行账号、同连接观测、异常回滚、池复用均需要证据。mock 只能验证装配，不能代替 AC-03。

### 3.5 成功信封与 BFF 主流程

- 将已有 `IdentityApiResponses` 移到 identity 的公共 controller 支持包（拟定 `controller/support`），供 management 与 oauth 使用。复用现有 Map 输出和 header 逻辑，不新增全局 ResponseBodyAdvice，不给 OAuth token/授权协议响应套普通 API 信封。
- `CurrentApplicationController` 调用同一个 helper，继续保留服务端 APPLICATION_VIEW 必需性校验；不把“view 缺失”包装成成功。
- 在 `BffNamespace` 集中现有登录成功/退出目的地映射；登录成功处理器抽成一个有明确职责的方法，保留 CSRF 清理→session ID 轮换→303 顺序。
- 对两处重复 OAuth 错误码集合只复用“是否凭据错误”的判定；Spring 登录入口仍返回 AuthenticationException，API/刷新路径仍返回 PlatformException，不用统一异常破坏协议。
- `BffRelay.filter` 按“路由归属检查→读取当前身份→实时身份/audience 比对→设置上下文并转发”整理成少量私有方法。保留 RateSubject 写入、Cookie 移除、Bearer 注入、Reactor context 与 401 会话失效顺序；不创建另一组授权策略类。
- 本轮不拆 UserProtocolProvider.authenticate / PasswordLoginService.authenticate 的事务流程。长度本身不是缺陷；前者还有“拒绝但提交撤销”的明确行为，不能为 R4 的行数评价扩大认证重构。
