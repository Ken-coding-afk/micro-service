## 1. 目标、范围与验收

让新项目通过标准组件配置和已有 SDK 接入获得请求限流、并发保护、超时与 Java 依赖熔断；不要求业务重写技术保护，也不替业务决定配额、排队和降级结果。Java 的统计型并发流控与 Python 的许可上限有明确差异，见 3.3，不以统一名称掩盖组件语义。

### 1.1 选型结论与职责

| 层次 | 方案 | 框架负责 | 项目负责 |
| --- | --- | --- | --- |
| 对外网关 | **基于 Spring Cloud Gateway WebFlux 原生路由/过滤器重整网关** | 标准路由、Nacos 发现接入、认证/BFF、安全边界、Redis 限流、统一错误 | 声明公开 API、audience、限流参数 |
| Java 服务 | Sentinel 官方核心、异步 Entry 与 Nacos 数据源 | 入站/出站并发流控、依赖熔断、原生规则与指标 | 声明需要保护的依赖、业务幂等和降级 |
| Python 服务 | AnyIO CapacityLimiter、HTTPX | 入站容量、出站并发、连接池、超时/取消和统一错误 | 业务资源分组、CPU/GPU 任务执行方式、外部供应商策略 |
| 配置 | Git 中配置源 → 现有发布工具 → Nacos | 校验来源及安全边界，按成熟组件格式加载 | 修改参数、审核、发布；Sentinel 规则动态生效，其他启动参数重启 |
| 运行 | 现有 Compose、Redis、Nacos、观测入口 | 同版制品、混合示例、故障验证 | 实际机器容量测量和生产阈值 |

本次**不默认给 Python SDK 增加通用熔断器**。Python 到内部服务先获得有界并发、连接池和 deadline；某个业务必须对外部模型/支付等依赖熔断时，需要按该依赖评审成熟客户端/代理的能力。它不是本计划的未完成任务，也不以“Java 有所以 Python 必须再造一套”扩张范围。框架不得宣传已经实现跨语言完全等价的熔断。

不新增微服务、Sidecar、治理控制台、数据库表、分布式信号量、自研熔断算法或跨语言配置 DSL。不引入 Dapr/Istio，不建设 Agent 调度、租户套餐计费、严格全局运行名额、消息任务重试体系。identity-service 不承载这些业务功能，只在适用 API 上使用通用保护。

### 1.2 为什么重新选择后仍推荐 Spring Cloud Gateway

| 路线 | 优势与成本 | 本次判断 |
| --- | --- | --- |
| SCG 原生能力 + Spring Security（Java 服务另用 Sentinel） | 与已选 Spring/Nacos、opaque token、服务独立 audience、浏览器服务端会话一致；需要少量身份上下文和错误适配 | 推荐；**保留产品选型，不保留旧自定义路由 DSL** |
| APISIX | 成熟独立网关，提供 OIDC、限流等插件；适合主要依靠网关插件治理的团队 | 可行替代，但当前多 audience 内省凭据、BFF 撤权/会话及插件执行顺序需要重新验证；不能假定装插件即等价替换 |
| Dapr/Service Mesh | 适合统一大量跨语言调用治理 | 会改变运行拓扑、调用入口和运维体系，不是本次简单框架的必要条件 |

依据是匹配本项目约束及减少长期自定义实现，不是旧代码量或已投入成本。当前 Gateway 确实有“原生 Spring 路由非空即拒绝”的限制；本次删除这项限制及重复的路由模型，直接使用标准配置和过滤器。若实施发现选定组件无法满足安全合同，停止对应任务并报告，不通过继续堆自研代理逻辑补齐。

### 1.3 可观察验收

| AC | 场景与输入 | 可观察预期 |
| --- | --- | --- |
| AC-01 | 独立混合项目用标准 SCG 路由配置接入 | 不改 Gateway 源码即可公开 Java/Python API；旧 gateway.routes 明确报迁移错误；无两套路由真相 |
| AC-02 | 两个 Gateway 实例收到同租户同逻辑路由的并发请求 | 共享 Redis 令牌桶；BFF 与 Bearer 入口不能获得双份额度；不同项目/环境/租户互不串桶 |
| AC-03 | 伪造 tenant/client 头、无效 Token、跨 audience 或 Redis 故障 | 伪造不能改变桶；未认证请求不转发；Redis 故障返回 503，不默认放行 |
| AC-04 | Java/Python 入站名额耗尽，绕过 Gateway 从受控内网调用 | 已达到并发阈值时后续请求快速返回 503；Java 按 Sentinel 统计型流控验收，Python 按许可上限验收，差异见 3.3；健康检查仍可响应 |
| AC-05 | Java/Python SDK 对指定依赖并发、超时、取消 | 出站名额与连接等待均有界；取消/错误正确释放；同步线程仍执行时不提前释放执行名额 |
| AC-06 | Java 被保护依赖持续故障、恢复、半开并发 | 官方熔断器按声明参数打开、快速拒绝、单探针恢复；业务 4xx/本地拒绝/客户端取消不作为依赖失败 |
| AC-07 | GET、写入、429、503、半开探针遇到故障 | 重试只有 SDK 一处；GET 最多额外一次且不延长总预算；写入不自动重放，HTTP 错误响应不默认重试 |
| AC-08 | 配置错误、配置修改、旧项目升级/回退 | 初始错误在注册前拒绝；Sentinel 合法规则动态生效、非法更新保留上一版；其他参数重启；新旧格式不混读；同版配置/制品可回退 |
| AC-09 | SSE/异步响应、BFF 会话及 OAuth 回归 | 不聚合流、不重试整段流；响应开始后不伪造第二个 HTTP 错误；现有认证、Cookie/CSRF、撤权与租户边界不退化 |
| AC-10 | 从新候选发行物复制独立混合项目并执行指南 | Java↔Python、限流、并发拒绝及 Java 熔断可观察；能说明每个保护发生在哪里、如何调参；无框架源码构建依赖 |

### 3.2 网关：使用原生路由，框架保留必要安全适配

1. 项目在 `config/nacos/api-gateway.yaml` 使用 `spring.cloud.gateway.server.webflux.routes`。路由使用原生 `id/uri/predicates/filters/metadata`，目标为 `lb://服务名`；服务发现交给现有 Nacos/LoadBalancer。不开启“发现即自动公开全部服务”。
2. 业务路由 metadata 只补必要身份信息：`platform.audience`。逻辑限流名默认等于原生 route id；BFF 派生路由携带原 route id，不按 URL 拼接桶。RedisRateLimiter 本身也把 routeId 纳入 Redis key，因此适配必须将传入 isAllowed 的派生 routeId 归一到原 routeId，不能只归一 KeyResolver。框架不提供任意脚本/表达式执行入口。
3. 原生 routes 是唯一来源。退役 `gateway.routes`、`GatewayRouteSpec` 的自定义路由解析和“禁止 Spring routes”限制；不能把原生配置再转回旧四字段模型。旧格式启动/发布时给出明确迁移错误，不静默忽略。
4. 使用原生路由选择结果。Bearer 鉴权可在选路后的安全 GlobalFilter 中委托 Spring 官方 ReactiveAuthenticationManager；它必须先于限流和 Netty 转发执行。不再单独用一张按路径匹配的安全路由表选择 audience。BFF 的浏览器登录、CSRF 和会话继续由 Spring Security 处理，其代理调用再获得同一 audience 的可信主体。
5. 业务路由必须有 audience；未知路由拒绝，缺失元数据启动失败。固定身份协议/页面例外由框架声明，项目不能通过添加 public=true 绕过认证。仅允许受控的 `lb://` 目标；禁止把 `/internal/**`、内省管理端点或任意外部 URL 借路由公开。
6. BFF 业务入口由同一个原生 RouteDefinition 派生：复制相同原生限流参数，再加入固定前缀处理及凭据头清理。请求只经过其中一个业务入口，不执行两次扣令牌。管理 BFF 的固定路径仍按已有协议生成，不让项目重新配置登录流程。
7. 限流采用官方 RedisRateLimiter 令牌桶；框架只实现可信 KeyResolver、失败适配和统一错误。租户用户桶：`project/env/tenant/逻辑路由`；机器桶：`project/env/client_id/逻辑路由`；已验证的平台账号没有 tenant_id，使用 `project/env/platform/subject/逻辑路由`。身份类型只能来自内省后的主体，缺少应有身份字段则拒绝，不能回退到匿名公共桶；三种类型使用不同前缀防止键碰撞。编码使用结构化字段摘要，不能让标识中的分隔符拼出另一租户的键。
8. Redis 连接从 BFF 条件配置中抽离成网关共用连接配置，复用原有 endpoint、secret、TLS 要求；无 BFF 时限流也可工作。限流和会话使用不同键前缀，不增加 Redis 容器。
9. Redis 故障采用拒绝策略，返回 `503 RATE_LIMIT_UNAVAILABLE`。官方实现把异常转换为 allowed=true、remaining=-1；薄适配继承官方 RedisRateLimiter 并在 isAllowed 结果处识别该标志及缺失/异常结果，保留官方配置绑定和脚本执行，不能只在外层 onErrorResume。固定启用内部 remaining 信息，响应输出可脱敏；升级 SCG 必须重跑这个组件合同测试。不复制一套 Lua 令牌桶。
10. 登录/验证码等匿名保护继续使用既有 LoginProtection；业务租户桶不覆盖匿名攻击防护。入口 DDoS/WAF 属于部署平台。本计划不宣称租户限流可以保护认证前的一切资源。

拟议配置示例（待实现后才能被当前发布工具接受）：

```yaml
spring:
  cloud:
    gateway:
      server:
        webflux:
          routes:
            - id: sample-python
              uri: lb://sample-python-service
              predicates:
                - Path=/api/v1/python-items/**
              metadata:
                platform.audience: sample-python-service
              filters:
                - name: RequestRateLimiter
                  args:
                    key-resolver: '#{@tenantOrClientKeyResolver}'
                    rate-limiter: '#{@platformRedisRateLimiter}'
                    redis-rate-limiter.replenishRate: 20
                    redis-rate-limiter.burstCapacity: 40
                    redis-rate-limiter.requestedTokens: 1
```

这里是每秒补充 20 个令牌、桶最多 40 个，允许突发；**不是固定一秒最多 20 个**。示例数值用于接入和验证，不是容量承诺。未声明限流过滤器的路由不自动获得配额。网关不叠加 Sentinel、依赖熔断或 Retry；本次不引入 SCG CircuitBreaker 所依赖的另一套熔断库。网关共享租户额度与 Java 进程资源保护各有职责，不在同一边界重复计数。

### 3.3 服务入站：使用 Sentinel 并发流控

- Java 使用 Sentinel `FlowRule`，`grade=0`（并发线程数）、`strategy=0`（直接）、`controlBehavior=0`（快速拒绝）；统一资源名 `http.inbound`。Python 使用 AnyIO CapacityLimiter。两者均不排队，事件循环中禁止阻塞等待。
- **不将 Sentinel 并发流控描述为严格信号量。** 它基于资源当前并发统计检查，检查与计数不是一次原子抢占；极短并发竞争下可能越过阈值。本任务以过载快速拒绝和正确资源生命周期为目标，不为保持旧表述再写一套原子并发引擎。数据库连接池、线程池等真实资源仍应有自身上限；严格 GPU 执行名额由业务资源池负责。Python CapacityLimiter 则提供进程内许可限制。
- 覆盖 `/api/v1/**`、`/internal/v1/**` 业务 HTTP，排除健康检查和 OAuth/OIDC 协议端点。准入在昂贵处理前执行，不依赖外部租户头；忙时可先返回 503，但不能跳过鉴权后执行业务。
- Java 异步请求使用官方 `AsyncEntry`，持有到 Servlet/Reactive 请求实际结束；禁止用同步 `@SentinelResource` 包住“创建 Future”就声称保护整个异步执行。Python 持有许可到 ASGI 请求结束。完成、错误、取消路径确保只 exit/release 一次。
- 客户端断连但同步线程仍执行时，资源占用不能提前结束。Python 不使用 `abandon_on_cancel=True` 把仍运行线程当作完成。HTTP 准入不承担 CPU/GPU 调度或后台任务取消。
- 阈值是每进程的：副本和 Uvicorn worker 各自计数。通过 Nacos 下发相同规则不会共享计数；本次不部署 Sentinel Token Server，不启用集群规则。Gateway 的跨节点租户桶仍使用 Redis。

### 3.4 出站调用：Sentinel 原生资源与熔断

Java 保留 `ServiceHttpClient.request(...)`，Python 保留 `await ServiceHttpClient.request(...)`。Java 资源名为 `http.outbound/<逻辑服务名>`，对同一依赖的所有实例合并治理；不能使用租户、用户、完整 URL 动态生成无限资源。资源名由 SDK 固定生成，业务规则文件按此命名。

Java 使用 Spring Cloud Alibaba 2025.1.0.0 BOM 管理的 Sentinel 1.8.9 核心和 `sentinel-datasource-nacos`，沿用官方 AsyncEntry/Tracer/规则管理 API；Reactor 适配按实际生命周期复用。不再引入上一版 Java 熔断组件，不擅升 Boot/Cloud。基础包中的自动装配仅在服务明确启用时执行，不能因 Gateway 引用 foundation 就自动重复装配 Servlet、WebClient 或网关埋点；不同时启用自动 WebClient 埋点和 SDK 手工埋点。

**统计单位为一次逻辑 SDK 调用。** 顺序为：检查 deadline 和发现实例 → Sentinel 异步准入（并发与熔断）→ 执行 HTTP 与允许的 GET 重试 → 读取完整普通响应 → 记录最终分类 → exit。整个逻辑调用占一个 Entry；失败后一次 GET 重试仍受原 deadline 和 Entry 约束，不累计成两个熔断样本。半开探针也是一个逻辑调用，可能包含最多两次 HTTP 尝试；不读取或修改 Sentinel 私有状态以另写探针策略。熔断拒绝不重试。

Sentinel 采用原生异常比例策略：`grade=1`、`count=0.5`、`minRequestAmount=10`、`statIntervalMs=10000`、`timeWindow=20`。即 10 秒统计窗口内至少 10 次完成且异常比例**大于** 50% 时打开 20 秒，之后由官方单逻辑探针恢复；不是旧版“最近 20 次调用”的计数窗口。一个逻辑探针仍受现有 10 秒整体 deadline 限制，不虚构组件的半开超时配置。

| 结果 | Sentinel 记录 | 重试 |
| --- | --- | --- |
| 最终传输失败、实际 I/O 超时、500/502/503/504 | 在当前 AsyncEntry 上通过官方 Tracer 记录一次远端失败 | 只有传输失败/超时且 GET、还有预算时最多额外一次；HTTP 错误响应不重试 |
| 2xx/3xx/业务 4xx（含 429） | 无远端异常，计入正常完成样本；不代表业务成功 | 无 |
| 调用前预算耗尽、无实例、Sentinel BlockException | 不创建成功 Entry 或按原生拒绝处理，不主动 trace 为远端故障 | 无 |
| 本地连接池等待失败、客户端取消 | 不主动 trace 为远端异常；如已有 Entry，按官方 exit 语义完成 | 无 |

保留原有 HTTP 响应对象和状态；对 5xx trace 仅用于统计，不能吞掉响应或伪造成功。仅真实网络尝试失败才失效对应实例，本地忙、熔断、取消不摘除健康实例。选用按 Entry 的 Tracer API，不能在异步线程上依赖错误的 ThreadLocal 上下文。

**原生取消语义的边界：** Sentinel 无异常退出的 Entry 可进入总样本，半开取消也可能使原生异常比例熔断器回到 CLOSED。本计划不承诺“取消完全不影响熔断统计”，不为该差异修改其内部状态机；独立记录取消指标，探针恢复指标不能解释成一次业务成功。取消必须关闭实际网络订阅、结束 Entry，不留永久并发占用。若业务需要更严格的恢复证明，应另行评审，不静默增加自研熔断层。

连接池仍采用 Reactor Netty ConnectionProvider / HTTPX Limits，有界等待并受 deadline 限制；创建者负责关闭，外部注入的客户端由注入方负责。内省/BFF 客户端不与业务调用共用一个小并发桶。绕过 SDK 的外部 HTTP 调用不宣称自动受到保护。

### 3.5 规则来源、配置字段与生效

Java 使用 Sentinel 原生 FlowRule/DegradeRule JSON，不再保留原 Java 组件的实例配置，也不建立跨语言 protection DSL。Git 中规则源经现有发布工具进入 Nacos；官方 NacosDataSource 负责订阅，框架只负责来源、资源命名、整份校验与启动检查。Dashboard 可独立评估，本次不部署、不作为运行依赖，也不开发规则控制台。

沿用项目/环境 namespace 和 DEFAULT_GROUP，新增以下文件/Data ID（拟新增，当前发布工具尚不支持）：

```text
config/nacos/
├── api-gateway.yaml
├── sample-java-service.yaml
├── sample-java-service-sentinel-flow.json
├── sample-java-service-sentinel-degrade.json
└── sample-python-service.yaml
```

Java 服务 YAML 使用原生开关 `spring.cloud.sentinel.enabled: true`。启用后由框架按服务名确定上述两个 Data ID，复用现有 Nacos 地址、namespace、凭据与 TLS 绑定，不在规则文件重复填写秘密；缺省未启用则不创建治理数据源。DataSource 的启动、关闭归服务 runtime，避免监听器和客户端泄漏。官方数据源日志可能格式化连接 Properties，传入的 Properties 必须对 toString 脱敏，并在测试中验证哨兵密码不进入日志。

FlowRule 示例（入站 64、出站 32，数字仅用于演示）：

```json
[
  {"resource":"http.inbound","grade":0,"count":64,"strategy":0,"controlBehavior":0,"clusterMode":false},
  {"resource":"http.outbound/sample-python-service","grade":0,"count":32,"strategy":0,"controlBehavior":0,"clusterMode":false}
]
```

DegradeRule 示例：

```json
[
  {"resource":"http.outbound/sample-python-service","grade":1,"count":0.5,"timeWindow":20,"minRequestAmount":10,"statIntervalMs":10000}
]
```

本次接受上述字段，`limitApp` 仅允许默认来源，规则资源必须匹配固定入站名或合法逻辑服务名；禁用正则资源/集群模式，不开放额外规则策略或任意异常类配置。FlowRule 的并发 count 必须为正整数；DegradeRule 依组件范围验证，重复资源规则拒绝。将 JSON 先完整校验再交给官方管理器，不能让原生“跳过非法项”导致保护悄悄消失。

| 配置 | 行为 | 生效 |
| --- | --- | --- |
| Gateway 原生路由及 Redis 令牌桶参数 | 保持 3.2 的原生配置和范围校验 | 重启 Gateway |
| Sentinel FlowRule / DegradeRule | 同一 Data ID 整份验证、整份替换；不同规则种类独立生效 | 原生 Nacos 监听动态更新，不重启 |
| Sentinel 启用开关、Nacos 连接与资源代码 | 随服务启动确定 | 重启/发版 |
| Python `concurrency.inbound_limit`、`concurrency.outbound_limits` | 缺省关闭，声明值必须是正整数；按指定依赖启用 | 重启 Python 服务 |
| SDK `http.max_connections: 64`、`max_keepalive_connections: 32` | 正整数且 keepalive ≤ max；Python 为客户端总池，Java 为远端池，不宣称相同总量 | 重启 |
| Java pendingAcquireMaxCount=64；两语言池等待上限 1 秒 | 等待同时受剩余 deadline 限制；池等待失败映射 DEPENDENCY_BUSY | 固定框架策略，不另开无限队列 |

Spring/Sentinel 原生字段允许其 camelCase/连字符格式，不改成另一套别名。其他公共参数继续现有来源和字段规则；Python 不加载 Java 规则文件。Gateway 原生 filter 的允许范围仍为 Path、lb://、RequestRateLimiter，安全/BFF 固定装配；不允许 Retry、任意 SpEL 或绕过鉴权的重写。

**动态更新及失败处理：**

1. 启用 Sentinel 时，首次必须读到两个有效 JSON 数组，完成校验后才能注册/ready；缺失、空白、非法配置或无法读取时启动失败，不把空配置当成默认放行。显式 `[]` 表示有意停用该类规则，发布必须展示删除差异。
2. 运行中收到合法更新，由对应官方 RuleManager 替换该类规则；非法、空白、删除或连接中断保留最后有效规则并记录错误，不发布空数组替代。首次没有有效规则时不使用不明来源本地缓存绕过启动校验。启动使用已有 NacosConfigReader 的网络读取完成核验；不能只依赖会吞初始异常/读取缓存的 NacosDataSource 构造器。
3. 两个 Data ID **不是跨文档事务**，多节点监听也是最终收敛。分别输出有效规则摘要/加载时间；发布验收核对所有目标实例的 flow/degrade 摘要，不把“写入 Nacos 成功”当作“全部节点生效”。不为此建设自研版本协调服务。
4. 调低并发阈值只影响新准入，不取消在途请求；修改/删除熔断规则可能重建状态和统计窗口，遵循组件语义，不承诺继承 OPEN 状态。回退规则是发布旧有效内容；无需重启，但同样要验证各实例已收敛。
5. 路由、HTTP 池、Python 并发等重启字段仍保持旧快照并提示需重启；只有 Sentinel 原生规则使用上述动态通道。Redis 桶按原 key 延续/过期，不清空 Redis。

### 3.6 错误、超时、流式与观测

| 情况 | HTTP / code | 约束 |
| --- | --- | --- |
| 网关令牌不足 | 429 / RATE_LIMITED | Retry-After 至少 1 秒，按单次请求令牌恢复间隔向上取整；只是建议，不保证等待后必成功 |
| 限流 Redis 故障 | 503 / RATE_LIMIT_UNAVAILABLE | 不冒充 429，不回退为本地独立桶 |
| 服务入站满 | 503 / SERVICE_BUSY | 不排队；健康检查不进入该桶 |
| SDK 出站名额/连接池满 | 503 / DEPENDENCY_BUSY | 不立即重试、不作为远端故障 |
| Java 熔断打开 | 503 / DEPENDENCY_CIRCUIT_OPEN | 不执行下游 I/O，不返回伪造业务成功 |
| 调用超时 | 504 / UPSTREAM_TIMEOUT | 写请求结果未知，由业务按幂等/查询处理 |

继续使用现有错误 envelope、request_id、HTTP 状态；OAuth/OIDC 错误保持协议格式。普通 API SDK 总预算 10 秒、连接 2 秒、网关整体 15 秒；Nginx 连接 2 秒，普通/流式统一读写空闲 60 秒。将旧设计中普通 API 的 20 秒改为 60 秒，整体截止由 Gateway 执行，避免 Nginx 再维护一套与动态路由重复的超时分类表；T-01/T-03 同步设计与模板。网关总预算是本次需实现/验证的行为，不能把响应头超时或 Nginx 空闲超时冒充整体 deadline。

普通 SDK 当前是缓冲响应 API，不能拿它转发 SSE。本次不新增流式客户端 API：网关流式转发沿用明确流式路由 metadata `platform.streaming: true`，不套普通 15 秒整体截止时间，按现有设计的空闲边界处理；普通/流式路由不得有歧义。入站许可在流结束/断连处理结束后释放，流已开始只能关闭/按业务协议报错，不能重发或改写为 JSON 503。流式业务心跳与重连语义仍由业务实现。

指标使用现有 Actuator/SDK 观测接入，增加拒绝次数、活动名额、连接池等待/超时、熔断状态/失败次数、Redis 限流故障；标签只用 service、route、dependency、reason 等有界名称，不带 tenant_id/user_id。复用 Sentinel 资源统计、状态变更观察接口与现有观测设施，记录规则有效摘要；不自建平行状态表，不默认暴露 Sentinel transport 管理端口。不开新指标控制台或公网管理端点。

### 4.1 创建与开发

独立项目结构不变：

```text
my-project/
├── services/
│   ├── sample-java-service/     # 项目自己的 Java 业务
│   └── sample-python-service/   # 项目自己的 Python 业务
├── web/                        # 项目业务前端
├── config/nacos/               # 路由和各服务运行参数源
├── config/environments/        # 环境绑定；秘密仍在受控文件
├── infra/                      # 依赖安装/资源准备
└── deploy/                     # 已发行镜像的部署材料
```

1. 获取同版框架发行物，按现有接入指南复制混合 examples 和工具，安装基础设施并初始化身份/业务数据库。此次保护能力不增加容器或迁移表。
2. 使用发行物中的新 Gateway 镜像、foundation 制品与 python-sdk wheel；项目不用复制/修改框架 Gateway 源码。
3. 在 `api-gateway.yaml` 按 3.2 配置 Java/Python 原生路由与限流；audience 仍需按既有管理流程登记。项目无需编写 Redis Lua、限流过滤器或逐控制器注解。
4. Java 服务按 3.5 启用 Sentinel，并配置原生 flow/degrade 规则文件；使用现有 ServiceHttpClient 自动获得已配置依赖保护，不在 controller/service 每层重复装饰。
5. Python 服务在既有 `PlatformRuntime`/应用安装入口启用入站保护，并使用 SDK 管理的业务 HTTP 客户端。项目只设置 concurrency 与 http 字段；现有示例会调整为生命周期只创建一次客户端和 limiter，不每个请求实例化。
6. 新增领域逻辑仍由项目写。请求是否幂等、超时后怎样核对写入、资源不足时是否交给消息队列、外部模型是否降级，框架不会替项目决定。
7. 首次先发布 YAML 与两个 Sentinel 规则文件，再启动服务；后续仅调整 Sentinel 规则无需重启，核对各实例的有效规则摘要。路由、连接池和 Python 并发变更仍重启对应服务。通过示例验收命令主动制造超额/故障，确认保护实际生效；不能以“应用启动成功”代替验证。

初始化示例默认配置入站 64、出站 32、路由令牌 20/40，Java 对示例依赖启用熔断；这些是演示值。已有业务升级后，未启用 Sentinel 或未声明 Python 保护的服务保持原行为；Java 开关启用但规则缺失必须启动失败，避免无声改变线上并发能力；指南明确列出启用项，不能宣称升级 jar 就自动保护所有调用。

### 4.2 已有项目迁移和回退

Gateway 配置采用一次性显式迁移：旧 `id/path/service/audience` 分别转成原生 `id/Path/uri=lb://service/metadata.platform.audience`，再添加限流配置。发行说明提供前后完整示例、校验命令和 BFF 路由对应关系；不长期保留双格式解析器。

旧 Gateway 不理解新格式，新 Gateway 不接受旧格式，因此不能在同一 Data ID 下直接混跑两版。当前部署模式按维护窗口：保存旧镜像 digest、配置快照（包括 Sentinel 两类规则）和部署记录 → 暂停入口 → 发布新配置并部署同版网关/SDK 服务 → readiness 与公开入口烟测 → 恢复入口。失败则恢复旧配置和旧镜像后重启；不得只回滚镜像留下新配置。不修改业务数据库，不删除 Redis 会话或桶。

Gateway/BFF 重构应保持既有会话序列化和 Cookie 合同；若组件验证发现无法兼容，必须在实施前报告影响并重新确认，不能默默让所有用户退出。后续制品拟使用 `1.0.0-rc.3` / Python `1.0.0rc3`，不得覆盖 rc.2 同名制品。

## 7. 风险、恢复与交接自检

| 风险 | 处理与停止条件 |
| --- | --- |
| 重整网关造成鉴权与选路不一致 | 使用同一原生选路结果；未认证不允许任何 upstream I/O；安全回归失败则不发行 |
| 原生 RedisRateLimiter 异常默认放行 | 固定版本合同测试覆盖 remaining=-1/异常结果；不依赖外层异常捕获的假设 |
| 配置兼容被误判为可滚动混用 | 本次原生路由为显式格式升级；同版配置+制品维护窗口切换及回退 |
| SDK 算子排序使取消/池超时算作远端失败 | 单独异常分类、许可生命周期与实例失效断言；不只断言 HTTP 状态 |
| 多副本/多 worker 或统计型并发导致容量误算 | Java Sentinel 是每进程并发流控，不承诺严格信号量；Python 许可也按进程计数；严格业务资源名额另立需求 |
| 动态规则短暂不一致或改变熔断状态 | 两 Data ID/多实例不承诺原子切换；校验有效摘要，异常保留旧规则，状态按官方规则更新语义处理 |
| 一些依赖只有几次失败，误称“熔断没用” | 记录实际窗口/最小样本；可配置而不盲目降低生产阈值 |
| BFF 会话兼容或组件版本冲突 | 记录预期/实际/影响/建议，暂停相关任务并重新确认，不扩大认证改造范围 |
| Python 熔断能力被夸大 | 不默认提供；验收/发行说明明确只有 Java 指定依赖熔断，Python 具备并发与超时保护 |

文档交接自检要求：每个 AC 有任务与证据；已有/拟新增入口区分；原生配置示例和 SDK 字段可实际加载；未保持两套路由源；错误/重试/取消/恢复边界明确；无业务 Agent/发布控制台/全局调度混入；历史验收不覆盖新能力；所有引用在重命名后仍可达。
