## 1. 目标、范围与验收

### 1.1 本次交付

交付一个固定引用框架源码的项目创建入口，以及可运行的 Java/Python 混合项目。业务项目维护自己的源码、配置、依赖锁和部署声明；框架公共库、基础服务、工具实现通过同一个 Git 提交引用升级。开发使用源码，发布交付独立镜像。

保留 identity-service、api-gateway、java-sdk、python-sdk 四个职责模块；保留 PostgreSQL、Redis、Nacos、Spring OAuth2/OIDC、BFF、租户独立账号、权限与 RLS、Sentinel/现有 Python 容量保护。MQ 仍按需启用。不开辟另一套认证、配置中心或发布平台，不接入聊天/算法业务，不迁入 vlpykernel 的业务代码。

本次替换的是“发行包展开 + 手工安装 JAR/wheel + 复制运维工具 + 手工改名”的默认接入路径。Git 版本引用、Maven reactor、uv 本地路径依赖、Docker 多阶段构建承担主要工作；新增入口只做项目装配和已有命令编排，不开发插件平台、通用模板语言、自动升级合并器或制品服务器。

### 1.2 已确认的目录收敛（2026-10-27）

用户已确认同步调整框架内部、生成项目及文档。仓库根即框架根：java-sdk、python-sdk、services/identity-service、services/api-gateway、template、tools、tests、docs。去掉旧 framework 外层；foundation 目录与 Maven artifactId 改为 java-sdk；Java 包名仍保留 com.ken.platform.foundation，避免把文件整理变成公共类型重命名。template 只保存新项目需要的骨架和声明；tools 维护创建/开发/构建及运维实现；集成测试和验收夹具集中到 tests，模块单元测试保留在模块中。原 examples 不整包改名：按职责迁移。

统一入口 manage.py；生成项目的 manage.py 是薄入口，工具来自 vendor/micro-service。Java parent 指向 vendor 根 pom.xml，Python SDK 指向 vendor 根 python-sdk。发布包携带 tools 和项目声明，Ansible 位于 tools/deploy/ansible。更新所有活跃设计、指南、规范和生成 README 的路径及命令；冻结计划只修复移动文件链接，不重写历史命令和证据。缓存与旧本地运行材料保留在 .local，不把它们当成新目录的有效产物。

本次先验证目录、创建/新增服务、定向 Java/Python 构建和部署载荷结构；Docker 运行验收继续暂停，不调用初始化或部署命令。T-01/02/03/05/08 的实现入口均随下文新路径更新，不新增运行服务或业务能力。

### 3.1 两种仓库，各自只有一个责任

框架仓库根按职责分为 java-sdk、python-sdk、services、template、tools、tests、docs；根 manage.py 是统一入口。完整目录以[权威设计](../design/01-总体架构与工程结构设计.md#framework-layout)为准，不保留 framework 外层或 project 工具目录。

```text
equipment-platform/                   # 拟生成的项目独立 Git 仓库
├── vendor/micro-service/              # Git submodule：完整框架仓库，固定提交
├── services/
│   ├── equipment-service/             # Java 业务，独立 POM/迁移/测试
│   └── inspection-service/           # Python 业务，独立 pyproject/uv.lock/.venv
├── web/                              # 业务演示，随后归项目；管理页仍归身份服务
├── config/                           # 环境样例、Nacos 文件、development.yaml
├── infra/                            # 本项目资源与组件声明，不复制工具源码
├── deploy/                           # 本项目 Compose、主机与发行声明
├── docs/                             # 项目指南、项目补充规范；链接固定框架规范
├── .vscode/                          # 初始化/启动任务、Java/Python 调试配置
├── .gitmodules                       # 框架远程地址；版本由 Git 的 gitlink 固定
├── pom.xml                           # Java reactor 聚合入口
├── manage.py                        # 薄入口，只定位项目根并转交固定框架工具
└── .local/、dist/                     # 被忽略：秘密/环境/构建缓存、部署包
```

选择 `vendor/micro-service/` 是为保留现有框架源码布局：SDK 实际路径为 `vendor/micro-service/python-sdk`。不使用含糊的 `framework/framework`，不新建一个仅用于分发源码的仓库。

业务服务默认跟随项目根同一个 Git 仓库；不复制 vlpykernel 的“每个服务都必须独立 Git”规则。`vendor` 不忽略：项目提交 `.gitmodules` 和 gitlink，不提交框架文件副本。submodule 不跟踪浮动分支；禁止以 `update --remote` 作为日常初始化。新机器用 `git clone --recurse-submodules`；已克隆目录用 `git submodule update --init --recursive` 恢复缺失引用。

框架源码可阅读和调试；修复在框架仓库提交，经审查后由项目升级引用。正常业务开发不修改 vendor。正式构建要求项目和框架均无未提交/未跟踪的有效构建输入，且引用能从记录的远程获取；开发调试允许明确标识的源码修改，但不能伪装成某个已发布提交。

### 3.2 项目创建入口与命名

根 `manage.py create` 调用 `tools/create.py`，入口本身只使用标准库，通过 Git 获取源码、通过 uv 生成新服务锁文件，因此创建前需要 Python 3.12、Git、uv 和 JDK 21（生成 Java 后用项目同版 Spotless 规范格式）。输入固定远程地址/提交、目标目录、项目代码、Java group/package、两个服务名及 Python 包名；默认交付一个 Java 和一个 Python 服务。生成材料必须来自解析后的目标提交，不能从另一个版本或带未提交修改的工作树复制；目标项目引用的是可从记录远程获取的完整提交。

下面是拟交付命令，不是当前可执行入口；`<已发布标签或提交>` 在实际使用时必须替换为完成本计划后的版本：

```powershell
# cwd：已检出固定版本的 micro-service 框架仓库
python manage.py create --output ../equipment-platform --ref <已发布标签或提交> --project equipment-platform --java-service equipment-service --java-package com.acme.equipment --python-service inspection-service --python-package inspection
cd ../equipment-platform
python manage.py init --local
# 两个终端分别运行
python manage.py dev equipment-service
python manage.py dev inspection-service
```

创建仅生成项目和源码引用，不启动容器、不生成运行秘密、不创建远程仓库、不自动提交/push。目标非空拒绝；先在同级临时目录完成本次生成和结构检查，再落到目标。失败保留明确命名的本次临时目录和错误，不删除用户目录，不自动覆盖。

服务名沿用小写连字符的职责命名；Java 包和 Python import 包通过显式参数确定并验证，不能用全仓文本替换猜名字。只对已登记的示例文件/字段做精确转换：源码与测试导入、POM/pyproject、启动入口、permissions、resources、Nacos Data ID/路由/Sentinel 资源、Compose、对端调用配置。相同服务名贯穿注册发现、audience 与部署声明；新服务权限资源固定生成为 `<服务名>-item`，权限为 `<服务名>-item:read/create`，OAuth scope 为 `<服务名>.items.read/write`，路由为 `/api/v1/<服务名>/items`。控制器、数据范围、清单、测试及 Web 同步生成，避免同语言第二个服务冲突。初始两服务配置彼此为对端；后来新增服务默认不配置对端。已有项目转换不改既有权限和路由。完成后扫描登记字段，不允许遗留 sample 的服务身份；示例说明中的普通文字不按关键字误删。

`config/development.yaml` 继续作为本地服务目录与入口清单，不新增 project.json/service.json；POM/pyproject 是构建依赖权威，resources/permissions/Nacos 文件各自保持现有职责。创建器一次性填好这些不同用途的文件，不把它们合并成一个万能 DSL，也不持续自动重写用户配置。

### 3.3 Java 如何开发与构建

项目根 POM 仅聚合 `vendor/micro-service` 和本项目 Java 服务。框架自身 POM 继续聚合三个核心模块；项目不能再重复聚合 java-sdk，避免 reactor 重复模块。

业务 POM 继承固定框架父版本，`relativePath` 指向 `../../vendor/micro-service/pom.xml`，java-sdk 使用父 POM 的依赖管理。例：在项目根通过 Maven wrapper 执行 `-pl :equipment-service -am package`，只构建该服务及必要父/基础库，不要求本地已有 java-sdk JAR。wrapper 使用 vendor 内同版本入口，不为每个项目维护第二份 wrapper。

IDE 导入项目根 POM，直接调试业务启动类并附带生成的运行绑定；使用 `manage.py dev` 时复用已有 dev.py 校验环境和凭据，再构建必要依赖并启动。Ctrl+C 只结束本次进程；不按端口号杀死其他项目进程。Java 与 Python 通信仍走 SDK/HTTP，不能依赖对方源码包。

### 3.4 Python 如何接入：源码共享，环境独立

采用 **uv 本地路径依赖**，不把所有服务放进同一 uv workspace。原因：算法服务第三方依赖较重，项目内各服务仍需独立锁定和发布；不复制 vlpykernel 的全局 uv.lock 耦合。

每个 Python 服务保留 `pyproject.toml`、`uv.lock` 和自己的 `.venv`；开发时 SDK 指向 `../../vendor/micro-service/python-sdk`，`editable = true`。SDK 版本约束与所引用源码的 metadata 必须一致。创建/添加服务时按当前固定源码解析并生成锁文件；后续安装执行 `uv sync --frozen`，不能每次启动隐式重锁。`uv lock` 失败时项目创建不宣称完成；保留未完成目录供排错。

框架工具环境与业务环境分开：工具使用固定源码里的 pyproject.toml 和 uv.lock，虚拟环境落到项目 `.local/tools-venv`，不修改 vendor 的锁文件。版本引用更新后重新同步工具环境。生成的 Python 调试配置选择对应服务解释器；Java 不进入 uv 成员列表。

增加第三方 Python 依赖只修改该服务的 pyproject/lock，其他项目和兄弟服务的锁文件不变化。生产构建通过锁文件安装依赖并将 SDK/业务转为非 editable 安装；不把开发期的源码挂载带到生产。

### 3.5 本地初始化：一个入口，明确顺序

开发机前提：Git、Python 3.12、uv、Docker Engine/Compose；调试 Java 需要 JDK 21。基础镜像和第三方依赖首次需要可访问仓库，不宣称完全离线。身份管理前端在 Docker 构建阶段完成，不要求宿主机先安装 Node/pnpm。

默认基础设施和 identity/gateway/Nginx 跑容器，业务跑宿主。全容器联调仍可通过生成的 Compose 进行，但不是 IDE 开发的前置步骤。

`manage.py init --local` 必须按以下顺序编排已有能力，逐步输出阶段名、结果和下一步，不打印秘密：

1. 检查源码引用、工具版本、端口和项目配置；准备项目独立工具环境，冻结安装业务依赖；端口冲突停止，不自动随机改所有地址。
2. 从环境样例生成 `.local/environment.env` 和每服务秘密；已有文件仅核对，保持原值。默认自建本地 PG/Redis/Nacos；外部环境仍使用现有显式绑定流程，不由本地便捷入口猜测。
3. 启动项目拥有的组件，等待 readiness；调用现有 infra 初始化器创建身份和业务资源；先身份迁移，再各业务迁移。
4. 从固定源码构建身份与网关镜像，执行既有身份 bootstrap，保留初始管理员强制改密规则。
5. 执行下面定义的开发身份初始化，登记本项目服务 audience、独立内省客户端、Gateway reader 和业务 BFF；先启动身份服务，用已有专用发布客户端经正式权限发布 API 写入开发清单，创建开发演示租户/用户/角色；写入各服务受限运行绑定。身份数据安装是本地维护动作；权限发布等待身份 ready 后调用已有 HTTP API，不绕过其目录校验。
6. 发布 Nacos 文件与 Sentinel 规则，再启动基础服务及入口；检查从宿主和容器均能访问身份服务。输出登录地址、秘密文件位置、两个业务启动命令；业务未启动不伪报双向调用成功。

宿主/容器寻址复用现有 compose.host.yaml 思路：选定一个双方可解析的 DEV_HOST、公开端口及服务端口；生成 host-gateway 映射和 Nacos 的宿主可达注册地址。在 Docker Desktop 和 Linux 上分别核对；不能只修改当前业务的注册地址而漏掉身份服务。Nginx 对 Gateway 重建后的校验/reload 由入口负责，不让使用者记住隐含步骤。

**开发身份初始化的边界：**增加 maintenance 的 `bootstrap-local`，只执行固定的首次演示数据安装，不开发任意导入/差异同步接口。CLI 必须显式提供 PROJECT_CODE、APP_ENV=local、DB_NAME、local 自建模式、首次清单及秘密文件；工具先检查当前 Compose 项目的 PG 容器及卷归属，CLI 再锁定并核对 sys_identity_bootstrap_state 的 project_code/app_env/public_origin 和当前数据库名。external/test/prod 拒绝。此限制是防误用边界，持有数据库凭据的运维本来就有数据库权限，不能宣传成防恶意管理员的安全隔离。

不调用需要 Web principal/recent-auth 的管理方法，不伪造 SecurityContext。维护服务复用 ClientPolicyRules、密码策略和 ClientManagementService.initialize（保持协议表/策略表成对写入）；权限目录由身份 ready 后的既有发布 API 校验并发布，再执行首次身份事务。首次事务写入两个开发租户、每租户一个普通演示用户及一个无权限用户、最小示例角色，以及每服务独立资源/Gateway 内省客户端和业务 BFF。管理员继续强制改密；演示用户的首次密码也必须修改。不存在设备/算法业务记录。

用独立的本地初始化记录保存项目身份及规范化清单摘要，和上述对象在同一身份事务提交。记录存在且摘要相同：仅校验初始化归属后返回 VERIFIED，绝不重写已被管理员改过的用户、角色和客户端。记录不存在但目标自然键已有对象：报冲突并回滚，不收养未知对象。摘要不同：停止并提示后续修改走管理页；不“增量同步”BFF 或角色。权限/客户端初始定义、秘密引用路径固定纳入摘要，秘密本身只在本地文件中，不进日志；已完成记录存在但秘密丢失时停止，走显式轮换。两个同时初始化进程通过数据库事务锁串行，重复不重复写入。

本地秘密一次生成后不覆盖。bootstrap.json 等首次文件固定使用创建时的两服务清单，不因 add-service 改写；后续新增服务的 audience、发布客户端、内省客户端、BFF 范围和角色由管理员按生成的接入清单登记。新增服务资源/迁移可通过现有工具执行，不反复运行首次身份初始化来扩权。运行 env、Compose 绑定是派生文件：仅当磁盘内容等于上次生成的摘要才允许更新，用户改过就拒绝并显示路径；这不是跨系统 reconciliation 引擎。

跨系统不做分布式事务：资源成功而身份事务失败，保留资源，修正输入重跑；数据库记录提交成功而后续发布失败，重跑读取同一记录，不改密码。配置发布仍用现有漂移检查，迁移 UNKNOWN 仍需人工核查，不自动确认。

### 3.6 日常开发与新增服务

项目团队主要修改 services/、web/、config/ 和业务资源/权限/迁移。SDK、用户管理页面、网关协议实现不用复制到业务代码。

拟新增的 `manage.py` 只暴露四个子命令：`init --local`、`dev <service>`、`add-service`、`build`。不提供远程发布控制台、后台守护进程、自动提交或自动部署；迁移、权限发布、Ansible 等高级操作继续使用既有明确入口。

新增服务例：`python manage.py add-service --language python --name scoring-service --package scoring --port 48084`。Java 使用 `--package com.acme.report`。命令复用混合示例单个服务生成能力，提供真实持久化用例、迁移、权限和测试，不仅生成无法验收的空目录。

添加时在临时区生成，检查名称/路径/端口冲突，预览将追加的 POM 模块、development 清单、资源/Nacos/Compose 条目；已有同键冲突拒绝，不自动覆盖用户字段。用户通过明确参数执行该命令即授权这些文件生成，命令不操作运行数据库。随后按新服务生成的接入清单初始化资源、迁移、登记 audience/发布客户端/内省客户端、发布权限，并在管理页更新业务 BFF 和角色；再填写其独立运行凭据并启动。`init --local` 只负责创建时的双语演示，不承担新增服务授权同步。脚手架错误不靠清空目录修复。

编码规范沿用既有通用/Java/Python 三份规范。生成根 AGENTS/CLAUDE/Cursor 入口、编辑器配置、服务测试和精简项目指南；权威规范链接到固定 vendor 版本，项目只维护自己的补充规范，不复制框架历史计划。IDE 配置不得携带秘密值。

### 3.7 配置、基础设施和部署分别归谁

| 内容 | 开发/部署来源 | 规则 |
| --- | --- | --- |
| 服务默认值/接口模型 | 服务源码 | 可在仓库审查；不从 Nacos 下载代码 |
| 路由、业务可调项、Sentinel 规则 | 项目 config/nacos，经发布器写入 Nacos | 继续既有 schema、漂移校验和刷新语义 |
| 主机、端口、环境、数据库地址 | 项目环境绑定 | local/test/prod 分开；容器地址不能直接用于跨机 |
| 密码、签名密钥、客户端 secret | 环境秘密文件/既有秘密管理方式 | 不进 Git/Nacos/镜像/普通发行包 |
| PG/Redis/Nacos 的部署与资源 | 项目 infra 声明 + 框架初始化工具 | 本地自建；正式可自建或 external，按环境明确选择 |
| 镜像组合、主机分配、入口与迁移顺序 | 项目 deploy 声明 | 框架不硬编码设备、备课或算法等具体服务名单 |

工具实现只保留在固定框架引用中。现有 dev/migrate/publish/infra 等工具按需增加显式 `--project-root`，把“工具源码根”和“项目输入/状态根”分开；所有项目状态写项目 .local，不写 vendor。部署包阶段允许复制本次固定工具作为不可变运行载荷，不意味着业务项目需维护一份工具源码。

### 3.8 构建、交付与多机部署

`python manage.py build --output dist/<业务发行号>` 构建本项目明确登记的服务和两个基础服务；可用 `--service <name>` 做局部镜像构建，但局部结果不能冒充完整首次部署包。不自动上传镜像、不自动远程部署。

Java 镜像用 Maven reactor 多阶段构建；身份/网关复用现有 Dockerfile。Python 用项目根为构建上下文，只 COPY 当前服务、固定 SDK 和锁定构建输入；在 Linux 构建阶段冻结同步并非 editable 安装，最终阶段不带 uv 开发工具、测试、JDK 或其他业务源码。构建前独立核验锁文件有效，不能用 frozen 掩盖 metadata 与锁不匹配。根 .dockerignore 排除 .local、所有 .venv/.git、缓存及本地秘密。

部署包只包含：项目 config/infra/deploy 的运行声明、固定版本的必要执行工具及其依赖锁、身份和业务迁移、权限清单、业务 Web 静态文件、release 清单。缺少已声明的 Web 构建产物则构建失败，不悄悄发布空前端。框架源码、业务源码和 vendor Git 目录不进入服务器部署包；identity-admin 仍在身份镜像中。

复用现有 release 清单，补充项目 commit、框架完整 commit、所选服务、锁文件摘要及身份/业务迁移摘要；不再生成另一份内容重复的 framework-baseline。运行镜像与迁移必须来自同一次固定输入的构建。首次本地验证可记录 Docker image ID；远程镜像拉取使用实际 push 后的 repository@sha256。生成阶段不伪造仓库 digest。

已有 Ansible 路径约定在部署包内保持，使运维仍能执行 initialize/migrate/deploy/reconcile/rollback。正式部署前需要运维填好主机、域名/TLS、真实秘密、镜像来源、备份和恢复信息；不会承诺从项目名自动推导生产环境。

本地开发构建使用 image ID/本地 tag 和 Compose。正式单机及多机统一使用团队认可的镜像仓库、repository@sha256 和现有 Ansible 拉取校验；不新增服务器预载/离线发布模式。镜像仓库账号与上传由项目运维管理，构建命令不自动推送。Nexus/Maven/PyPI 私有仓库不属于本次必装依赖。

多机沿用现有模型：一个资源初始化/迁移执行点，应用按主机清单启动，Nacos 登记私网可达地址；Docker bridge DNS 不跨主机。身份 ready 后再更新依赖内省的服务；迁移失败不发布。保留维护窗口，不把 serial=1 或本地容器模拟称作无损滚动发布。

### 3.9 从创建到发布的完整顺序

1. 在固定框架检出目录运行 create，提供 `--ref`、`--output`、项目/服务/包名及 `--port-offset`（默认 0）。新项目目录仅生成文件和 gitlink。生成 README 的命令已填实际名称。
2. 进入项目，检查 `.gitignore` 后 `git add .`、`git commit`；团队自行创建业务远程并 push。新机器递归 clone。没有业务远程不妨碍本地开发，正式发行需记录可获取的源码引用。
3. `python manage.py init --local`：同步工具/业务环境，构建基础镜像，准备并启动组件，初始化资源，迁移，bootstrap，固定本地演示身份，发布配置，启动入口。每阶段非零即停；同样命令可重入。
4. 在两个终端 `python manage.py dev <服务名>`。前者构建必要 Maven 模块再启动，后者 frozen sync 再启动；启动后检查 ready。打开 README 中的管理页和业务首页，用秘密文件中的首次密码改密后创建/查询记录、访问对端。
5. 日常只改 services/web/config；新增服务使用 add-service 后完成其生成接入清单。授权变化明确由管理页完成，不隐式给用户增加权限。
6. `python manage.py build --release <版本> --output dist/<版本>` 做本地完整镜像构建；`--service <名称>` 仅构建单个镜像，不能生成完整正式发行。默认 Web 输入是项目 web 的静态文件；需前端编译的项目先自行构建，并传 `--web-root <产物目录>`，必须包含 index.html。
7. 正式发行先提交项目与锁文件，维护者将上一步镜像推送到获准仓库，再准备 `--images <映射JSON>`（每服务 repository@sha256）及部署环境 `--env-file`。`build --release <版本> --output <新目录> --images <映射JSON> --env-file <环境文件> --package-only` 核对固定源码、镜像和迁移，输出完整不可变部署载荷；不复制环境秘密。提供不匹配镜像必须拒绝，不把外来 tag 直接写成验收通过。
8. 运维在部署包使用现有 initialize → migrate → bootstrap（仅新身份库）→ deploy → 验收。配置主机清单、真实地址/TLS/秘密和恢复策略；正式授权在管理页建立。升级按下一节，两个真实 Linux 主机验证仍须有环境后执行。

**本地网络与端口：**全部端口成组加 `--port-offset`：PG 15432、Redis 16379、Nacos API 8848/gRPC 9848/控制台 8080、入口 18080、身份映射 18081、Java 48082、Python 48083。新建另一项目须选不冲突的 offset；所有派生地址同时改变，不能只改公开入口。容器服务之间仍用容器 DNS；宿主业务的发现地址在 Docker Desktop 使用 host.docker.internal，必须在宿主能解析且从网关容器能连通。Linux 用户显式提供 `--dev-host <宿主私网IP>`，用真实地址注册；不把 Docker bridge 名当作跨机名。宿主业务监听该接口或经用户明确选择的 0.0.0.0；不自动修改 hosts/防火墙。业务未启动时仅报告网络准备，dev 启动后从容器检查 readiness；失败列出地址/端口而不报告成功。身份服务分别提供宿主 loopback 和容器 DNS 绑定，SDK 发现中使用双方能连接的公布地址。端口冲突拒绝，不随机重选。

### 3.10 框架升级与旧项目转换

开发升级和生产发布是两次不同操作：

1. 在业务项目建立升级分支，确认项目与 vendor 的修改已妥善保存；记录旧 gitlink/镜像/配置。读取目标版本兼容与迁移说明。
2. 将 submodule 切换到明确目标提交；不跟随 main，不运行重置/清理用户修改的命令。更新业务 POM 父版本与 SDK 版本约束，重锁受影响 Python 服务；工具按目标源码锁同步。
3. 按发行说明修改必要项目配置和脚手架差异。服务业务文件不重新生成，manage.py 不做自动 merge；框架内部工具因引用变化直接升级，项目定制保留。
4. 完成受影响测试、初始化幂等核对和本地登录/调用/权限验收；将 gitlink、构建配置、必要锁文件和项目改动作为同一次项目提交。
5. 构建新镜像与部署包，再按既有备份→兼容迁移→应用更新→验收流程发布。开发目录升级不会自动触碰运行环境。

回退开发引用不会回退数据库。应用回退必须满足现有 schema/API/安全兼容及回退窗口；否则停下按恢复方案处理。升级不重新创建租户或修改角色，不重新 bootstrap，不覆盖签名密钥。

现有 rc.3 发行项目采用**人工一次性转换清单**，不做通用迁移平台：先提交/备份现有项目；加入固定框架引用、项目聚合和源码 SDK 路径；保留原服务名、包名、权限、audience、PROJECT_CODE、环境资源前缀、卷名与数据库；整理相同工具实现为固定引用；更新锁并构建。确认文件组织转换没有要求新 SQL/schema 后，再做实际应用升级。不得用“新建同名项目 + init --local”替代存量迁移。

旧已发布候选及其历史验收保留。新版本的默认文档只讲源码工作区；旧 package_runtime 文件删除，部署载荷只由 tools/build.py 维护。旧项目继续使用原发行，不在没有授权时远程替换任何项目。

## 4. 影响范围与保持项

| 范围 | 修改 | 必须保持 |
