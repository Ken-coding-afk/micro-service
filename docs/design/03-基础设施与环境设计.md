## 1. 依赖清单与启用条件

infra/compose.yaml 只定义第三方组件。deploy/compose.yaml 定义 identity、gateway、业务 API/Worker、Nginx。二者是独立 Compose 项目；本地通过明确创建的同机 external network 互通，默认项目名为 PROJECT_CODE-APP_ENV-infra、网络为 PROJECT_CODE-APP_ENV-net，卷名随项目/环境隔离。已有环境可显式绑定 INFRA_PROJECT_NAME/INFRA_NETWORK 保留已核实的卷与网络；不能因框架升级改名而静默挂空卷。连接别名固定，不能假设两个 Compose 项目默认网络相通。

| 组件 | 本地默认 | 测试/生产默认 | 初始化结果和持久化责任 |
| --- | --- | --- | --- |
| PostgreSQL 17 | 一个容器，开发命名卷 | 独立数据目录/卷，固定补丁，备份与 WAL 归档 | 每服务库、owner/migrator/runtime 角色；按数据库实例恢复 |
| Redis | 一个容器，独立开发凭证 | 独立实例，AOF everysec，默认 noeviction，设置内存上限和告警 | 登录/BFF 与缓存使用不同 key 前缀和受限账号；满内存写失败按依赖故障处理 |
| Nacos | 单节点、内置 Derby、持久卷 | 当前基础拓扑同为单节点持久化并启用鉴权；独立维护 | namespace、服务/配置凭证、配置摘要；不使用业务 PG 冒充原生 Nacos 存储 |

纯同步 HTTP 示例不启动 RabbitMQ 或 Worker；只有项目明确选择 mq 适配才创建 vhost/消息账号并安装 RabbitMQ。框架不预建 Agent 数据库或运行时表。

每项目/环境默认独立组件实例；同一项目的多个服务可共用 PG 实例，但不能共用数据库账号/任意跨库查询。若采用已有外部组件，则跳过相应容器安装，保留能力检查和本项目资源初始化；不同时启动一个闲置容器假装它是实际依赖。测试与生产不共用数据、消息 vhost 或凭据。

当前基础拓扑有单点，不宣称 HA；高可用涉及具体 PG/Redis/Rabbit/Nacos/入口拓扑、预算和故障验收，不是把 app 副本数改为 2。Nacos 内置 Derby 与外部 MySQL 部署方式以官方为准，不能因业务统一 PG 就添加未验证的存储插件。[Nacos 单机部署](https://nacos.io/en/docs/v3.0/manual/admin/deployment/deployment-standalone/)

## 2. 本地、测试与生产环境

| 项 | local | test | prod |
| --- | --- | --- | --- |
| 用途 | 首次运行、个人调试 | 集成、升级和故障验收 | 正式业务 |
| 数据与凭证 | 独立随机开发凭证、假数据 | 独立库/卷/namespace/vhost、脱敏数据 | 独立数据与秘密，禁止复制开发账号 |
| 应用运行 | 基础组件/身份/网关容器，业务默认宿主进程 | 全部固定镜像 | 测试通过的同一镜像 digest |
| 基础设施 | 本机 Docker，按组合启用 | 独立服务器组件或明确外部实例 | 按环境清单安装/接入，独立维护 |
| 登录入口 | 显式 local loopback；内部/外部地址分开 | 实际 HTTPS 域名与真实代理 | 固定 HTTPS、内部信任与证书续期 |
| 数据保护 | 显式 local reset；普通启动不删卷 | 验证迁移与恢复样本 | 备份/WAL/恢复演练、受控发布 |
| 管理执行机 | Windows/Python/Docker 或 Linux | Linux/WSL Ansible 管理机 | 唯一授权的 Linux/WSL 管理入口 |

Ansible 不假设能原生运行在 Windows PowerShell；本地日常启动不要求 Ansible，服务器发布从 Linux/WSL 管理机执行。三种环境使用相同代码合同，差异通过环境配置与组件运行规格表达，不维护三份分叉业务代码。基础设施、地址与凭证不因应用镜像跨环境复用而共享。

## 3. 本地运行、IDE 与前端调试绑定

开发机前提：Git、Python 3.12、uv、JDK 21、Docker Engine/Compose；创建器调用项目格式器生成符合规范的 Java 源码，因此创建时也需要 JDK。基础镜像和第三方依赖首次需要可访问仓库，不宣称完全离线。身份管理前端在 Docker 构建阶段完成，不要求宿主机先安装 Node/pnpm。

默认基础设施和 identity/gateway/Nginx 跑容器，业务跑宿主。全容器联调仍可通过生成的 Compose 进行，但不是 IDE 开发的前置步骤。

本地初始化执行 `uv run --frozen python scripts/init.py --env local --services all`；可选演示显式追加 --with-demo。阶段顺序唯一见[脚手架初始化](11-源码脚手架交付与开发体验设计.md#initialization)：先准备开发/迁移镜像并发布基础配置，身份 ready 后再分阶段登记客户端、发布目录。仅准备基础环境成功不等于业务已运行。

项目的 Redis 模板由项目维护。`scripts/init.py --env local --services all` 给资源工具传入 `--redis-template <项目根>/infra/redis/redis.conf`；首次初始化使用此文件生成运行副本，显式模板缺失时停止，不回退到框架模板。重复初始化不覆盖已有运行配置、不旋转秘密；后续修改运行配置需显式审核和更新。独立调用资源工具未传该参数时，仍保留框架或部署包的默认输入行为。

**开发身份初始化的边界：**增加 maintenance 的 `bootstrap-local`，只执行固定的首次演示数据安装，不开发任意导入/差异同步接口。CLI 必须显式提供 PROJECT_CODE、APP_ENV=local、DB_NAME、local 自建模式、首次清单及秘密文件；工具先检查当前 Compose 项目的 PG 容器及卷归属，CLI 再锁定并核对 sys_identity_bootstrap_state 的 project_code/app_env/public_origin 和当前数据库名。external/test/prod 拒绝。此限制是防误用边界，持有数据库凭据的运维本来就有数据库权限，不能宣传成防恶意管理员的安全隔离。

不调用需要 Web principal/recent-auth 的管理方法，不伪造 SecurityContext。维护服务复用 ClientPolicyRules、密码策略和 ClientManagementService.initialize（保持协议表/策略表成对写入）；权限目录由身份 ready 后的既有发布 API 校验并发布，再执行首次身份事务。首次事务写入两个开发租户、每租户一个普通演示用户及一个无权限用户、最小示例角色，以及每服务独立资源/Gateway 内省客户端和业务 BFF。管理员继续强制改密；演示用户的首次密码也必须修改。不存在设备/算法业务记录。

用独立的本地初始化记录保存项目身份及规范化清单摘要，和上述对象在同一身份事务提交。记录存在且摘要相同：仅校验初始化归属后返回 VERIFIED，绝不重写已被管理员改过的用户、角色和客户端。记录不存在但目标自然键已有对象：报冲突并回滚，不收养未知对象。摘要不同：停止并提示后续修改走管理页；不“增量同步”BFF 或角色。权限/客户端初始定义、秘密引用路径固定纳入摘要，秘密本身只在本地文件中，不进日志；已完成记录存在但秘密丢失时停止，走显式轮换。两个同时初始化进程通过数据库事务锁串行，重复不重复写入。

本地秘密一次生成后不覆盖。bootstrap.json 等首次文件固定使用创建时的两服务清单，不因 add-service 改写；后续新增服务的 audience、发布客户端、内省客户端、BFF 范围和角色由管理员按生成的接入清单登记。新增服务资源/迁移可通过现有工具执行，不反复运行首次身份初始化来扩权。运行 env、Compose 绑定是派生文件：仅当磁盘内容等于上次生成的摘要才允许更新，用户改过就拒绝并显示路径；这不是跨系统 reconciliation 引擎。

跨系统不做分布式事务：资源成功而身份事务失败，保留资源，修正输入重跑；数据库记录提交成功而后续发布失败，重跑读取同一记录，不改密码。配置发布仍用现有漂移检查，迁移 UNKNOWN 仍需人工核查，不自动确认。

**本地网络与端口：**全部端口成组加 `--port-offset`：PG 15432、Redis 16379、Nacos API 8848/gRPC 9848/控制台 8080、入口 18080、身份映射 18081、Java 48082、Python 48083。新建另一项目须选不冲突的 offset；所有派生地址同时改变，不能只改公开入口。容器服务之间仍用容器 DNS；宿主业务的发现地址在 Docker Desktop 使用 host.docker.internal，必须在宿主能解析且从网关容器能连通。Linux 用户显式提供 `--dev-host <宿主私网IP>`，用真实地址注册；不把 Docker bridge 名当作跨机名。宿主业务监听该接口或经用户明确选择的 0.0.0.0；不自动修改 hosts/防火墙。业务未启动时仅报告网络准备，dev 启动后从容器检查 readiness；失败列出地址/端口而不报告成功。身份服务在 local 显式发布开发端口到宿主网卡供容器访问，SDK 发现使用已验证的公布地址；开发者应通过防火墙限制来源，此绑定不用于 test/prod。端口冲突拒绝，不随机重选。

本节定义 local 的网络和调试绑定；认证例外的安全限制以[认证环境规则](05-认证与OAuth2设计.md#origins)为准。

本地全容器模式中，infra 与 deploy 接入同一个明确创建的 external network，PG/Nacos/identity 使用各自网络别名。浏览器只访问固定 loopback 入口，例如 http://localhost:18080。local profile 显式允许该 loopback HTTP 的开发 Cookie；测试/生产必须 HTTPS + Secure Cookie，不能复用本地 profile 到服务器。

PUBLIC_ORIGIN 是浏览器 issuer/跳转来源；IDENTITY_INTERNAL_ORIGIN 是 Gateway/资源服务的内部连接入口。本地容器不能把 localhost 当成另一容器。BFF 的服务端 token/UserInfo/JWKS 连接明确使用内部地址，浏览器授权跳转和回调使用 PUBLIC_ORIGIN；签名/内省仍校验固定外部 issuer，不能通过改 issuer 来迁就网络。受信任的本地 HTTPS 可覆盖开发 HTTP 入口，外部厂商需要公网回调时使用测试环境域名。

| 调用方向 | 本地全容器 | IDE 调试 | 服务器 |
| --- | --- | --- | --- |
| 服务 → PG/Redis/Nacos | external network 别名与容器端口 | host 配置中的 127.0.0.1 与映射端口 | 私网 DNS/IP 与固定端口 |
| Gateway → 业务 API | Nacos 中可达容器地址/同网端点 | Nacos 中 DEV_HOST 与业务监听端口 | 私网发布地址 |
| 浏览器 → 入口 | localhost:18080 | 同一入口，业务本地入口代理业务页面到 Vite | 固定 HTTPS 域名 |
| 资源服务 → 身份内省 | 身份内部入口 | host 绑定的身份入口 | 固定内部 TLS 入口，避免递归经过 Gateway |

日常调试停掉对应业务容器，等待其注册摘除，再通过 scripts/deploy/dev.ps1（Windows）或 dev.sh（Linux）加载 local.env + 允许的 local-host 覆盖。辅助入口导出环境变量并执行固定 Maven/uv 启动方式，不让用户把 secret 贴进 IDE 参数。DEV_HOST 是从容器和宿主机都验证可达的本机地址；监听地址与注册地址分开，不能注册 127.0.0.1 供其他容器访问。防火墙只允许必需的 Docker/开发来源。

普通 HTTP 调试只替换选中的 API；多个实例端口/instance_id 不重复。后台消费进程由业务项目自行配置，不注册成 HTTP 实例。

业务 Web 热更新时，本地 Nginx 只把业务页面和明确的 HMR 路径转发到 DEV_HOST 上的 Vite，API/BFF/身份路径仍交 Gateway；浏览器始终访问 PUBLIC_ORIGIN，不切到另一个端口重新构造回调。Vite 仅向必需开发来源开放，HMR 代理只在 local 启用。前端不复制认证逻辑，注册回调与固定入口完全一致。本地首次验收必须包括容器调用 IDE、IDE 调用容器、BFF 登录/刷新/退出，而不是只运行一个 curl localhost。每位开发者默认自己一套 local 依赖，不连生产库调试。

## 4. 自建组件与外部实例接入

环境通过 PG_MODE/REDIS_MODE/NACOS_MODE/RABBIT_MODE 显式声明 self_hosted 或 external；scripts/infra/up.py 仅启动所选自建组件，所有 Compose 服务均置于显式 profile，普通 up 不得隐式安装 external 组件。组件模式不由“能否连接某端口”推断。infra/resources.yaml 保存本项目资源声明；各环境的 self_hosted/external 选择、实际 endpoint 和秘密引用统一来自 config/environments。资源声明只引用这些绑定，不重复保存第二份环境值。

| 模式 | 操作 | 验证 | 不允许的隐式行为 |
| --- | --- | --- | --- |
| self_hosted | 在指定 infra 主机启动锁定镜像和持久卷 | 版本/卷/网络/健康、管理员与运行身份边界 | 应用 deploy 顺带替换镜像 |
| external | 使用已提供服务，跳过对应 Compose 服务 | 协议/TLS/账号权限/本项目资源、备份责任方 | 外部不可用时偷偷改连本地临时实例 |

外部数据库可能不允许应用方建库。此时由组件所有者预创建清单中的库与角色，初始化入口执行只读/最小权限核对并记录“外部提供”；不要求把共享集群管理员密码交给项目。PG/Rabbit/Nacos/Redis 可分别采用不同模式，交付清单必须能准确显示实际使用者。

## 5. 组件运行配置与持久化

| 组件 | 固定运行材料 | 本地与服务器的差异 | 必须验证 |
| --- | --- | --- | --- |
| PG | 锁定镜像、postgres 参数、数据/WAL/备份路径、健康检查 | local 命名卷；服务器明确卷/UID、备份目的地和容量 | 运行账号无 DDL/BYPASSRLS；可恢复 |
| Redis | 内存上限、AOF、noeviction、ACL、数据目录 | local 随项目；服务器独立凭据与告警 | 会话写入失败不放行，key 前缀/ACL有效 |
| Nacos | 服务端配置、鉴权密钥、持久卷、端口清单 | local 每人独立；服务器环境独立 | 配置源与服务端配置分开；注册/读取/发布权限符合冻结版本 |
| Rabbit | 数据卷、vhost/账号、服务声明的拓扑、内存/磁盘阈值 | local 按组合启用；服务器有积压和磁盘告警 | 发布确认、持久化及消费者权限 |
| S3 | endpoint/bucket/访问身份与策略 | local 可用测试实例；prod 独立数据/凭据 | 对象归属、大小和下载授权；备份责任明确 |

镜像使用 digest；组件进程支持的环境变量、挂载路径和实际端口由兼容冻结任务按所选版本核实，不凭经验硬编码。主机 NTP、可用磁盘、文件权限、日志轮转、CPU/内存与连接上限是安装前检查项。

## 6. 数据库、账号及命名空间初始化

| 阶段 | 执行入口归属 | 使用身份 | 必须产生的结果 |
| --- | --- | --- | --- |
| 安装/启动组件 | infra/compose.yaml，受 Ansible infra.yaml 调用 | 主机维护身份 | 进程健康、卷可写、版本/网络正确 |
| 创建环境资源 | scripts/infra/init.py 及声明清单 | 限时使用 PG/Nacos/Rabbit 管理凭证 | 服务数据库/角色、namespace、vhost/账号；不创建业务表 |
| 发布应用配置 | scripts/config/publish.py | Nacos 配置发布身份 | 对应环境的参数可读及摘要记录 |
| 迁移 schema | 独立 Flyway/Alembic 工具入口 | 该服务迁移账号 | Flyway/Alembic/RLS/约束达到目标版本 |
| 初始化身份应用 | identity 镜像 bootstrap 入口 | 本服务受控初始化身份 | 初始平台账号、固定管理客户端和内置权限 |
| 启动身份服务 | deploy 中固定镜像 | identity runtime 账号 | readiness、内省/授权和管理 API 可用 |
| 发布业务权限 | 服务 permissions.yaml，经 sync_permissions.py 调用身份 API | 受限权限目录发布凭证 | 目录建立，新权限不自动授予 |
| 登记业务客户端/资源服务 | 管理页面或同等受保护管理 API | 有权管理应用的管理员 | BFF、机器、资源内省客户端及允许范围就绪；禁止将权限目录发布凭证用于任意客户端扩权 |
| 启动业务应用 | deploy 或本地 IDE | 对应 runtime 账号 | 可注册、可鉴权；项目用户按角色访问 |

PG 的库/角色默认使用 project_code_environment 前缀，外部共享实例也不能让 test/prod 解析到同名资源。既有已核实的同项目 local 环境可显式设置 PG_RESOURCE_PREFIX 保留原名称；非 local 拒绝该例外，复制新项目不得继承。PG 初始化为每服务创建 NOLOGIN owner、独立 migrator 和 runtime；迁移具备该服务 DDL 能力，runtime 无 DDL/超级用户/BYPASSRLS。owner/表默认权限在迁移中检查，不能让新增表丢失 runtime 授权或 RLS。PG 管理凭证不挂进常驻应用。

初始化按明确资源名幂等执行：不存在才创建，存在则核对归属和权限；重复执行不改密码、不清库、不吞掉不一致。凭证变更走独立轮换；未知资源或归属冲突停止。不能只依赖空数据卷首次启动时运行的 SQL，因为后续新增服务还需要增量建库和账号。业务迁移另有数据库锁，不能用“初始化已完成”跳过迁移历史。

<a id="initialization"></a>

## 7. 幂等、增量与部分失败恢复

资源声明通过绑定取得 project_code、environment，包含逻辑服务所有者和资源名称。声明 schema 固定包含 resource_id、component、owner_service、name_binding、management（create/verify）、账号角色及授权引用、必要的 depends_on；禁止含秘密值、任意 SQL 或任意 shell。create 只在具备授权时创建缺失资源；verify 只核对外部预建对象。运行名称从绑定解析后校验项目/环境和允许字符，先展示脱敏差异再执行。初始化对每项记录 ABSENT/CREATED/VERIFIED/CONFLICT/FAILED；结果中不记录密码。现有资源先比对预期归属和权限，不能因为同名就默认属于本项目。

新增 document-service 时只创建该服务的新库/账号及消息资源，不重新初始化 identity。部分资源创建成功后失败，保留已成功资源，下一次先核对再继续；不自动删除已创建对象来“回滚整个环境”。不存在的数据库可以创建；已存在却版本/归属不明的数据库不能自动 baseline。

prepare-local 只生成未存在的本地秘密和网络；resources 只创建环境资源；服务 migrate 只改自己的 schema。凭据轮换、资源删除和 local reset 都是独立显式动作。初始化入口以 OS 文件锁/服务器发布锁避免并发操作相同环境；不删除 PID 锁文件抢占。资源状态与秘密跟随指定环境文件目录隔离。

<a id="network"></a>

## 8. 网络、访问身份与端口

同一主机 infra 与应用是两个独立 Compose 项目，显式连接项目专属 external network。容器访问网络别名；宿主机访问仅映射到 loopback 的开发端口。服务实际发布地址由所在运行模式决定，规则见配置与服务发现文档。

跨服务器使用私网 DNS/IP 与映射端口，按消费方放行；Nacos 附加客户端通信端口也纳入清单。互联网只允许应用入口端口，数据库/队列/配置控制面不公开。Docker 端口发布可能影响主机防火墙的实际路径，验收从另一台主机实测。

组件管理员凭据仅在初始化/维护阶段提供，按需临时挂载；常驻业务进程只拿本服务身份。共享 PG 实例不等于共享账号，Redis 的数据库编号不构成访问控制边界。

<a id="maintenance"></a>

## 9. 数据维护、组件升级与开发重置

本地卷可长期保留；清理仅针对当前项目 local 的明确卷，独立显式 reset 动作不进入日常启动/发布。测试/生产使用明确宿主机数据路径与运行 UID 权限；应用版本目录、镜像与持久数据分开。禁止发布时 down -v、volume prune 或用新镜像挂不兼容旧数据目录。

维护资料至少包括：版本/digest、网络端口、卷路径、资源上限、健康检查、账号/秘密引用、备份和恢复步骤、责任人。PG 备份恢复合同见[数据库迁移与升级设计·迁移所有权、账号和执行入口](10-数据库迁移与升级设计.md#ownership)；Rabbit/Nacos 数据和定义、身份签名密钥、对象存储配置纳入恢复清单。组件升级是独立维护任务，不由普通应用 deploy 顺带更新。

资源部署成功的条件是实际连接和权限检查通过，而非仅有容器 running。检查包括从消费主机连到目标、运行账号不能 DDL、数据库可恢复、控制面不对公网开放；未具备真实服务器时只可记录本地验证。
