## 1. 定位、保留项和范围上限

脚手架交付可独立维护的 Java/Python 源码项目。生成完成后不依赖创建器安装目录、另一个框架仓库或私有 Maven/PyPI 仓库。初始两个业务服务直接在主仓库，后续新增业务服务统一以固定 Git submodule 引入；这是业务源码引用，不是恢复整个框架 vendor。每个业务项目拥有自己的基础代码、业务代码、配置、数据库与部署；身份服务不是所有项目共享的中央平台。

保留 identity-service（含通用管理页面）、api-gateway、java-sdk、python-sdk；保留租户独立账号、OAuth2/OIDC、BFF、权限目录、RLS、Nacos、PG、Redis、Sentinel 和 Python 保护能力。协议与权限语义不借交付改造重新设计。消息适配继续可选，不默认安装 RabbitMQ。

不交付 Agent/聊天业务、不做 CRUD 通用生成平台、不做模板插件市场、不做服务管理控制台、不做自动源码升级合并器、不建设制品平台。脚本只处理文件生成、配置检查及标准工具编排，不成为运行时服务。

默认能力：源码双语工程、独立初始化、开发调试、OpenAPI、健康检查、日志、指标、服务选择、迁移、镜像构建和发布样板。可选组合：RabbitMQ、Prometheus/Grafana、业务 Web。ELK/Loki、链路平台、Alertmanager、分布式事务、服务网格、Kubernetes 和自动备份调度不作为启动前提；项目可按现有标准接口另行接入。

## 2. 仓库、样例与生成结果

维护仓库沿用公共 SDK/services/config/infra/deploy/tests/docs 的职责，将 Java/Python SDK 收拢为 sdk/java、sdk/python，将项目所需工具能力迁入 scripts；维护仓库与业务项目使用相同的公共代码布局，不再另套 framework/project 外层。基础源码与样例各只有一份：services/sample-java-service、services/sample-python-service 可直接运行和测试；config、infra、deploy、web 归根目录。创建按明确参数转换样例，输出中不保留原样例，不维护 template 或 scripts/templates。

```text
equipment-platform/
├─ sdk/
│  ├─ java/                          # Maven artifactId 仍为 java-sdk
│  └─ python/                        # 发行包名仍为 ken-platform-sdk，导入名 ken_platform_sdk
├─ services/
│  ├─ identity-service/admin/        # 身份 API 与通用管理页同服务发行
│  ├─ api-gateway/
│  ├─ equipment-service/
│  ├─ inspection-service/            # 初始 Python 服务在主仓库
│  └─ scoring-service/               # 后续新增服务为固定 submodule
├─ web/                             # 可替换的业务页面；不复制身份管理前端
├─ config/
│  ├─ services.yaml                 # 服务登记唯一来源
│  ├─ development.yaml              # 仅开发端口/地址等非秘密设置
│  ├─ nacos/                        # 配置源文件
│  └─ environments/                 # local/test/prod 样例
├─ infra/                           # PG/Redis/Nacos；可选组件配置
├─ deploy/                          # 应用 Compose、Nginx、Ansible
├─ scripts/                         # 见第 3 节；完整项目内实现
├─ .gitmodules                      # 有新增业务 submodule 后才出现
├─ .vscode/                         # 可提交的 tasks/launch/extensions/settings
├─ docs/                            # 接入/调试/SQL/发布/升级及编码规范
├─ tests/                           # 本项目接入烟测；非维护仓库历史验收脚本
├─ pom.xml                          # 父 POM + Java reactor
├─ pyproject.toml / uv.lock         # 仅脚本工具依赖；不合并业务 Python 环境
├─ mvnw / mvnw.cmd / .mvn/
├─ .gitignore / .editorconfig
├─ README.md
└─ .local/、dist/                   # 运行/秘密及产物；均忽略
```

没有 manage.py 或框架 vendor；.gitmodules 仅用于后续新增业务服务。业务项目不带 template、scripts/templates、原 sample 服务、脚手架 create.py/create_service.py/generation.py、历史计划、开发者 .cursor/.codegraph 配置、测试缓存和旧发行材料。SDK/基础服务的模块测试随源码保留；跨模块测试按生成项目行为交付。规范复制成项目自己的文件，不链接框架磁盘位置。现有用户协作规则不从维护者工作区自动复制，使用受版本管理的项目规则模板。

创建从显式 Git ref 的已提交快照读取白名单文件；拒绝已有目标目录，不从脏工作区混入内容，不删除失败现场。变量替换仅作用于声明的项目名、业务包/服务名、路由、权限和对应测试。公共包 `com.ken.platform.foundation` 与 `ken_platform_sdk` 本次保留，避免文件交付重构同时重命名公共 API。

创建不执行 Docker、数据库、Maven 编译或依赖安装；Python 锁在首次依赖准备生成并提交，此后 frozen sync。创建阶段不联网格式化；首次依赖准备运行根 Maven Spotless 格式化改名后的 Java 包名/导入，再提交生成源码。后续构建使用格式检查。README 记录模板标签/提交；项目当前 Git commit 才是部署源码身份，没有第二个可变 framework-version 权威。

## 3. scripts 入口与命令边界

项目公开入口固定 init/dev/compose/add_service/migrate/build/package。local 合入 init、deploy/dev 合入根 dev、instructions 合入 generation；构建与打包实现各归自身。create/create_service/generation 仅留脚手架仓库。新项目带共享协议 JSON 与 acceptance/smoke，不带维护者测试；CI 导出时移除框架维护专用 job；非纯文档变更运行固定核心模块与明确列出的定向测试，纯文档变更不构建业务但仍扫描秘密。Java/Python job 使用显式 module/tests 矩阵；scope job 校对 config/services.yaml 与 SDK，缺模块、重复模块、测试文件不存在均失败；执行测试时零匹配失败。生成时同步替换初始业务服务名。新增业务服务由项目维护其 CI 定向用例，不新增自动依赖图/测试选择系统。真实集成默认不自动启动，显式启用后环境故障不能当通过。

下表定义命令合同；实际实现和验证状态以计划第 8 节为准。工作目录均为项目根；Windows 使用 Python 3.12 的 `python`，Linux 可用 `python3`。不生成两套 PowerShell/Bash 业务逻辑。

| 入口 | 参数与职责 | 禁止副作用 |
| --- | --- | --- |
| `scripts/create.py` | **仅维护仓库**；`--ref --output --project --java-service --java-package --python-service --python-package --port-offset` | 不初始化数据库、不提交/push |
| `scripts/create_service.py` | **仅维护仓库**；`--language --name --package --output --project-root`；以两个样例为唯一来源，在项目外生成独立仓库，以目标项目 SDK 生成锁，含迁移、测试、配置初始值及接入说明 | 不自动建远程/commit/push，不直接登记运行环境 |
| `scripts/add_service.py` | `--repo --ref --language --name --package --port`；将已提交业务仓库引为 services 下的 submodule，并追加服务登记、Maven/Compose、Nacos、VS Code | 不重新生成远程业务源码，不跟随浮动分支，不覆盖已有服务或用户条目 |
| `scripts/init.py` | `--env local --services <逗号列表或all> [--dev-host ...] [--with-demo]`；依赖、资源、迁移、技术身份和本机运行绑定 | 不以初始双语名单限制服务；不重置密码/角色/卷 |
| `scripts/dev.py` | `<service> [--prepare-only] [--reload] [--tenant-code ...]`；检查并准备受限运行环境，或启动单服务 | 不自动迁移、授权、启动一整套环境；不按端口杀进程 |
| `scripts/migrate.py` | `--env --service <数据库所有者> --check` 或 `--apply`，test/prod 必须 `--env-file`，Python 指定 `--migration-image`，跨机用 `--previous-state`；绑定固定迁移工具/目标 | 无 clean/downgrade 自动入口；详见设计 10 |
| `scripts/config/publish.py` | `--env-file --source [--data-id ...] [--dry-run]`；init 根据服务选择传入 Data ID 列表 | 不自动读取全局管理员凭据注入应用 |
| `scripts/build.py` | `--release --services ... --output ... [--base-release ...]`；构建所选应用、迁移产物和来源记录 | 不重新解析生产依赖、不隐式推镜像 |
| `scripts/package.py` | `--build-record --images --output ...`；从同次构建和 registry digest 映射产生部署包 | 不手工重新编写文件摘要，不把局部包当首次完整环境 |

生成项目同时携带 docs/guides 中的工程检查、SDK 使用参考及安全验收清单；tests/fixtures 包含 introspection-v1.json、gateway-routes-v1.json、api-errors-v1.json，供双语测试共用。日志、错误、动态就绪与任务入口的唯一行为合同见[协作设计](07-Java与Python协作设计.md#developer-basics)。

根工具依赖锁随模板交付，工具环境通过项目根 `uv sync --frozen` 建立；初次无工具环境的脚本仅用标准库给出这一明确命令，不偷偷安装全局包。VS Code task 使用 `uv run --frozen python scripts/...`，工具环境与业务服务 .venv 分离。scripts 内可复用少量内部函数；不得重新建立命令注册中心、通用插件装载器或任意 YAML 命令执行器。

状态、日志和停止由薄入口 scripts/compose.py 调用 Compose 的 ps/logs/stop，固定读取本机已初始化的 env-file 和 Compose 文件；VS Code tasks 调用同一入口，只管理基础容器。宿主业务的日志和停止归对应终端或调试会话。脚本捕获 Ctrl+C 后仅终止自己创建的子进程/容器并保留数据，输出阶段、对象、失败原因和恢复入口，不记录秘密。

## 4. 服务声明、配置与派生文件

`config/services.yaml` 登记 identity/gateway 以及所有业务服务，不含真实秘密。固定 schema 示例（拟新增）：

```yaml
services:
  equipment-service:
    source: local
    language: java
    directory: services/equipment-service
    package: com.acme.equipment
    main_class: com.acme.equipment.SampleApplication
    resources: services/equipment-service/resources.yaml
    permissions: services/equipment-service/src/main/resources/permissions.yaml
    migration:
      tool: flyway
      path: services/equipment-service/src/main/resources/db/migration
    requires: []
```

source 仅允许 local/submodule；初始两服务为 local，后续新增为 submodule。提交由主仓库 gitlink 固定，URL 在 .gitmodules，不在 YAML 再写一份 ref。Python 使用 `entry`（现有 console script）、`debug_module`（如 `inspection.main`）和 `app_factory`（如 `inspection.main:create_app`），不声明 main_class。main 模块必须提供模块执行保护，使 `python -m inspection.main` 调用已有 main 并保留事件循环策略。固定基础服务字段同样校验；无数据库服务显式省略 resources 中的 PG 资源及 migration，生成骨架默认带数据库。requires 只列确实必须运行的项目内服务；示例 peer 调用是可选演示，不列为强依赖。只接受已知服务、仓库内路径、合法包名；未知字段、同名端口、环依赖或未知 requires 均拒绝。

development.yaml 保留 project、port_offset、DEV_HOST 和各服务开发端口，移除重复的 language/directory/entry/package 和 initial_services。资源名及 owner/migrator/runtime 仍由服务 resources.yaml 定义，服务登记只引用路径，不复制第二份资源定义。环境连接和自建/external 模式在环境文件；Nacos 启动所需地址/凭证不能放到 Nacos 自己里面。

初始化不重写版本管理中的项目配置。add_service 只追加新服务声明、Maven module、独立服务 Nacos 文件和固定名称的 IDE 条目，不修改 submodule 内源码。Compose 的服务定义放 deploy/generated.services.yaml，用户覆盖放 deploy/compose.override.yaml；生成文件注明禁止人工编辑。网关既有路由保留，只追加新服务路由，重名即拒绝，不实现通用合并器。

需共同编辑的 .vscode/launch.json、tasks.json 用固定的 `service:<name>` 名称识别新增条目；正常新增不替换旧条目。支持 JSONC 识别与原文保护，发现无法保留的注释/格式或名称冲突时输出候选文件供人工合并，不直接覆盖。读取所有输入并预检全部冲突后才写入，写前再次核对输入摘要。B 克隆时按已提交的声明与条目标识识别归属，不依赖 A 的 .local/generated-files.json。运行绑定等完全位于 .local 的文件仍可用本机摘要防覆盖；摘要丢失且内容不同即停止，不能影响版本管理文件的正常新增服务操作。

## 5. 初始化、技术身份和演示数据

首次 local 端口预检只覆盖实际自建且启用的组件、基础入口以及本次选中的业务服务。业务监听使用 development.yaml 中的最终 port，不重复叠加 offset；仅监控启用时检查业务指标监听。RabbitMQ/Grafana 未启用或组件为 external 时，不要求其本地发布端口空闲。既有环境的重复初始化不把自身已占用端口判为外部冲突。网关配置失败恢复遵循[成功应用摘要](02-配置与服务发现设计.md#refresh)。

初始化作用于**当前选择的服务及其必需依赖**，而非最初两个样例。支持从零安装、重复执行、增加服务后补齐、全新克隆后重建本机环境。local 默认自建 PG/Redis/Nacos，external 时只验证连接与项目权限，不启动对应本机容器。

首次 local 顺序固定：配置/端口检查 → 工具与所选 Python 依赖准备 → 从本项目源码构建 identity/gateway 开发镜像及所选 Python 迁移镜像（不要求 clean Git）→ 组件启动或 external 验证 → 创建/核对资源 → 发布公共、identity 和所选服务 Nacos 配置 → 身份迁移 → 签名密钥/基础管理员 bootstrap → 准备服务/Gateway/BFF 运行绑定 → technical 登记 → 身份 ready → 权限目录发布 → applications 登记 → 所选业务迁移 → Gateway/Nginx ready。开发镜像由 init 调用共用构建函数准备；正式 build 的 clean/source 校验不套到本地编辑流程。迁移镜像锁定依赖在构建时安装，迁移运行时不联网安装包。只报告基础环境就绪，业务仍需 F5/dev 启动；任何阶段失败停止下游，保留资源，不删库重试。

服务技术登记与用户授权分开：

- 增加受控离线维护命令 `bootstrap-services-technical` 与 `bootstrap-services-applications` 两阶段。technical 先创建/核对 service→audience、目录发布客户端和各资源/Gateway 内省客户端；随后在线发布权限目录；applications 才创建/核对业务 BFF 与 local Swagger 客户端，否则业务 scope 尚不存在。复用 ClientPolicyRules、协议/策略双表事务和审计，不新增 Web 管理 API、业务表或通用同步状态机。
- 原 initialize() 的首次 bootstrap 摘要用于固定管理身份，保持原语义；新增服务登记用独立的维护用例核对当前定义，不能通过改写旧 bootstrap 摘要绕过校验。当前对象存在时核对主体类型、公开/私密类型及私密客户端凭据，不写策略；此类归属冲突停止。scope/audience、回调、启停与允许租户以管理员当前策略为准，维护输出 EXISTING_PRESERVED，不按骨架恢复。新增服务后管理员明确调整所需范围，旧策略不足由真实协议/业务请求拒绝，初始化通过不代表用户获得访问权限；不可自动扩权、旋转秘密或抹掉管理员新增的租户绑定。允许租户集合由管理员管理，技术初始化不将空集合解释为所有租户，不用空集合覆盖已有绑定。
- 稳定客户端 ID 沿用原算法；每用途独立秘密先原子写入受控目录再创建，失败重跑使用同一秘密。公开 Swagger 客户端没有 client_secret。新增服务扩大已有 BFF 的 audience/scope 时，先提示管理员修改，再同步 BFF 请求 scope 配置；旧会话/token 不自动扩大授权，用户退出业务会话后重新登录同意。
- 通过既有权限发布 API 发布代码清单，不直写权限库；租户角色是否获得新权限始终显式决定。未授权请求应返回 403，不以关闭鉴权实现“开箱即用”。
- 演示账号仅 `--with-demo`、APP_ENV=local、自建隔离 PG 时安装；沿用现有演示事务和身份绑定校验。新增服务不会重新运行旧演示定义，不自动给演示角色增加新权限。test/prod 拒绝 --with-demo。
- 不新增通用同步状态机或技术登记专用业务表。现有客户端定义、数据库资源及迁移历史为事实来源；单次登记事务失败回滚本事务，跨服务失败保留前序结果并可核对重跑。

新机器连接已有环境时，从受控秘密存储取回既有秘密，不把“本机没文件”当作服务没注册；缺失时停止并指明恢复材料。既有数据项目转换先备份、保留 project/环境/库/卷/namespace/client ID，见第 10 节；不通过创建同名新项目替换运行环境。

### 5.1 第一次登录到第一次业务请求

init 输出 PUBLIC_ORIGIN、`/identity/admin/`、业务页、每服务 Swagger URL，以及平台首次密码文件的路径，不在日志打印秘密。两种使用路径必须分别写入生成 README：

1. 演示路径：显式 init --with-demo，使用输出的 alpha/beta 组织代码与账号密码文件，按要求完成首次改密；打开业务页登录，启动 Java/Python 后验证列表与双租户隔离。重跑不重置密码，也不给后续新增服务自动加角色权限。
2. 正常路径：不带 --with-demo；平台管理员登录管理页并完成首次改密 → 创建租户及租户管理员 → 在客户端管理为业务 BFF/所需 Swagger 客户端允许该租户（空列表拒绝所有租户）→ 租户管理员进入本租户，创建普通用户与角色、勾选已发布的业务权限并分配用户 → 普通用户登录业务页。平台管理员不当作租户业务账号。

首次业务请求验收必须用普通用户，未授权用户返回 403。新增服务重复“发布目录→管理员调整客户端范围/租户绑定→租户角色授权→更新调用方请求范围→重新登录”，然后分别验证网关调用和跨服务调用。403 排查按角色、客户端、token scopes、audience、租户能力检查，不关闭鉴权。

## 7. OpenAPI / Swagger

Java 复用与当前 Spring Boot 4 兼容的 springdoc-openapi 3.x starter，T-01 核实精确版本并锁定，不顺带升级 Spring。Python 用 FastAPI 内置 OpenAPI/Swagger UI；不引入另一个接口文档服务，不另造协议扫描器或聚合平台。

开发提供每服务文档地址：Java `/swagger-ui/index.html` 与 `/v3/api-docs`，Python `/docs` 与 `/openapi.json`。服务直接端口默认仅开发网络可达；Gateway/Nginx 不自动向公网发布这些路径。文档 URL 从服务登记与开发端口输出，Java/Python 数据模型、错误格式、分页、security scheme、业务 scope 和 tenant 来自可信认证上下文的说明随模板提供。

local 默认启用；test/prod 默认禁用 UI 和 JSON。非 local 显式启用只允许私网/受控管理入口，不允许一条配置把文档匿名公开。文档可见性与业务接口授权分开；不从 BFF 导出 token，不提供密码模式或免认证调试接口。

local 调试直接复用 Swagger UI 的 Authorization Code + PKCE（S256）。每服务登记独立公开客户端 `<service>-swagger`，无 client_secret、无 refresh token、非 first-party，必须用户同意；audience 为当前服务，scope 为其已发布业务范围和 profile，允许租户由管理员选择，演示模式才显式绑定演示租户。Java 精确回调为 `http://localhost:<port>/swagger-ui/oauth2-redirect.html`，Python 为 `http://localhost:<port>/docs/oauth2-redirect`，端口来自 development.yaml；不得使用通配回调。授权端点经 PUBLIC_ORIGIN，token 端点同源于身份入口；身份服务仅在 local 为这些准确 Swagger origins 的 token 请求提供 CORS，生产不带此名单，不开放任意 origin 或其他管理端点。

使用步骤：F5 启动服务 → 打开输出的 Swagger URL → Authorize 选择 scope → 身份页选择组织并登录普通用户 → 同意 → 回到 Swagger Try it out。UI 不持久化授权到浏览器存储，页面关闭/失效后重新授权。跨服务演示需要额外下游 audience/scope 时由管理员明确配置，不能因 Swagger 登录成功就认为下游也已授权。T-07 同时验证 PKCE、精确回调、CORS 和 401/403；不只是 JSON 可读。

Python 当前模板不声明 FastAPI security scheme 的部分需显式补齐，不能只打开 docs_url 就认为接入完成。错误响应只展示脱敏示例，内部维护接口不进入业务 API 文档。

实现细节：Spring Boot 4.0 系列使用固定 springdoc 3.0.3，兼容性以本计划定向构建/测试为证据。现有授权协议要求 tenant_code，CLI 使用 `scripts/dev.py <服务> --tenant-code <租户编码>`；VS Code 的 prepare task 提示输入，参数只进入 authorization URL，不进入换取 token 请求，也不替代登录后的租户核验。留空可查看文档，但租户授权必须补齐编码后重启。身份服务只允许已登记、ACTIVE、公开 Swagger 客户端精确 localhost 回调的 origin 对 token 端点 POST；不放开 Cookie 或其他端点。

依据：[springdoc 兼容与配置](https://springdoc.org/)、[FastAPI 文档 URL](https://fastapi.tiangolo.com/tutorial/metadata/)、[Swagger UI 原生 PKCE 配置](https://swagger.io/docs/open-source-scripts/swagger-ui/usage/oauth2/)。

## 8. 健康、日志与可选监控

默认服务提供 liveness、readiness、结构化日志及 Prometheus 格式指标。Java 主端口健康探测及独立指标监听规则统一引用[部署设计](09-应用部署与运维设计.md#observability)。Java 用现有 Actuator/Micrometer；Python 复用已有 prometheus-client，不安装第二套指标 SDK。liveness 不随短暂数据库故障失败；readiness 检查服务实际依赖和当前数据访问能力。业务 schema 条件见设计 10；不能仅检查迁移版本字符串就宣称所有表兼容。

日志输出 stdout，容器日志配置轮转；含 project/env/service/instance/request_id/trace_id，错误记录脱敏原因。不默认记录 token、Cookie、密码、完整请求正文。请求 ID 必须贯穿 Java→Python，已有 trace context 继续传递，但本次不承诺交付完整分布式链路平台。

基础指标：请求量、错误率、时延、在途请求、保护拒绝；Java JVM 与连接池、Python 进程可用指标。标签使用路由模板，不使用用户/租户 ID、任意 URL、request_id 等高基数字段。

Prometheus/Grafana 作为 `monitoring` 可选 profile，提供固定版本配置与一份基础 dashboard；默认不启动，Grafana 不匿名对公网，初始秘密不进 Git。抓取目标按实际选中服务生成：local 支持宿主 DEV_HOST，单机容器用服务 DNS，多机使用私网地址；不能只提供 127.0.0.1 样例。指标端点只在内部采集网络开放，不复用业务 OAuth token 供抓取，也不因此放行其他管理端点。

没有监控组合时仍可 `Compose ps/logs` 和读取 readiness。示例告警表达式可以随配置提供，通知渠道/值班接收由项目现有体系负责；本次不强制 Alertmanager，不声称部署 Grafana 即已具备运维闭环。

## 9. 按需运行、构建与部署

服务选择按服务名，不按语言整体打包。选中业务会带上既定 identity/gateway 和入口基础组合；强依赖从 requires 解析并检查，不以 Nacos 动态发现来猜依赖。未选择服务不启动、不迁移、不发布权限，也不删除已有资源。单独停用服务不是删表或退租户。

| 组合 | 必需项 | 不自动加入 |
| --- | --- | --- |
| Java 开发 | 基础组合 + equipment-service 宿主进程 | Python、RabbitMQ、监控 |
| Python 开发 | 基础组合 + inspection-service 宿主进程 | Java 业务、RabbitMQ、监控 |
| 双语联调 | 基础组合 + 两业务进程 | MQ/监控 |
| 全容器单机 | 基础组合 + 显式选中的业务镜像 | 未选业务 |
| 外部 PG/Redis/Nacos | 保留资源权限/连接验证，跳过对应容器 | 同名本机替代组件 |
| monitoring / mq | 在显式启用时加入对应成熟组件 | 新常驻管理服务 |

默认基础组合是 identity、gateway、Nginx 与自建模式的 PG/Redis/Nacos，六个常驻容器；业务宿主进程不是容器，全容器模式按所选业务增加。monitoring 增加 Prometheus/Grafana 两个容器，MQ 另计；迁移/bootstrap 是临时任务，不算常驻副本。不把“仅 Python 业务”说成可以移除身份系统的 Java 运行时。

局部构建必须通过 --base-release 提供已部署发行清单，核对项目及基础输入指纹后复用 identity/gateway/nginx 的不可变镜像；基础 SDK、核心源码或构建配置变更要求完整构建。业务模块清单变化不单独触发基础镜像重建。部署包记录 complete，首次 bootstrap 拒绝局部包。

沿用 infra/deploy 两个 Compose 项目与同机明确 external network，不混淆 Docker external network 与 external 托管数据库。Compose profiles 固定使用 monitoring 与 mq；在所需 infra/应用 Compose 命令显式加 --profile monitoring 或 --profile mq，不通过虚构的 init 参数启用。选定业务若声明需要 MQ 而环境未启用/未绑定 external Rabbit，则预检拒绝并给出启用步骤。指定服务名选择业务；profiles 不跨两个 Compose 项目自动处理依赖，初始化脚本显式分两阶段启动。多机 bridge 不互通，使用私网可达注册地址，Ansible 按主机清单运行同版 Compose。参考 [Docker profiles](https://docs.docker.com/compose/how-tos/profiles/)。

首次安装与升级使用同一部署包，单机也是一台主机的 Ansible inventory，不另维护第二套发布逻辑；Compose 用于实际容器与日常 ps/logs/stop。部署包根先 `uv sync --frozen`，从受控 Linux/WSL 控制机执行 `ansible-playbook -i deploy/ansible/inventory.yaml deploy/ansible/<动作>.yaml --extra-vars @<包外环境变量文件>`。固定动作沿用 infra、initialize、migrate、deploy、reconcile、rollback；具体变量、TLS/秘密和恢复规则归设计 09。首次顺序：准备包外环境材料与源镜像仓库权限 → infra 启动/核对组件 → initialize 创建资源并发布基础 Nacos 配置 → 预拉取/校验全部所选应用和迁移镜像 → migrate 身份库并 bootstrap/启动身份 → technical 登记/权限发布/applications 核对 → 迁移业务 → deploy 启动网关/入口/业务 → 真实登录与业务烟测。首次 phases 由已有 playbook 编排，不能要求运维自行拼 bootstrap 内部参数。

升级先拉取校验镜像、核对配置/秘密和备份，再按设计 10 选择兼容迁移或维护窗口。兼容分支先迁移再更新应用；维护窗口分支先摘除入口流量、停止受影响旧应用及消费/任务写入者、核实已停止，再迁移及启动新版本，验收后恢复流量。发布说明必须列出项目额外写入者的停止/恢复步骤，框架不能猜测外部任务。迁移失败保持维护状态并停止下游，不自动回退 schema，不重建组件或重复首次 bootstrap。

构建只用本仓库源码和锁；Dockerfile/构建上下文公开可读，不只存在于隐藏临时目录。Java 根 POM 聚合 sdk/java、两基础服务和已登记 Java 业务；SDK 与服务 parent 都指向 ../../pom.xml。Java 用 reactor（sdk/java 与所选服务），Python 在 Linux 非 editable 安装 sdk/python，身份管理页在身份镜像内构建；Web 有自定义构建时显式提供静态产物。正式源码须 clean 且可由团队取回，但不再 fetch 已不存在的框架 gitlink；新增业务 submodule 必须 HEAD 与主仓 gitlink 一致、源码可取回且无未提交构建输入，记录每个所选业务提交。来源/镜像/迁移摘要自动生成；registry push 用现有 Docker/CI，digest 映射由同一发布步骤采集，不让人逐项手填。

应用镜像在测试和生产复用同一 digest；环境秘密不进镜像/包。部署包包含 config/infra/deploy、scripts/config/infra/deploy 所需执行代码及根工具锁、Web 静态产物、release 清单；各服务只携带 `services/<name>/resources.yaml`、原相对路径的权限文件和 Java 迁移目录，不携带业务源码。Python 迁移镜像包含由服务锁文件固定的依赖和 revision；部署包另带原相对路径的迁移文件用于官方版本图及历史 SHA 校验。执行时只读挂载这份受发行摘要保护的迁移文件，使用固定镜像内 Alembic，不在运行时安装依赖；不依赖服务 .venv 或原仓库。包内 config/services.yaml 是运行所需字段的投影，不要求 main_class/debug_module 指向源码存在；禁止部署入口导入创建器/生成器模块。部署包还包含初始化身份所需的基础服务资源与权限材料。

必须在原源码不可用、没有 .local 的目录校验包内引用完整，再在获准环境仅凭部署包、外置环境材料和镜像仓库完成首次安装。清单、工具依赖和迁移摘要自动生成；不让运维逐项手填。保留已有失败锁、unknown 核对和恢复底线，不新建审批数据库或发布平台。

## 10. 源码升级与旧项目转换

生成项目的源码属于项目，基础模块允许项目维护。脚手架修复提供明确提交/补丁和影响清单，项目在升级分支选择合并；不能承诺自动或无冲突更新。规范/配置变化同样审查差异，不整目录覆盖。公共代码只做必要变化，避免无关格式重排提高未来合并成本。

SDK/身份/Gateway 修复、模板改进、数据库迁移、PG 等引擎升级分别说明。项目以自己的 Git commit 和镜像标识发行，README 模板来源只是溯源信息。升级不自动改变角色/租户/签名密钥；API/schema 不兼容时必须有具体转换步骤。

现有 vendor 项目仅提供转换检查清单：备份并提交旧项目，检查定制，恢复精确公共源码，保留业务目录、client ID、库/卷/namespace，调整路径与锁，最后移除框架 gitlink。不编写转换器或将未知旧项目转换夹具作为本计划交付门槛；有真实迁移项目时另行安排隔离恢复和数据/授权验证。不能因本计划完成而宣称旧项目可直接迁移。

<a id="service-submodules"></a>

### 10.1 业务服务 submodule 的完整接入合同

**两条路径固定，不自动选第三种：**

1. 已有兼容服务：先确认远程仓库符合本项目 SDK、包名、迁移/权限声明和启动入口合同，执行 `scripts/add_service.py --repo <URL> --ref <固定提交> --language python --name scoring-service --package scoring --port 48085`。不能把任意 Python/Java 仓库挂进来就宣称已接入。
2. 全新服务：在兼容版本脚手架根执行 `uv run --frozen python scripts/create_service.py --language python --name scoring-service --package scoring --project-root ../equipment-platform --output ../scoring-service` → 用户在独立目录提交、建立远程并 push → 使用上面的 add_service 挂载 → 初始化技术资源 → 管理员授权 → 启动/调试 → 提交主项目登记与 gitlink。创建器不代替用户创建远程仓库或提交/push。

create_service 仅在框架仓库运行，从根 services 的标准样例生成服务仓库，不从已有项目业务复制，也不带身份/网关/SDK 副本。项目内只保留 add_service.py 等运行/接入工具。服务仓库的 config/nacos 是首次接入的配置初始值；add_service 首次复制到宿主项目根 config/nacos 后由宿主维护，升级不再覆盖。Java parent relativePath 为未来挂载位置的 ../../pom.xml；Python SDK 路径为 ../../sdk/python。独立仓库的正常开发上下文是主项目 services/<name>，单独 clone 到任意目录不能保证构建；README 必须说明先接入兼容宿主项目。需要真正独立发布 SDK 的场景不在本轮。

新 Python 服务锁在生成时于临时的同构主项目目录中解析：复制必要 SDK 输入到 sdk/python，服务置于 services/<name>，执行 uv lock；输出锁中的相对路径必须等于最终挂载路径，不含临时绝对路径。不安装业务环境或启动容器；解析失败保留临时现场并不宣称服务可交付。根工具 uv.lock 随脚手架模板交付；初始业务 Python 锁在第一次依赖准备时显式生成并由用户提交，后续 frozen sync。新增 submodule 服务提交前已生成锁，接入时只检查，不在主仓静默改写子仓锁。缺锁时给出具体修复步骤，不能直接 frozen sync 冒充已就绪。

add_service 先在临时目录读取目标提交并完成名称、路径、包、锁/SDK 兼容和目标声明检查，再安装 submodule 与写登记。目标服务目录/名称已存在即拒绝。若 Git 操作后写文件失败，停止并列出已产生的 .gitmodules/gitlink/目录，不删除用户数据或伪报成功；测试覆盖重试和人工恢复。不隐式允许任意 file:// 协议或改变全局 Git 设置，测试夹具使用明确本地测试配置。

新机器：`git clone --recurse-submodules`；已有克隆缺目录时 `git submodule update --init --recursive`。脚本预检缺引用或 HEAD 不匹配，给出恢复命令，不能自动 update --remote、切分支或覆盖服务未提交改动。创建项目时若尚无新增服务，普通 clone 仍有效。

开发者在 submodule 建立明确工作分支，编辑、测试、提交并先 push 服务仓库，再在主仓提交 gitlink 和配套登记/配置。主项目自己的版本不能代替服务版本。主仓中的初始两个业务继续普通提交，不能把目录差异理解为不同权限/开发标准。

VS Code 统一从主项目根打开，Maven/uv/launch 只认服务实际路径；新增服务的配置在主仓 .vscode 中追加。submodule 的 .git 不复制进 Docker 上下文，正式构建使用被固定的文件内容。构建记录包含根项目提交和所选 submodule 的 path/URL/commit；服务升级只更新该服务提交及必要配置，不能顺带更新全部子仓。

## 11. 文档与交付检查

与本次修复直接相关的非集成回归必须列入既有 CI 显式矩阵，源仓和生成项目保持一致；不能只提交测试文件却不让其被选择执行。scope 检查读写统一使用 UTF-8，在 Windows 默认本地编码下也能运行，不要求用户预先设置 PYTHONUTF8。

维护仓库保留 design/guides/standards/plans 分工；生成项目仅带本项目 README、开发调试、SQL 变更、部署升级及必要规范，不带冻结计划。指南给出前提、工作目录、命令、结果和排错；说明哪些命令仅生成、哪些会改变运行环境。脚本名称、参数和 VS Code 配置由同一测试核对。

文档随每个功能阶段交付，不等全部发布功能完成：创建阶段有可复制命令与前提，初始化阶段有演示/非演示登录与首次请求，新增服务阶段有管理员授权及重新登录步骤，部署阶段有包外材料与完整命令。最终复审只汇总，不是第一次验证 README。

完整使用验收必须包括：A 创建项目 → 演示与非演示首次登录分别验证 → 第三个 submodule 接入、授权及重新登录 → B 递归克隆且无 A 的 .local，继续新增第四服务 → F5/Swagger PKCE/调用与租户隔离 → 源码不可用时从部署包首次安装 → 兼容与停机两种升级。Docker 及真实 UI/多机验收在用户恢复相应验证前保持未执行，静态候选不标“日常开发已可用”。
