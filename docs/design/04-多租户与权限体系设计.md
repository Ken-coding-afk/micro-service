## 1. 租户、账号与平台身份边界

用户以 `tenant_code + username + password` 登录。租户选择可以来自输入框或可信域名映射；identity-service 最终将其解析为 tenant_id 并校验。账号唯一约束为 `(tenant_id, normalized_username)`，username 去首尾空格并使用统一小写规范；显示名称独立保存。数据库内部 ID 使用 UUID，对外均为字符串。

同名账号可以存在于不同租户，密码、禁用状态、角色、第三方绑定均独立。用户切换租户必须重新完成目标租户认证；不能修改一个 header 就变成另一个租户用户。OAuth2 授权记录、登录会话和 access token 都绑定确定的 tenant_id，刷新 token 也不能改变租户。

## 2. 核心实体、约束与授权版本

| 表 / 概念 | 关键字段或约束 | 归属 |
| --- | --- | --- |
| `sys_tenant` | id、code 唯一、name、status、expires_at、auth_version | 平台控制数据 |
| `sys_user` | id、tenant_id、normalized_username、display_name、password_hash、status、auth_version；租户内用户名唯一 | 租户数据 |
| `sys_role` | id、tenant_id、code、name、status、protected、version、authorization_version；租户内 code 唯一 | 租户数据 |
| `sys_user_role` | tenant_id、user_id、role_id；复合唯一，复合外键保证同租户 | 租户数据 |
| `sys_permission` | code 唯一、name、owner_service、principal_type、group_code/group_name、resource_code/resource_name、action_code、description、sort、supported_data_scopes、oauth_scope、status | 项目级权限目录，不是账号授权；平台/租户类型隔离 |
| `sys_permission_catalog_state` | 固定单行 id、version | 目录同步与角色授权使用的版本/锁入口；不新增服务 |
| `sys_role_permission` | tenant_id、role_id、permission_code、data_scope（无对象操作为 null） | 租户数据 |
| `sys_platform_user` | 平台运维账号及密码状态 | 平台控制数据，与租户账号分开 |
| `sys_external_identity` | tenant_id、provider_registration_id、provider_subject、user_id；前三项唯一 | 租户数据 |
| OAuth2 标准持久化表 | RegisteredClient、Authorization、Consent，使用官方 JDBC 模型并增加明确的租户关联索引 | identity-service 控制数据；由授权服务访问 |
| `sys_client_policy` | registered_client_id 唯一外键、principal_type、owner_tenant_id、allowed_tenant_ids、audiences、status、version | 仅客户端扩展策略；协议字段归 RegisteredClient，合同见认证设计 |
| `sys_auth_audit` | actor、actor_type、tenant_id（可空）、action、target、result、request_id、created_at | 审计数据 |

OAuth2 标准表中对租户的关联必须以可查询列或专门关系表落库，不能只存在可变内存 Session 内。平台身份管理平台账号、租户生命周期、初始管理员、应用配置及平台安全策略，不自动具有读取租户业务数据的权限。

账号只由管理员创建，使用一次性初始凭证并强制首次改密；密码重置使旧授权失效。公开自注册、邀请与邮件激活不属于当前交付，见[账号生命周期](#registration)。

密码哈希、长度、弱密码保护、登录限速/锁定以及安全策略字段统一定义于[认证安全策略](05-认证与OAuth2设计.md#security-policy)。这里只要求账号保存算法标识散列、不保存可逆密码，不重复维护默认值。

管理实体持久化：sys_user/sys_tenant/sys_platform_user 等可编辑实体增加 version（与用于撤销的 auth_version 分开）；平台管理员使用固定受保护身份，不再建立一套跨租户可配置角色。另有 `sys_tenant_capability`（tenant_id、capability、enabled、version）、`sys_security_policy`（字段与项目统一规则见[认证设计](05-认证与OAuth2设计.md#security-policy)）、`sys_password_reset`（主体、tenant_id、token_hash、expires_at、consumed_at）、`sys_session_binding`（主体、tenant_id、SSO 会话摘要、授权记录 ID、创建/最后活动/到期/撤销时间）支撑页面。唯一键、归属检查和 RLS 与[租户实体及隔离](04-多租户与权限体系设计.md#isolation)一致，身份协议数据不能当作业务服务可直接访问的表。

## 3. 资源操作、角色与数据范围

功能权限采用稳定的字符串，如 `document:read`、`document:analyze`、`identity:user:manage`。用户可拥有多个本租户角色；角色授权基础集合为有效角色授权的并集，实际应用可用权限还须按 [认证与OAuth2设计·内省、应用权限与最终授权交集](05-认证与OAuth2设计.md#introspection) 与客户端、token、目标资源取交集。

涉及数据对象的 permission 范围只支持 `SELF` 和 `TENANT`；无数据对象的操作声明空支持范围并保存 data_scope=null（不适用），不代表访问全部记录。同一对象操作的范围规则为：SELF 只能操作 `owner_user_id = 当前用户` 的记录；TENANT 可操作当前租户全部对应数据。同一个权限有多个角色授权时取较宽范围，但范围永远不扩展到其他租户。没有授权就是拒绝，不把空集合解释为全部权限。

业务服务声明某个操作支持哪些范围。例如 `identity:user:manage` 只支持 TENANT，文档读取可以支持 SELF/TENANT。平台导入权限目录时校验这一限制，避免给一个服务无法落实的范围配置出“看似成功”的角色。

业务页面和按钮如何展示由项目自行实现；框架不提供菜单授权模型，最终检查在服务端。详情、分页、统计、导出、更新、删除都需要相同的数据范围；不能只限制列表。查不到或不可见的资源统一 404，避免泄露另一租户是否存在某条记录。

“租户管理员”是系统内置受保护角色，管理本租户账号、业务角色、授权、会话和身份审计。应用/提供方/安全策略只由平台管理；禁止普通角色包含受保护身份管理权限。最后一个有效管理员的删除/禁用在事务中锁住租户管理记录后拒绝。管理员不自动获得业务数据访问权。

## 4. 多存储租户隔离

一个项目使用独立的 identity-service 数据库和业务服务数据库，可位于同一 PostgreSQL 实例。每个服务只持有自己数据库的运行账号，不跨服务 JOIN，不直接读写 identity-service 用户表。Python 独立持久化时拥有自己的库；纯 Worker 通过任务所有者 API 读写状态。

租户业务表统一包含 `id UUID`、`tenant_id UUID NOT NULL`、`created_at TIMESTAMPTZ`、`updated_at TIMESTAMPTZ`，需要个人数据范围的表增加 `owner_user_id UUID NOT NULL`；需要并发更新的表增加 `version BIGINT`。审计操作人可另设 `created_by`，不将其默认等同于数据所有者。

数据库唯一约束按租户组合，如 `(tenant_id, document_code)`；同服务内跨表关系使用 `(tenant_id, referenced_id)` 复合外键及对应唯一索引。跨服务 ID 是逻辑引用，通过 API 校验归属，不跨库建外键。默认不全局启用逻辑删除；有恢复需求的实体明确删除语义、唯一键和查询条件。

应用层主动添加租户和权限条件，同时启用 PostgreSQL RLS。每次访问租户业务数据必须在事务内设置 transaction-local 的 `app.tenant_id`，并在本次事务连接上执行查询；Python 使用 ContextVar，Java 使用请求上下文与受控事务钩子传递。禁止在连接池上设置跨事务的 session 级租户值。

RLS 的核心约束示意（不是本设计执行的 SQL）：

```sql
USING (tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid)
WITH CHECK (tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid)
```

缺少上下文时策略不匹配任何租户；SELECT 无结果，写入拒绝。运行账号不得是超级用户、表所有者或拥有 BYPASSRLS；迁移账号和运行账号分开；租户表启用 RLS 与 FORCE ROW LEVEL SECURITY。RLS 保证租户底线，SELF 等细粒度条件仍由服务实现。PostgreSQL 明确说明表所有者通常绕过 RLS，因此账号权限必须同时落实。[PostgreSQL RLS 文档](https://www.postgresql.org/docs/17/ddl-rowsecurity.html)

控制数据（租户目录、OAuth2 客户端、平台账号、授权记录）由 identity-service 的专用 repository 访问，不套租户业务表的通用策略；它们必须有独立的权限与租户关联检查。登录查询在 identity-service 解析并验证租户后建立受控事务，只查目标租户账号。后台扫 Outbox 等跨租户内部工作使用只允许访问相应技术表的专用数据库角色，不能给整个业务服务 BYPASSRLS。

| 位置 | 规则 |
| --- | --- |
| Redis | 业务 key 使用 `项目:环境:服务:tenant_id:用途:业务键`；全局 key 必须显式登记用途；授权敏感操作不使用陈旧业务缓存作最终判断 |
| 对象存储 | key 使用 `项目/环境/tenant_id/资源类型/随机ID`；客户端不自行指定任意完整 key；下载前验证数据库记录及权限 |
| 预签名 URL | 默认最长 5 分钟；签发后不能承诺瞬时撤销；需要立即撤销的文件走服务端代理下载 |
| 检索/向量库 | 租户作为强制过滤条件，工具只接收受控过滤参数；不得靠模型提示词要求模型“别读其他租户” |
| MQ | tenant_id 为协议字段，但字段本身不是授权凭证；消费者核对生产者权限和业务记录归属 |
| 定时任务 | 显式枚举授权租户并分别创建上下文；执行完立即清除；禁止无租户默认执行全部数据 |
| 并行/异步代码 | 明确复制不可变身份上下文；请求结束后不复用其 DB session 或连接 |

租户停用阻止新登录、新授权、新任务领取和新的业务访问。正在执行的模型计算可协作停止；已发生的外部副作用不能靠修改租户状态回滚。删除租户采用“停用 → 保留期内审查 → 独立清理作业”，不提供一键同步删除所有存储的接口。

## 5. 权限目录、固定管理边界与并发规则


一个权限由服务所有者、业务分组、资源类型、操作编码、中文说明及支持的数据范围构成。管理员按照“选择角色 → 选择资源操作 → 选择范围 → 查看差异与影响 → 保存 → 分配用户”的顺序操作，不需要理解 URL、前端组件或策略表达式。

示例：doc-insight 中建立“文档分析员”，授权 `document:read=TENANT`、`document:analyze=SELF`、`document:cancel=SELF`，不授予人工恢复。角色页展示资源“文档/分析任务”和各自操作；chat-assistant 只发布 Agent 权限时，同一页面展示 Agent 操作，不出现文档项目专属逻辑。操作不局限于 CRUD，可以是运行、取消、批准、恢复。

业务服务随版本提交 permissions.yaml，受限发布身份同步到 identity-service。权限展示元数据为 `code`、`name`、`owner_service`、`principal_type`、`group_code`、`group_name`、`resource_code`、`resource_name`、`action_code`、`description`、`sort`、`supported_data_scopes`、`oauth_scope`、`status`；清单中的 data_scopes 映射为 supported_data_scopes。业务服务只能发布自己的 TENANT 类型权限，PLATFORM 类型和身份管理保留编码仅由身份服务的受控发行入口维护。group_code 在 owner_service 内唯一，相同组的名称/排序必须一致，缺失分组时归入服务默认组。元数据仅用于显示与分组，不包含可执行脚本、任意组件路径或 HTML。

项目权限清单随服务制品交付，例如：

```yaml
service: document-service
permissions:
  - code: document:read
    resource_code: document
    resource_name: 文档
    action_code: read
    name: 查看文档
    data_scopes: [SELF, TENANT]
    oauth_scope: documents.read
```

`POST /internal/v1/permission-catalogs:sync` 接收 service、release_version、清单校验和与权限条目；调用凭证必须获准发布该 service。部署脚本从指定服务制品读取，不另维护一份 deploy 权限定义。新增/改名可幂等同步，清单缺项不删除旧权限；废弃采用 deprecated → 迁移角色 → 显式停用。同步和角色编辑按目录版本/锁协议执行，不自动修改现有用户授权。identity-service 尚未 ready 时禁止执行该 API。

oauth_scope 是固定的 scope 到操作映射；服务可有多个操作映射同一个 scope。它与 client 允许 scopes、token 实际 scopes、用户角色授权共同生效。服务需同步配置却未同步时，接口拒绝访问并给出可定位日志，不默认为已授权。

角色编辑页调用 `GET /api/v1/identity/permissions?assignable=true&role_id={role_id}` 获取“当前主体在当前租户可分配的目录”，响应包含 catalog_version、条目与范围；服务端根据主体操作权限、受保护管理身份及目标角色保护状态、租户状态和权限类型/状态计算，不能由浏览器提交任意 tenant_id 扩权。当前租户权限目录定义为本项目启用的 TENANT 类型权限；不隐含套餐/许可证模型，PLATFORM 类型权限不可给租户角色。用户角色选择调用租户 `/roles?assignable_to={user_id}` 查询可分配项；用户列表调用 `/users`。项目换成课程、订单或聊天应用，这些 API 和管理页面不变，只改变业务权限目录中的数据。

**业务权限与管理身份分开。** 受保护租户管理员管理本租户有效的普通业务角色和目录，不需要先拥有被授出的业务权限。普通业务角色即使留有历史 identity 管理编码，也不能成为管理资格；禁止新增此类授权。平台账号管理租户/应用和初始管理员，不通过租户 API 冒充用户。

管理员资格以有效受保护管理员角色及有效账号、租户为准，不能按角色名称猜测。维护受保护管理员沿用专用入口和最后管理员保护，普通角色编辑不能更改保护标记或复制出管理员。管理员角色只含固定身份管理操作；业务访问通过另授普通业务角色取得。

角色/用户查询只返回本租户对象。写入依次检查主体与租户有效、受保护管理身份、目标归属、对象保护/最后管理员、提交版本；同事务写入并审计。目标越租户按不可见处理。个人资料/密码/本人会话仍走 `/me`，不能自改角色或租户。

不再提供管理委派、权限上限编辑或模拟接口；旧 `/management-grants`、`/authorization-evaluations` 及其路由移除并返回未知路由 404。历史委派表与审计保留，不参与在线授权，不自动转管理员，不修改已应用 SQL。存在真实部署依赖时先核对影响清单再切换，禁止借兼容自动扩权。

查询是快照，提交重查主体、目标、目录/角色版本；不再提交 management_grant_version。事务锁顺序保持目录→租户→角色（按 ID）→账号/动作凭证。

角色授权使用 `GET/PUT /api/v1/identity/role-permissions/{role_id}`：提交 role_version、catalog_version，以及 permission_code/data_scope 的明确集合；服务端在事务中重查角色归属、操作者授权能力、租户状态、权限状态及支持范围，并校验版本。不合法项整体拒绝，不静默裁剪；角色或目录版本变化返回 409，页面刷新后由管理员确认，不自动用旧表单覆盖新授权。写入与审计同事务完成并递增 role.version；内省按实时角色授权查询使变更对后续请求生效，不因普通角色编辑强制全租户退出登录。用户/租户禁用的 auth_version 撤销规则保持不变。身份服务内锁顺序为目录状态行→租户→角色（多角色按 ID 排序）→账号/动作凭证；目录同步/停用同样先锁目录状态并递增 version。仅修改租户/角色的流程不能反向再申请目录锁；注册激活与初始角色分配也遵循目录→租户→角色→账号/动作凭证的锁顺序。角色权限/范围/启停另递增 authorization_version；保留现有版本字段，不再为注册/邀请扩展状态机。

分组父节点只用于选择子项，不是可被授予的权限；全选保存当时明确选择的编码，不保存 `*`。新增权限显示为未授权，不因用户有“管理员”字样自动放行；已停用/不可再分配的历史权限显示只读状态并允许受权移除，不能重新授予。SELF/TENANT 的选项来自对应服务声明，前端不统一添加“全部数据”或自行实现后端不支持的数据范围。

内置受保护角色、最后一个有效管理员等约束由服务端执行；页面依据允许动作提示禁用原因，不能依赖按钮隐藏保证规则成立。平台身份与租户身份分开验证，平台账号不通过同一租户接口获得隐式超级权限。

目录中的 `resource_code/resource_name` 表示服务内稳定资源类型，`action_code` 表示操作，操作中文名使用 `name`；分组和资源节点仅用于展示，只有叶子权限 code 可授予。同一 owner_service/resource_code 的资源名称必须一致，`(owner_service, resource_code, action_code)` 唯一。权限编码/资源/操作的语义变更须发布新编码并迁移角色，不允许悄悄重解释旧授权。

没有数据对象的操作使用 `supported_data_scopes=[]`，授权项 `data_scope=null`，页面显示“不适用”；这不意味着 TENANT，也不允许用于读取任意对象。涉及目标对象的操作必须声明并实施 SELF/TENANT。目录或角色存在无效范围时整个提交返回 400，未授权/越权返回 403，不可见对象返回 404，版本冲突返回 409；所有边界由后端执行。

搜索筛选后的批量选择只作用于可见且可授出的条目；页面明确显示本次选中数量。范围增大、撤权、角色停用在保存前展示差异和受影响成员数；影响数对应查询时刻，事务提交仍重新检查授权。没有直接用户授权、角色继承或任意 Deny 表达式；多个角色授权取并集，同一操作按可访问数据集合合并。数据范围冲突不会跨越租户。

角色停用使其授权不再参与有效权限计算；保留成员关系与审计便于恢复，不把“停用”实现成删除。用户分配角色使用 user.version；角色属性、授权、成员引用变动使用 role.version，以便并发授予、降权、复制和删除能检测过期视图。角色移除成员与最后管理员检查按固定锁顺序执行，不能由前端先查人数再决定能否删。

<a id="registration"></a>

## 6. 管理员开户、激活与禁用

平台管理员创建租户与首位受保护管理员；租户管理员创建本租户账号。临时凭证一次性受控交付，用户完成首次改密前仅可进入受限账号流程，不能取得业务授权。账号状态与 must_change_password 分开保存；现有 PENDING_ACTIVATION/ACTIVE/DISABLED 模型与数据库迁移保持兼容。

普通用户不能自行选择角色或变更租户。禁用账号/租户使后续认证、内省与刷新失败，密码重置递增 auth_version 并撤销已有授权；不能通过改密或第三方回调恢复 DISABLED。恢复须管理员明确操作并审计。

密码重置使用有期限、散列持久化、单次消费的凭证；未配置发送渠道时明确受控交付，不能显示已发邮件。账号无自动注册入口，第三方未绑定用户提示先取得本租户账号并完成显式绑定，不按邮箱自动开户/合并。

业务资料归业务项目，用 tenant_id/user_id 关联。框架不要求每个业务建立档案，也不在开户事务中调用业务数据库。将来注册/邀请或业务生命周期事件另经具体需求定义；当前不承诺激活事件驱动的资料初始化。

<a id="evaluation"></a>

## 7. 当前权限与角色来源

保留用户当前有效角色权限、SELF/TENANT 范围和来源角色查询；管理者必须有本租户受保护管理身份。本人 `/me` 只展示当前已验证应用、token scopes 与客户端策略交集后的权限。两种视图分别标记 ROLE_GRANTS 与 APPLICATION_EFFECTIVE，不接受浏览器指定任意 client_id 冒充当前应用。

共同授权计算和失败原因由[内省设计](05-认证与OAuth2设计.md#introspection)定义。结果是当时快照，不是未来授权凭证；对象可见性仍由业务服务检查。不提供任意目标客户端/scopes 的授权模拟产品。角色编辑的差异预览仅比较明确的前后授权集合，提交仍需重验版本。

<a id="boundaries"></a>

## 8. 变更场景、边界与验证

| 场景 | 后端必须保持 |
| --- | --- |
| A/B 租户同用户名 | 独立账号、密码、角色、第三方绑定和授权记录 |
| 同用户多个角色 | 仅有效角色取并集，同操作合并范围；不跨租户 |
| 修改角色与管理员同时分配 | 锁与版本保护；过期提交不能覆盖新授权 |
| 旧委派与普通角色含历史管理编码 | 不产生管理身份；普通角色不能新增受保护权限 |
| 注册后重复收到激活事件 | 身份不重复激活，业务档案按唯一键/Inbox 幂等初始化 |
| 用户/租户停用 | 新授权拒绝；恢复不能由找回密码或重复注册绕过 |
| 删除最后有效管理员 | 服务端事务拒绝，不能只依赖前端人数判断 |
| 服务绕过 Gateway 或原生 SQL | 仍鉴权、校验租户并受 RLS 约束 |

权限规则的权威定义在本文；管理界面负责呈现和调用，不通过按钮隐藏代替后端检查。协议、令牌和撤销检查点在认证设计中定义；页面提示和编辑交互在管理界面设计中定义。
