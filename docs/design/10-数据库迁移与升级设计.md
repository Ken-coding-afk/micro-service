## 1. 迁移所有权、账号和执行入口

数据库迁移是发行物的一部分，由发布流程独立执行。API/Worker 启动时只校验所需 schema 版本，不自动迁移；多个副本启动不会各自改表。应用账号无 DDL 权限，迁移使用单独凭证。

| 对象 | 迁移源与所有者 | 执行规则 |
| --- | --- | --- |
| identity-service 数据库 | 身份服务源码中的 Flyway SQL | 框架提供；项目按基础镜像版本执行对应迁移 |
| Java 业务数据库 | 各服务 `src/main/resources/db/migration` | 项目编写；Flyway 按版本执行；其他服务不改它的表 |
| Python 业务数据库 | 各服务 `migrations` 中的 Alembic revision | 项目编写并审查；发行前要求单一明确 head，不能临时自动生成生产迁移 |

普通 Python 服务只执行业务自己的 Alembic 迁移。框架不提供 Agent runtime schema/迁移；可选消息适配所需表由明确版本的官方迁移入口纳入业务服务维护，不自写 revision 图解析。

一个服务内采用共享表的多租户设计，schema 升级只执行一次；不是为每个租户重复建表。数据回填涉及租户时，按 tenant_id 分批，使用该次迁移限定的维护权限并审计；业务账号不能借迁移入口绕过 RLS。

迁移入口对目标数据库使用统一的 PostgreSQL advisory lock，锁由专用控制连接持有直到整条迁移链结束；所有自动及应急入口都遵守同一锁键。Flyway 自身锁不能代替 SDK + 业务迁移链的统一互斥，也不能假设 Alembic 自动提供该互斥。控制连接丢失立即停止调度新步骤，终止本次入口创建的迁移容器，任务标记结果待核对；步骤超时同样按未知结果处理，不以 Docker CLI 超时断言数据库未执行。重启后先检查原迁移进程、数据库活动、历史记录和实际 schema，不能仅因锁释放就重跑。远程执行还受 [应用部署与运维设计·首次安装、正常发布和中断核对](09-应用部署与运维设计.md#releases) 的主机操作锁约束。

## 2. 兼容变更与多版本运行

1. **构建时验证**：将迁移封装进同版镜像/制品；从空库及上一受支持版本库分别升级，检查 RLS、约束、权限和数据结果。记录目标 revision、历史脚本摘要、应用可支持的 schema 范围。示例数据也必须包含两个租户。
2. **发布前检查**：比对实际版本、迁移历史与制品校验值；检查待执行 SQL、锁等待、磁盘、备份及已验证的恢复路径。Flyway 校验失败不能自动 repair；Alembic revision 文件另记录 SHA-256，与历次已部署清单比对，不能只检查 revision ID。失败/中断不得清空最后成功部署的摘要；已执行文件删除同样拒绝。
3. **执行扩展迁移**：加表/可空列/兼容索引等，保持旧应用可运行；记录每步开始、结束、版本和结果。迁移失败即停止该次发布，不继续替换应用。
4. **必要的数据回填**：使用独立可续跑任务，保存版本、tenant_id、主键游标和批次结果。每批短事务、幂等写入，断点与数据同事务提交；不能用一笔大事务把全库更新和发布绑定。若新应用依赖回填完成，发布必须等待完成并校验，否则新应用保留兼容读法。
5. **分批更新应用**：新旧版本兼容共存，检查读写和业务烟测；应用 readiness 对不支持的 schema 明确失败。新列上线后不立即删旧列。
6. **后续版本收缩**：只有旧应用/旧 Worker 已退出、旧检查点可处理、回滚窗口关闭且数据校验通过，才在独立发行中删旧列/旧索引或收紧约束；在发行清单明确标为不可直接回退至哪些版本。

历史已执行脚本不可改写，新增修复脚本向前修复；禁止在生产默认使用 Flyway clean、自动 baseline、ORM 自动建表或 Alembic 自动生成并直接执行。已有系统首次纳管必须先比对真实 schema 并审查 baseline，不能把未知数据库直接标为最新。[Flyway validate](https://documentation.red-gate.com/flyway/reference/commands/validate) 校验 SQL 历史摘要；[Alembic autogenerate](https://alembic.sqlalchemy.org/en/latest/autogenerate.html) 的候选迁移仍需人工检查，不能替代迁移设计。

DDL 默认设置 `lock_timeout=5s`、`statement_timeout=5min`，回填单批默认 30s；更大表的索引等操作必须在发行配置中给出独立超时和验证过的维护窗口。锁超时视为失败，不无限等待。不能在事务内执行的操作必须单独声明，使用对应迁移工具的非事务入口；失败后检查残留对象，再决定向前修复，不能宣称整个迁移已经自动撤销。

## 3. 回退窗口、发布责任与收缩门槛

回退窗口不是全框架一个固定小时数。每次发行由项目发布负责人提出，业务负责人/数据负责人确认；输入写入 deploy/release.yaml，成功时间和期限写入管理机的 `<operation_id>-deployment.json`。这份部署结果凭据区别于发布输入 deploy/release.yaml：

- rollback_window_hours：正数，必填；从本次发布全部实例验收成功时起算。没有填写不得宣称支持自动/受控应用回退。
- rollback_deadline：成功后计算的 UTC 时间；发布部分失败时仍保留原兼容版本，不因计划时间到达自动收缩。
- compatible_previous_versions：可回退镜像与配置版本，须经过目标 schema、所选消息版本验证。
- contract_not_before：允许考虑破坏性收缩的最早时间，不早于 rollback_deadline。
- owner 与 approval_reference：负责人及该发行确认记录；不是新增审批平台。

全部目标主机烟测成功后才生成部署凭据，并原子更新同一项目/环境的 latest-deployment.json；失败不更新当前成功记录，保留操作锁。回退在同一管理锁内核对当前发行号、项目/环境、未过期窗口、当前发行允许的旧发行 ID、目标清单的 compatible_schema_from 及空迁移列表；另需操作人确认授权影响。窗口外停止，不自动延期或执行 schema downgrade。回退成功也记录为一次独立发行。contract_not_before 默认等于窗口截止时间，仅是最早门槛，不自动执行收缩。

缩短已批准窗口必须重新评估并记录确认，脚本不能替用户决定。窗口到期只是必要条件：还须无旧实例/消费者/检查点依赖、回填完成、数据一致、备份可恢复，才在独立发行执行 contract。数据库物理恢复的保留期与 RPO/RTO 独立管理，不等于应用回退窗口，也不是自动 downgrade。

部分失败的应用恢复不要求失败发行先成为“成功版本”。以执行中尝试的 schema 来源、双向兼容声明、实际范围和之前成功基线判断：恢复镜像须对应已记录的成功实例，覆盖本次可能更新的所有主机/服务，回退清单 migrations 为空。恢复窗口由失败发行开始时间及其明确的时长计算；恢复失败再次接续时保留同一 schema 来源和原期限，不能借新 operation_id 自动延期。新加服务没有旧实例基线时自动恢复检查拒绝，由运维先核对移除/保留，不能伪造成功记录。数据库不降级；无成功基线的首次安装失败使用修正配置后的显式续发。

## 4. 字段调整的完整示例

文档项目将 `title` 更名为 `display_name` 时，不能直接在首个上线版本 rename/drop：

- 版本 A：增加可空 `display_name`，保持 title 为混跑期权威字段；迁移增加临时同步触发器，把 title 的新写入同步到新列，新代码也同时写两个字段。按主键分批回填空的新列，使用原子 SQL 从同一行 title 赋值，避免先读后写覆盖并发更新。
- 版本 B：确认所有旧实例退出、回填完整且两列一致后，切换读取新列；在回滚窗口内继续同步写旧列，保留上一版本可运行的条件。
- 版本 C：关闭向旧版回退后，删除同步触发器与旧列。此时回退检查拒绝仍需要 title 的镜像。

触发器是这个重命名迁移的临时兼容手段，不是所有字段变更必须采用的通用架构。单纯新增可选字段不需要复制这套复杂度。迁移风险由实际 SQL 和数据量决定，版本号本身不能证明安全。

## 5. 存量数据接入与 RLS 切换

新项目从首张租户表开始启用 tenant_id 与 RLS。下面仅适用于已有系统迁入，不允许拿“需要回填”作为新系统不隔离的理由。

1. 项目数据负责人确认每条旧数据的租户和账号映射，生成可审阅映射版本；无法确定归属的记录进入隔离清单，停止切换，不分配一个公共默认租户。
2. 保留已演练恢复点，准备旧应用兼容条件；迁移期关闭旧应用对受影响表的业务读写，或以已验证的兼容代码强制隔离访问。不能在回填期间让无租户过滤的旧实例继续服务混合数据。
3. 迁移账号增加过渡列与索引，按已批准映射批次回填，持久化游标并校验数量/归属；普通 runtime 不得到维护权限。新写入必须来自已具备明确 tenant_id 的兼容代码，否则保持维护窗口。
4. 校验所有记录、复合外键与唯一约束，处理错误后设置 NOT NULL；建立租户策略并启用 RLS/FORCE RLS，校验 owner/migrator/runtime 权限分离。
5. 用真实 runtime 账号执行缺上下文拒绝、跨租户拒绝、连接复用、缓存和文件访问测试，再恢复新应用流量。
6. 旧应用不支持租户隔离时禁止直接回退旧应用接库；需要恢复时走隔离恢复与数据核对。不能通过关闭 RLS 把迁移判为成功。

实际映射、维护时段和数据量属于项目迁移输入，必须在该项目实施计划填写；不得把框架示例当自动迁移所有历史账号的工具。

## 6. 迁移失败、备份恢复与数据库引擎升级

| 情况 | 发布状态与处理 |
| --- | --- |
| 事务型迁移失败 | 回滚当前事务，记录失败并停止；已成功的先前迁移保留，检查后按工具历史继续 |
| 非事务 DDL 或回填中断 | 标记待核对；检查残留索引、历史版本、回填断点和实际数据，修复后继续，不能直接忽略错误 |
| schema 扩展成功，应用发布失败 | 保留扩展后的库；允许回到清单中已验证兼容的旧镜像/配置，不执行数据库 downgrade |
| 收缩迁移后想回退旧应用 | 拒绝普通回退；走单独的修复发行或经批准的数据恢复，不自动 DROP/恢复整库 |
| 数据损坏、误删除 | 停止受影响写入，在隔离实例恢复并核对；明确丢失窗口、切换方案和补偿责任后再切生产 |
| 部署执行器中断 | 操作记录标记待核对，核查目标主机与迁移事实；禁止自动把未知状态标成失败后再执行一遍 |

生产基线采用 pgBackRest 执行 PostgreSQL 基础备份 + 持续 WAL 归档到独立存储，不自研备份引擎。infra/postgres 中的 PG 运行环境包含固定版本的归档工具；定时备份由主机调度调用，不依赖发布操作是否正在执行。仅有容器卷和同机备份不满足基线。对象存储、签名密钥、必要配置和发布记录也纳入恢复清单。项目必须在首次生产发布前填明可接受的数据丢失时间 RPO、恢复时间 RTO、备份保留期和责任人；测试环境实际演练后记录达到的数值，不把期望写成已达成 SLA。每月至少一次隔离恢复演练，备份策略改变后重做；发布前核查最近成功备份、WAL 连续性与恢复演练记录。[PostgreSQL PITR](https://www.postgresql.org/docs/17/continuous-archiving.html)、[pgBackRest 指南](https://pgbackrest.org/user-guide.html)

恢复后的 Outbox、Inbox 与业务外部副作用记录可能早于外部系统已经发生的动作。隔离恢复默认禁用消息投递、消费者和外部工具；核对事件/业务幂等键及外部副作用后再恢复流量，不能将“数据库能启动”当作业务恢复完成。基础备份/PITR 的恢复单位是数据库集群，多个服务共用实例时必须核算一起恢复的影响；优先恢复到隔离实例，再决定服务数据提取或整体切换。

PostgreSQL 17 升 18 属于数据库引擎升级，单列维护任务：扩展兼容、磁盘、版本配套、备份恢复、`pg_upgrade --check`/完整演练、停写及切换窗口。Flyway/Alembic 处理 schema，不负责引擎升级；不能仅改 Docker 镜像版本挂载旧卷启动。引擎升级、Redis/Rabbit/Nacos 升级不混进普通业务发布。[PostgreSQL pg_upgrade](https://www.postgresql.org/docs/17/pgupgrade.html)

## 7. 框架、身份页面及配置基线升级

开发升级和生产发布是两次不同操作：

1. 在业务项目建立升级分支，确认项目与 vendor 的修改已妥善保存；记录旧 gitlink/镜像/配置。读取目标版本兼容与迁移说明。
2. 将 submodule 切换到明确目标提交；不跟随 main，不运行重置/清理用户修改的命令。更新业务 POM 父版本与 SDK 版本约束，重锁受影响 Python 服务；工具按目标源码锁同步。
3. 按发行说明修改必要项目配置和脚手架差异。服务业务文件不重新生成，manage.py 不做自动 merge；框架内部工具因引用变化直接升级，项目定制保留。
4. 完成受影响测试、初始化幂等核对和本地登录/调用/权限验收；将 gitlink、构建配置、必要锁文件和项目改动作为同一次项目提交。
5. 构建新镜像与部署包，再按既有备份→兼容迁移→应用更新→验收流程发布。开发目录升级不会自动触碰运行环境。

回退开发引用不会回退数据库。应用回退必须满足现有 schema/API/安全兼容及回退窗口；否则停下按恢复方案处理。升级不重新创建租户或修改角色，不重新 bootstrap，不覆盖签名密钥。

现有 rc.3 发行项目采用**人工一次性转换清单**，不做通用迁移平台：先提交/备份现有项目；加入固定框架引用、项目聚合和源码 SDK 路径；保留原服务名、包名、权限、audience、PROJECT_CODE、环境资源前缀、卷名与数据库；整理相同工具实现为固定引用；更新锁并构建。确认文件组织转换没有要求新 SQL/schema 后，再做实际应用升级。不得用“新建同名项目 + init --local”替代存量迁移。

旧已发布候选及其历史验收保留。新版本的默认文档只讲源码工作区；旧 package_runtime 入口已删除，部署载荷统一由 tools/build.py 维护。旧项目继续使用原发行，不在没有授权时远程替换任何项目。

| 变更 | 维护者交付 | 项目动作 |
| --- | --- | --- |
| java-sdk/python-sdk | 固定版本、兼容说明、必要 SDK 运行表迁移 | 只更新受影响服务依赖和锁文件、构建/验证；迁移在应用前独立执行 |
| identity/gateway | 镜像、迁移、配置变更与兼容范围 | 备份检查、迁移、逐实例更新、登录/权限/业务烟测 |
| 管理界面 | 与身份 API 同镜像发行 | 更新身份镜像，不重建业务 Web；保留账号/授权，旧页面要求刷新 |
| config/infra/deploy 基线 | 原版到新版差异、兼容说明 | 以原始版本做三方比较，保留项目环境值/秘密；先测试后应用 |
| 业务服务 | 项目镜像、迁移、权限清单 | 新权限人工授权，旧调用方/消息兼容后发布 |
| PG/Redis/Nacos/Rabbit 引擎 | 组件升级说明与演练材料 | 独立维护，不混入普通应用发布 |

基础镜像升级不覆盖项目业务代码或数据库，生成的业务代码 后续按项目维护。框架发布材料不能假设“覆盖整个 deploy”就完成升级，也不能把环境值写回公共默认配置。恢复/回退入口与实际备份属于环境资产，必须验证可用。

结构化日志包含 request_id、trace_id、service/instance、主体/租户与任务标识；凭证、正文和隐藏推理不入默认日志。采集 Micrometer/Prometheus/OpenTelemetry 标准信号，接现有平台；告警覆盖认证依赖、磁盘/WAL/备份、MQ/Outbox、证书和发布失败。容量/RPO/RTO 需真实环境证明，源码结构不等于性能结论。

## 8. 项目升级操作清单

| 阶段 | 输入/动作 | 放行条件 | 失败时 |
| --- | --- | --- | --- |
| 评估 | 阅读目标发行说明和兼容矩阵，比较当前 SDK、镜像、迁移、配置基线 | 所有受影响组件及不兼容项列明 | 不直接覆盖项目目录 |
| 合并 | 升级依赖；对框架原始基线、项目现状、新基线做三方比较 | 项目自有代码/配置保留，冲突人工处理 | 停留旧版本并记录冲突 |
| 测试 | 独立测试环境用脱敏备份/代表数据执行迁移与业务回归 | 老数据可读写、权限不变、已选消息兼容 | 修复新迁移或兼容代码，不改已执行历史 |
| 准备 | 冻结发行摘要、检查备份恢复点、准备兼容回退版本 | 回退与恢复途径可说明且已演练 | 不执行生产迁移 |
| 迁移 | 固定入口申请锁、验证历史、执行 expand/回填步骤 | 历史与 schema 一致，失败状态清楚 | 停止发布并核对数据库事实 |
| 发布 | 排空受影响实例、分批切换、实际业务冒烟 | 每批 digest/配置/健康与预期相符 | 停止后续批次，兼容回退或前向修复 |
| 收尾 | 完成后核对全部实例、记录基线与证据 | 不存在未解释的混合版本或积压 | 保留事件记录，不标记完成 |
| 清理 | 在兼容窗口结束后的独立变更执行 contract | 无旧应用/任务依赖且恢复策略已确认 | 推迟删除字段/权限/旧协议 |

升级身份镜像不会重新初始化租户、角色或覆盖管理员授权；升级权限目录不会自动给现有角色增加新权限；升级管理页面不要求业务前端复制源码。业务项目决定何时升级，框架发布不能直接修改所有项目的安装实例。
