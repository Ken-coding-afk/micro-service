## 1. 现状判断与成熟实践

本轮例外（2026-10-28，D-20261028-07）：用户明确要求基础管理后台改造不做旧版本兼容和旧数据迁移。允许直接修订其建库定义，在新建的项目隔离测试库初始化验证；不对已运行旧库repair校验和，不编写回填/转换器。此授权仅适用于本轮后台重整，不代表可以清理其他项目或原26080环境。

结论：每服务维护版本化迁移是合适的，保留 Java Flyway / Python Alembic，不增加第三种引擎，不为统一命令强行把 Python 改成 Flyway，也不依赖手工导出全量 SQL 覆盖环境。

| 当前事实（1473c8e） | 判断与处理 |
| --- | --- |
| identity 的 V1～V10、Java 示例的 SQL、Python 0001 revision 随源码维护 | 保留既有版本与内容；改目录不重编历史 |
| runtime 无 DDL；独立 migrator/owner；迁移在应用前运行 | 保留，多个应用副本不各自启动迁移 |
| scripts/deploy/migrate.py 包含锁、unknown 恢复、工具调用与校验，超过千行 | 收窄公开参数、内部按职责复用；不能以行数为由删除并发和失败保护，不另建迁移服务 |
| run_alembic 每个 heads/upgrade 步骤启动 Python 容器并 pip install | 改为构建期锁定并安装迁移依赖；部署时不下载包 |
| Alembic 摘要从本机 migration-state 中读取 | 只覆盖保留该文件的执行机；迁移文件不可变校验要使用可交接的上次部署产物，不能宣传为 Alembic 原生校验 |
| Python env.py 无 target_metadata，模板无 script.py.mako | 目前不能按普通 Alembic 教程直接生成完整 revision；补标准 authoring 模板，默认手写迁移，不强加 ORM |
| DatabaseReadiness 检查受限账号/连接 | 保留，不增加通用 schema 兼容性扫描器；必要的服务级查询由业务决定，结构正确性由迁移校验与升级测试验证 |
| V6 包含已退役委派表，后续业务不使用 | 不改 V6、不直接删迁移文件；是否清理旧表需单独影响核对，不因脚手架整理顺手删真实数据 |

参考实现不是“修改旧建表 SQL 后重跑”。Flyway 用版本和 checksum 追踪已执行变更；FastAPI 官方全栈模板使用 Alembic 编写、审查并执行 revision；JHipster 也采用版本化 changelog（其文档示例使用 Liquibase）。工具不同，但都要处理数据和新旧应用兼容，脚手架无法仅从模型修改推断全部业务意图。

## 2. 迁移所有权、SQL 分类与执行入口

| 材料 | 位置/所有者 | 执行方式 |
| --- | --- | --- |
| identity 表结构及必要固定数据 | services/identity-service/src/main/resources/db/migration | 身份服务维护的 Flyway 链 |
| Java 业务结构 | 对应服务 src/main/resources/db/migration | 该服务的 Flyway 链 |
| Python 业务结构 | 对应服务 migrations/versions；env.py、alembic.ini、script.py.mako 在 migrations | 该服务的 Alembic 链 |
| 数据库/角色、组件配置 | infra 与服务 resources.yaml | 资源初始化，不混进业务 DDL |
| 演示租户、账号、演示业务数据 | 独立显式 local seed 入口 | 不放进每环境都会执行的版本迁移；不覆盖人工密码/角色 |
| 大量数据回填 | 服务按需建立 scripts/backfill_*.py 或对应 Java 工具 | 独立受控任务，非 API 进程隐式执行 |
| 已执行历史 | 数据库 flyway_schema_history 或 alembic_version | 数据库事实；JSON 日志不能代替 |

每个数据库只由一个服务和一套迁移链拥有，Java/Python 不能各自维护同一批表。多个服务可使用同一个 PG 实例但使用独立库和账号。多租户共享表只迁移一次，不按租户重复改表。submodule 服务的迁移随该服务 commit 交付，主项目通过 gitlink 固定版本，不把业务 SQL 复制到根 infra 再维护一份。

runtime 不具有 DDL、owner 成员或 BYPASSRLS 权限。迁移使用独立 migrator，在所需 owner 身份执行；源码中不写真实账号秘密。API/Worker 启动保持运行身份/连接检查；业务可按需使用一条实际查询检查必需对象，不提供全库表/列/约束对照、模型差异或兼容版本推断引擎，不能执行 create_all、ddl-auto=update 或自动 migrate。

开发、CI、部署都复用同一迁移实现；建议公开入口为：
`python scripts/migrate.py --env local --service equipment-service --check` 与 `--apply`。check 不写库、不建资源；apply 先验证再迁移，失败退出非零。Java 资源/迁移目录从服务登记解析，不让普通用户手动填写 owner、库名、Docker 网络等十多个参数。

Python 作者在服务目录用 `uv run alembic -c migrations/alembic.ini revision -m "add equipment status"` 创建草稿；补齐 tool/dev 锁依赖和 script.py.mako。生成 revision 本身不应连接生产库。默认不提供自动模型差异，因为当前示例使用 SQL/Repository；项目选择 ORM 后才能显式设置 target_metadata，并审查 autogenerate 输出。删除 ORM 类不等于批准删表。

## 3. 版本与历史不可变

应用版本（如 0.4.0）和数据库迁移版本是两个概念。一次应用发布可以没有 SQL，也可以包含多个版本；运行部署记录把源码、镜像和目标迁移连接起来，不要求 migration 号等于应用版本号。

Java 新迁移采用 `V<递增整数>__<英文动作>.sql`，沿用已有 V1～V10；新服务可从 V1 开始。冲突在合并前处理：尚未进入共享环境的迁移可改成下一个号，已在共享/测试/生产执行的不能改号或内容。默认 outOfOrder=false，顺序和校验用 Flyway 官方 info/validate/migrate，不自己按字符串排序 V2/V10。repeatable 不用于演示数据或表结构增删；有视图等需求再按工具原生方式明确使用。

Python 用 Alembic 官方 revision 图；允许在开发分支出现分叉，发行前用经过审查的 merge revision 收敛为单一 head。禁止通过修改已部署 down_revision、删除旧 revision 或 stamp head 掩盖分叉/缺失。revision ID 不是时间或大小顺序，不自写排序器。

一旦脚本进入共享环境，就保持不可变；发现错误写新迁移向前修复。空库安装从同一条历史执行到目标版本，不同时维护 init.sql 和另一套升级 SQL。SQL 基线压缩/归档不在本轮；没有真实项目和升级边界证据，不删除历史“瘦身”。

Flyway 自带历史 checksum；Alembic 默认不提供等价的逐文件历史 checksum。Python 的补充校验读取上次成功迁移归档中的 revision→SHA-256，只比较**数据库已应用 revision 的祖先集合**，不能把尚未执行的 revision 当成已发布历史。归档与发布包一起保存在项目制品/受控运维目录，换执行机必须带回；本地缓存只是副本。数据库非空但没有可信旧摘要时进入人工纳管核对，不能从当前源码生成一份摘要就声称历史未改过。空库第一次可直接建立基线。

修复命令的边界：不自动 clean、repair、baseline 或 stamp；repair 只修正历史元数据，不替人修复业务表或恢复数据。确需操作时先定位对象、比对记录并保留批准证据，不作为常规启动/升级步骤。[Flyway repair](https://documentation.red-gate.com/flyway/reference/commands/repair)

## 4. 字段和表变更如何选择方式

不是所有变更都需要多次发布。每次先选择**维护窗口**或**兼容并行**，记录影响、旧应用是否需要运行/回退及数据处置；不能为了简化流程把在线破坏性 DDL 当成普通新增。

两条发布路径均先拉取并验证新应用/迁移镜像、配置与备份材料。兼容路径允许旧应用运行时迁移，再更新应用；维护窗口路径必须先摘除受影响入口、停止旧应用及相关消费/定时/外部写入者并确认停止，再执行迁移、启动新版本和验收，最后恢复流量。项目在发布说明列出框架外写入者的停止/恢复命令。迁移失败不放流量、不启动新应用，也不自动 schema 回退；保留维护状态，按失败核对处理。不能把“预留维护窗口”代替实际停止步骤。

| 变更 | 常规方式 | 必查项 |
| --- | --- | --- |
| 新增可空列/新表 | 新迁移添加，旧代码继续运行；新表同时配置 RLS/索引/受限权限 | 旧 SQL 不用无列名 INSERT；锁时间、默认值成本 |
| 新增非空列 | 先可空/有合适默认值；回填、验证无 NULL，再加 NOT NULL | 新写入同步填值，旧实例是否仍能写入 |
| 放宽长度/类型 | 根据 PG 实际转换成本决定直接 ALTER 或新列迁移 | 不假设所有“扩大类型”都无锁、无重写 |
| 缩短长度/类型转换 | 先验证数据可转换；复杂转换新列+回填+切换 | 超长/非法值处理由业务定义，不能静默截断 |
| 重命名字段/表 | 全部相关应用停机时可直接 RENAME；需混跑时新增兼容结构后切换 | 旧 SQL、索引/视图、消费者/报表和回退范围 |
| 删除字段 | 先代码不再读写，再独立迁移 DROP COLUMN | 数据保留/归档、旧实例已退出、旧版不能再回退 |
| 删除表 | 先停止所有读写/任务，确认外部依赖，必要时归档，再 DROP TABLE | 不默认 CASCADE；外键/视图/定时任务/报表明确处理 |
| 新增唯一约束/外键 | 先查重复/孤儿数据并修复，再添加/验证约束 | 大表锁；多租户唯一性通常包含 tenant_id |
| 新增大表索引 | 评估普通 CREATE INDEX 或 CONCURRENTLY | 后者不可在普通事务块中执行，失败可能留下无效索引 |

默认 DDL 设置 lock_timeout=5s、statement_timeout=5min，超时停止，不无限等待；项目可针对已测量的大操作显式覆盖。阈值不是容量保证。PG 支持许多事务性 DDL，但不能据此把跨步骤/非事务迁移视为原子操作。[PG ALTER TABLE](https://www.postgresql.org/docs/17/sql-altertable.html)、[PG CREATE INDEX](https://www.postgresql.org/docs/17/sql-createindex.html)

迁移文件中直接出现 DROP 不等于一律禁止，关键是已审查的数据损失与兼容结果；也不靠正则扫描承诺拦住所有危险 SQL。工具保留发布前检查，项目代码评审负责 SQL 语义和业务依赖。

## 5. 增删改字段、删表的具体例子

下面的 equipment、equipment_event 是讲解模型，不是要求给框架新增设备业务。

**增加状态字段：**

1. V2 增加可空 status，旧代码继续工作。
2. 新代码为新记录写 status，读取旧 NULL 时使用业务确认的默认含义。
3. 小表可在受控迁移中短事务回填；大表独立分批回填。
4. V3 在校验无 NULL、旧写入者已退出后增加 NOT NULL。不能只给列加 DEFAULT 就认为旧行已经按业务含义全部补齐。

**将 name 改为 display_name：**

维护窗口方式：停相关写入与旧进程，备份/演练后执行 RENAME COLUMN，启动配套新应用，验证后恢复流量。旧应用不能未经验证直接回退。

兼容并行方式：A 版本新增列，name 暂为权威写入源，必要时使用短期触发器捕获仍存活旧实例的写入；分批原子回填并检查一致。B 版本在旧实例退出后切换读取，回退窗口内维持旧字段兼容。C 版本在回退窗口结束且依赖清零后删除旧字段和临时同步。不能只让新代码双写，却漏掉旧进程的写入。临时双写/触发器仅用于需要它的变更，不建全项目同步框架。

**删除 obsolete_code 字段：**

A 版本删除代码对它的读写但保留列；确认旧程序、任务和报表无依赖，数据保留要求已满足后，B 的新迁移执行 DROP COLUMN。不删除最初创建该列的 V 文件。重建同名列只得到空列，不恢复旧数据。

**删除 equipment_event 表：**

停止写入入口、消费/定时任务与查询依赖 → 核对外键/视图/外部报表 → 视数据要求归档并验证可读 → 明确旧版应用不再允许回退 → 新迁移 DROP TABLE（默认 RESTRICT）→ 验证剩余业务。不要默认 DROP CASCADE 自动删掉所有依赖。数据库已存在表时也不能通过删实体类或删 V1 文件完成这一过程。

## 6. 数据回填、事务和并发

普通小量静态数据修复可随迁移执行；大批量回填与 DDL 分离，不在启动事务里循环更新全库。业务服务负责自己的回填脚本，不建设框架级任务平台。

回填要求：确定来源权威、tenant_id/主键分批、写入条件明确（如新列 IS NULL）、每批短事务、可重复执行、输出处理/跳过/失败计数。有检查点时，检查点和本批数据在同事务提交；可通过数据条件本身续跑的无需再建进度表。默认单批超时 30s，批大小由项目基于数据量测量确定。并发更新使用原子 SQL 或版本条件，不能先读旧值再覆盖新写入。

RLS 默认 FORCE，不能假设 owner 自动绕过。迁移/回填使用单独维护连接并设置该批可信 tenant 上下文，按明确租户清单处理；确需全局特权的任务另行批准，不授予 API runtime。回填写权限限定相关表，完成后撤销临时授权。新代码依赖回填完成时，发布前必须校验完成；否则保留兼容读法。

迁移入口继续对目标库持有同一 PG advisory lock，所有脚本/CI/Ansible 走同一入口；锁仅保护遵守该约定的执行者，不是跨系统分布式事务。暂保留现有控制连接与子容器终止逻辑，不在本轮换锁算法。控制连接丢失、超时或进程被杀必须停止后续步骤，核对仍存活的执行容器/数据库会话后恢复；不得假设控制锁释放等于 DDL 已停止。

非事务操作独立迁移：Flyway 使用相应脚本配置，Alembic 使用官方 autocommit_block；不能把前面已提交的操作标成全部回滚。需要 CONCURRENTLY 时同时核对 Flyway PostgreSQL 锁方式及固定版本支持，在隔离 PG 验证，不凭 SQL 语法正确宣称可发布。

## 7. 应用回退、破坏性变更与恢复门槛

应用镜像回退、schema 向前修复、备份恢复是三件事。默认发布脚本不执行 Alembic downgrade 或 Flyway undo；Python 可以在隔离开发库测试作者明确写出的可逆 downgrade，但必须拒绝把 DROP 后 CREATE 当作数据恢复。

项目发布说明记录：所选服务/源码与镜像、目标迁移、是否破坏性、兼容的旧应用版本、负责人、维护窗口、备份恢复引用和回退截止条件。简单新增字段可写“无需停机、兼容旧版”，不要求为每个开发实验写审批编号。生产破坏性操作必须有明确数据处置与责任记录。

旧 release.yaml 与操作锁的执行校验在新发布入口通过验收前不能绕过；新入口从同一发布说明/构建记录自动生成所需字段，不要求人重复写两套摘要。没有批准并验证的兼容旧版，就应明确“只前向修复/备份恢复”，不能让用户随意填写一个版本宣称支持回退。

contract 删除动作独立发行；允许执行的最早时间必须晚于项目承诺的回退窗口，且旧应用/任务/消费者已退出、回填完成、依赖清零、保留和恢复要求满足。窗口到期不触发自动删表。默认维护窗口不免除这些检查，但已确认不需要旧版兼容的小项目可以一次停机变更，不强制三次上线。

## 8. 失败核对、备份与引擎升级

| 情况 | 处理 |
| --- | --- |
| 已知事务失败且已回滚 | 核对工具历史与实际对象；未发布新脚本可修正，已发布脚本用新的修复方式 |
| 非事务步骤失败 | 检查已提交变更/无效索引，清理或前向修复后再执行；不能自动 repair 消除证据 |
| 执行机断连、超时、running 遗留 | 标结果待核对，检查旧进程、数据库活动、历史和实际表结构；显式确认后恢复 |
| 应用更新失败、schema 已扩展 | 用已验证兼容的旧应用恢复，保留新 schema；不自动数据库降级 |
| 误删列/表 | 停止相关写入，评估备份/PITR；优先恢复到隔离实例，再提取数据或整体切换 |
| 有历史库但无迁移链/摘要 | 人工纳管、比对 schema 与历史来源；不可默认 baseline/stamp 到最新 |

备份复用托管 PG 能力或成熟工具（如 pgBackRest），不自写备份引擎，也不在脚手架源码改造中强制搭建完整备份平台。生产项目必须确定 RPO/RTO、备份保留期、责任人和恢复演练；只有同机卷不等于备份。PITR 恢复整个集群时可能影响同实例其他服务，先隔离恢复再决定切换，不能默认覆盖线上集群。

恢复后的业务消息/外部动作可能已经发生，隔离环境禁用消息消费和外部副作用，核对幂等记录后再放流量。恢复成功的判断包含数据和权限，不只是 PG 可以启动。[PG PITR](https://www.postgresql.org/docs/17/continuous-archiving.html)

PG 大版本升级与 Flyway/Alembic schema 迁移分开；按扩展兼容、备份、pg_upgrade/导出恢复演练和维护窗口处理，不能只改镜像 tag 挂旧卷。[PG pg_upgrade](https://www.postgresql.org/docs/17/pgupgrade.html)

## 9. 存量租户数据接入

新项目租户表从第一份迁移就带 tenant_id、索引、权限与 RLS。已有系统接入：确认旧数据租户映射 → 加可空列与兼容写入 → 分批回填/核对未知归属 → 收紧约束与索引 → 配置 runtime/RLS → 验证双租户、无上下文拒绝 → 切换应用。不为未知数据指定一个“公共租户”逃避归属判断。模式变更和数据归属需要项目单独确认，本轮不自动操作真实旧库。

## 10. 脚手架源码、服务 submodule 与 SQL 升级

根项目公共模块及初始两个业务直接拥有源码；后续业务按用户决定通过固定 submodule 提交引入，源码接入规则见[脚手架升级](11-源码脚手架交付与开发体验设计.md#upgrade)。

升级步骤：在项目升级分支合并所需公共源码补丁/更新选定服务 gitlink → 检查依赖和迁移差异 → 验证空库安装与上一支持版本的有数据升级 → 提交根项目与必要的服务提交 → 构建同版应用/迁移产物 → 备份核对/迁移/应用发布/业务验收。代码 checkout 不会改变数据库。

项目自己的 identity 已加 V11，而上游也发布 V11 时不能覆盖或改写已执行项目脚本：检查上游实际变化，将尚未应用于本项目的修复合并为项目下一个版本，并验证新代码兼容；记录来源补丁及项目迁移号。Python revision 冲突同理用官方图处理。这是源码分叉的真实成本，不承诺升级一个版本号自动完成。

已有 vendor 项目转换保持迁移历史、client ID、库/卷名和数据；只换源码组织不执行 clean/baseline，不把存量数据库当新项目安装。SDK 自身不在 runtime 隐式建表，可选 SDK 功能需要的表作为所属业务链中的明确迁移。

<a id="project-upgrade"></a>

## 11. 最低验证与交付要求

每次改 SQL 至少验证：空库安装到目标版本、上一支持版本带代表数据升级、再次执行不重复、历史文件篡改/缺失拒绝、runtime 无 DDL、双租户隔离。复杂变更增加专属场景：

- 加 NOT NULL：旧 NULL/新写入同时存在时的回填与约束结果。
- 改名/改类型：旧代码兼容（若承诺）、异常值处理、并发写入不被覆盖。
- 删列/删表：只删除目标，保留数据不损坏；旧版本拒绝回退；恢复演练能取回代表数据。
- 大回填：中断续跑、重复批次、跨租户与并发更新。
- 非事务索引：失败后的无效对象核对，不能伪报全回滚。
- Alembic：revision 模板可用、多 head 拒绝、换执行机携带旧摘要仍识别篡改、缺摘要不能假装通过。
- 发布：迁移失败不更新应用，单服务更新不执行其他库迁移。

上述属于必要场景，不要求每次跑全部数据库测试。真实 PG 验证必须在用户恢复 Docker 或提供隔离数据库后执行；本次只编写方案和静态文档核对，不把工具替身测试当作 DDL 证据。
