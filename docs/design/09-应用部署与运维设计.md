## 1. 部署拓扑、主机清单与发布输入

部署清单位于 config/environments/test|prod/hosts.yaml，列明 infra、app、ai、edge 角色及主机固定地址。同一主机可以承担多个角色；这是部署位置，不是新增框架服务。生产以 Linux Docker 主机为基线，使用唯一授权的 Linux/WSL Ansible 管理机。

| 示例主机 | 运行内容 | 谁维护 |
| --- | --- | --- |
| infra，10.20.0.10 | PG、Redis、Nacos、Rabbit；持久数据与备份工具 | infra 配置及独立维护任务 |
| app，10.20.0.11 | identity、gateway、Java 业务、Nginx 与可选静态页面 | deploy 中选中应用 |
| ai，10.20.0.12 | Python API/Worker，可连接 GPU/外部模型 | deploy 中同镜像不同角色 |

跨主机连接使用私网 IP/DNS 和固定映射端口，不使用另一机器的 Compose 别名。SERVICE_ADVERTISE_HOST/PORT 是真实消费端可达地址；服务端口、Nacos 客户端连接端口及锁定版本要求的附加端口都进入防火墙清单。PG/Nacos/Rabbit/Redis/Actuator 不公开；宿主机 Docker 端口发布后必须从外部实际验证访问边界。

生产前检查 NTP、磁盘/卷权限、DNS/TLS、镜像仓库拉取、资源上限、日志轮转、秘密权限、备份目的地与告警责任人。缺项不以“容器能启动”通过。开发数据和账号不得随镜像进入生产。当前单组件实例拓扑允许有维护中断，不能据应用副本数承诺全链路 HA。

<a id="first-install"></a>

## 2. 首次安装的统一顺序与停止条件

这是本地与服务器安装顺序的权威定义；操作指南只展开命令和排错。依赖描述的是必要先后关系，不要求所有不同数据库的迁移机械串行。

| 顺序 | 执行者与输入 | 必须完成后才允许下一相关步骤 |
| --- | --- | --- |
| 1. 校验环境 | 固定入口读取所选组合、环境绑定和秘密引用；local prepare-local 准备外部网络及未存在秘密 | PROJECT_CODE/APP_ENV/资源归属正确，必需文件可读；服务器不得自动生成替代生产密码 |
| 2. 安装或验证依赖 | infra Compose / infra.yaml | 自建组件健康，外部组件连接/权限通过；数据卷正确 |
| 3. 创建环境资源 | infra/init 的 resources / initialize.yaml | 数据库、角色、namespace、vhost 等存在且归属正确 |
| 4. 发布配置 | tools/config/publish.py，由 initialize.yaml 调用 | 类型/来源检查与漂移检查通过，记录每 Data ID 摘要 |
| 5. 迁移所选数据库 | migrate.py 调用官方 Flyway/Alembic；服务器 migrate.yaml | 身份库及所选业务库迁移成功 |
| 6. 身份 bootstrap | identity-bootstrap | 平台初始账号、管理客户端和目录发布身份就绪；已有资源只核对 |
| 7. 启动基础应用 | identity-service、api-gateway、nginx | schema/配置兼容，实际 ready，管理页和登录可用 |
| 8. 发布业务权限 | sync_permissions.py / deploy.yaml 中对应步骤 | 身份 API 已 ready；仅同步服务权限目录；audience 由平台管理员登记 |
| 9. 登记项目身份数据 | 管理员通过管理页/等价 API 创建租户、用户、角色及业务客户端，配置受控秘密 | 对所选应用进行客户端登记、audience/scopes/秘密匹配检查；普通用户已有明确授权 |
| 10. 启动业务与冒烟 | 所选 API/Worker、业务静态页面 | 经公开入口走真实登录、允许/拒绝请求及项目业务链路 |

各库迁移不依赖尚未启动的身份 HTTP API，因此可以在步骤 5 统一执行；不能把客户端/权限同步混进数据库迁移。启动业务之前所有必需迁移与客户端检查必须完成。迁移失败立即停止；配置批次或初始化部分成功保留逐项结果，禁止自动清库回滚。

服务器四个入口的职责为：infra.yaml 处理步骤 2；initialize.yaml 处理步骤 1/3/4 的服务器适用动作；migrate.yaml 处理步骤 5；deploy.yaml 处理步骤 6—10。首次步骤 9 未完成时，app_services 先只选择基础服务；管理员完成登记、秘密交付后，再选择业务服务执行下一次 deploy。缺失认证材料或 readiness 失败时停止所选批次，不自动生成业务客户端。正常升级已登记时无需重复人工操作。

普通应用发布只执行受影响迁移、兼容检查和应用替换，不重跑组件安装。新增服务先增量初始化资源，再执行该服务的上述步骤；重复初始化不覆盖已有密码或管理员授权。

<a id="execution-entrypoints"></a>

## 3. 固定入口、Compose 名称与参数

入口是固定适配器，不是通用命令平台。源码项目在项目根运行 manage.py，工具实现来自固定 vendor；配置、环境文件和输出路径相对于业务项目根。部署包在包根执行随包工具。既有 dev.ps1/dev.sh 是维护工具，不要求复制到新项目。

| 入口 | 固定参数/含义 | 结果与限制 |
| --- | --- | --- |
| tools/infra/up.py | --env-file、可选 --compose-file、重复 --service；仅启动环境中选中的 self_hosted 组件 | external 不安装；profile 显式启用 |
| tools/infra/init.py | --env-file；--phase=prepare-local/resources | 前者仅 local；后者按 infra/resources.yaml create/verify；不迁移业务表 |
| tools/config/publish.py | --env-file；--source=config/nacos | 校验和发布指定环境，拒绝来源错误/漂移，输出摘要 |
| tools/deploy/sync_permissions.py | --identity-origin、--app-env、--client-id、--secret-file、--manifest（服务 permissions.yaml）、--release-version | 通过 client_credentials 获取发布令牌，读取目录版本后提交一次；冲突/拒绝即停止，不创建客户端、不授予角色、不修改 audience |
| tools/deploy/dev.ps1 | -Service、-Role、-EnvFile、-HostEnvFile | Service 必须在 config/development.yaml；Role 为 api；可用 -Check 只校验 |
| tools/deploy/dev.sh | --service、--role、--env-file、--host-env-file | 与 PowerShell 参数对应；共用 dev.py，--check 只校验 |
| tools/deploy/migrate.py | --env-file、--resources、--target（资源 ID）、--tool=flyway/alembic、--migrations-dir、--yes；控制连接/容器连接可显式绑定 | 独占锁、历史校验；迁移文件随制品交付，禁止自动 clean/repair；运行时不加载迁移凭据 |
| Ansible 各 playbook | -i config/environments/test或prod/hosts.yaml | 只处理清单明确的环境/主机，秘密由文件引用；不从命令行传密码 |

dev.py 只启动已登记的 Java JAR 或业务虚拟环境中的 Python console entry；不装依赖、不启动 worker、不继承管理员环境。EnvFile 是该服务运行绑定，不是 infra 管理环境。local-host 仅覆盖所调试服务的连接地址、监听和发布地址、宿主可达名以及已声明秘密文件路径。project/env/namespace、issuer、权限策略和 Nacos 技术参数不允许被该覆盖文件改变；重复键、来源冲突、未知键或与目标服务不符均在启动进程前拒绝。Java 不自动读取 .env，固定入口/IDE 配置负责注入；Python 业务使用自己的 uv 环境，运维工具使用根 uv 环境。

| Compose 名称 | 镜像/入口角色 | 是否常驻 |
| --- | --- | --- |
| identity-service / api-gateway / nginx | 对应基础镜像与公开入口 | 是 |
| identity-bootstrap | 身份镜像 bootstrap 入口 | 否；maintenance profile，仅显式 run |
| 项目登记的 Java / Python 服务 | 由项目源码构建的业务镜像 | 发布时启动；本地开发由 manage.py dev 启动宿主进程 |

混合调试必须保证宿主与容器均能访问 Nacos 中登记的地址。本地初始化在项目 `.local/` 生成 Compose 覆盖及每服务 host 绑定；`manage.py dev` 检查宿主及 Gateway 容器到业务的连通性。基础服务仍在容器。选择私网 IP 时核对路由与防火墙；框架不修改 DNS、hosts 或防火墙，PUBLIC_ORIGIN/issuer 不随业务调试切换。

数据库迁移通过独立工具容器执行，不要求每个服务镜像再实现一套 migrate 命令。Java SQL 使用 Flyway runtime_role 占位符，Python 迁移由入口注入 DATABASE_URL 和 DB_RUNTIME_ROLE；迁移环境不得导入业务应用、SDK 或启动 Nacos。业务运行角色仅取得迁移中显式授予的 DML 权限。

项目应用 Compose 位于 deploy/compose.yaml，业务追加文件位于 deploy/business.compose.yaml（创建与新增服务时生成）；不将业务容器写入框架基础 Compose。RUNTIME_DIR 是绝对目录，各服务使用 <service>.env 与 <service>-secrets/，bootstrap 使用独立文件/秘密目录。基础服务只挂载自己的运行秘密，不能挂载组件管理员或其他业务的秘密目录。Compose 不设固定 container_name，复用项目专属 external network。PUBLIC_ORIGIN 与 Nginx 实际入口一致；local.conf 只用于 local HTTP，不能当作生产 TLS 配置。

项目根 `manage.py build` 从固定源码构建镜像；`build --package-only` 组装正式部署载荷。载荷包含项目 `config/infra/deploy` 声明、固定框架的 `tools/config`、`tools/infra`、`tools/deploy` 执行代码、根工具环境锁、Web 静态文件、各服务迁移和权限清单。`deploy/release.yaml` 固定源码提交、锁文件摘要、镜像 digest、迁移及文件摘要。源码项目通过 gitlink 升级，部署机使用镜像；不再生成供业务开发复制的 JAR/wheel 包，也不维护第二份 framework-baseline。禁止收集 `.local`、秘密、虚拟环境或业务开发源码；打包验证不等于服务器运行验收。具体操作见[开发与升级指南](../guides/04-新项目开发与规范升级指南.md#deployment)。

## 4. 首次安装、正常发布和中断核对

`python manage.py build --release <业务发行号> --output dist/<业务发行号>` 构建本项目明确登记的服务和两个基础服务；可用 `--service <name>` 做局部镜像构建，但局部结果不能冒充完整首次部署包。不自动上传镜像、不自动远程部署。

Java 镜像用 Maven reactor 多阶段构建；身份/网关复用现有 Dockerfile。Python 用项目根为构建上下文，只 COPY 当前服务、固定 SDK 和锁定构建输入；在 Linux 构建阶段冻结同步并非 editable 安装，最终阶段不带 uv 开发工具、测试、JDK 或其他业务源码。构建前独立核验锁文件有效，不能用 frozen 掩盖 metadata 与锁不匹配。根 .dockerignore 排除 .local、所有 .venv/.git、缓存及本地秘密。

部署包只包含：项目 config/infra/deploy 的运行声明、固定版本的必要执行工具及其依赖锁、身份和业务迁移、权限清单、业务 Web 静态文件、release 清单。缺少已声明的 Web 构建产物则构建失败，不悄悄发布空前端。框架源码、业务源码和 vendor Git 目录不进入服务器部署包；identity-admin 仍在身份镜像中。

复用现有 release 清单，补充项目 commit、框架完整 commit、所选服务、锁文件摘要及身份/业务迁移摘要；不再生成另一份内容重复的 framework-baseline。运行镜像与迁移必须来自同一次固定输入的构建。首次本地验证可记录 Docker image ID；远程镜像拉取使用实际 push 后的 repository@sha256。生成阶段不伪造仓库 digest。

已有 Ansible 路径约定在部署包内保持，使运维仍能执行 initialize/migrate/deploy/reconcile/rollback。正式部署前需要运维填好主机、域名/TLS、真实秘密、镜像来源、备份和恢复信息；不会承诺从项目名自动推导生产环境。

本地开发构建使用 image ID/本地 tag 和 Compose。正式单机及多机统一使用团队认可的镜像仓库、repository@sha256 和现有 Ansible 拉取校验；不新增服务器预载/离线发布模式。镜像仓库账号与上传由项目运维管理，构建命令不自动推送。Nexus/Maven/PyPI 私有仓库不属于本次必装依赖。

多机沿用现有模型：一个资源初始化/迁移执行点，应用按主机清单启动，Nacos 登记私网可达地址；Docker bridge DNS 不跨主机。身份 ready 后再更新依赖内省的服务；迁移失败不发布。保留维护窗口，不把 serial=1 或本地容器模拟称作无损滚动发布。

| 动作 | 固定入口 | 运行什么 | 明确不做什么 |
| --- | --- | --- | --- |
| 首次依赖安装 | tools/deploy/ansible/infra.yaml | 调用 infra 配置，在指定依赖主机启动所选组件或检查外部实例 | 不启动业务，不改已有密码 |
| 资源初始化/增量新增服务 | tools/deploy/ansible/initialize.yaml | 调用 infra/init；随后发布 config/nacos；记录资源归属 | 不代替 Flyway/Alembic，不清空数据 |
| 应用首次部署 | migrate.yaml → deploy.yaml | 按[基础设施与环境设计·依赖清单与启用条件](03-基础设施与环境设计.md#dependencies)及[首次安装顺序](09-应用部署与运维设计.md#first-install)执行迁移、身份 bootstrap/就绪、客户端/权限同步、业务启动与入口验证 | 不假定权限 API 在身份启动前可用 |
| 普通应用发布 | migrate.yaml（确有迁移时）→ deploy.yaml | 固定 digest、配置兼容检查、受影响实例逐机更新与烟测 | 不启动 infra.yaml、不重建依赖、不 down 整个项目 |
| 基础设施升级 | infra.yaml 的明确维护范围 | 独立备份/兼容验证和维护窗口，仅更新指定组件 | 不在发布业务时顺带升 PG/Redis/Nacos |
| 应用兼容回退 | rollback.yaml | 检查 schema/消息与授权行为兼容，恢复已验证镜像与配置 | 不执行数据库 downgrade |
| 中断核对 | reconcile.yaml | 核对远程进程、镜像、配置和迁移事实后决定续跑 | 不自动重做未知写入 |

Ansible 只串起已有固定操作，不拥有数据库实例参数、业务 SQL 或应用运行参数。infra/init 与 config/publish 是同一份本地/服务器实现，Ansible 调用它们，不维护第二套初始化逻辑。目标文件路径来自发行清单的受限声明，不提供任意远程 shell 输入。

deploy/release.yaml 记录 project、environment、id、compose_files、images、files（相对路径→SHA-256）、有序 migrations（target/tool/path）和 compatible_schema_from，并填写[回退窗口与责任字段](10-数据库迁移与升级设计.md#rollback-window)。主机角色、app_services、infra_services、秘密文件路径、烟测 URL 和维护窗口在 hosts.yaml 声明；两者不重复维护同一字段。verify_release.py 拒绝摘要变化、越界路径、未登记迁移、可变镜像、构建指令与缺少健康检查；执行端清单须与管理机逐字节一致。构建在开发/构建环境完成，生产拉取测试通过的同一制品。框架源码版本由 gitlink 固定，项目 release.yaml 统一记录部署镜像、文件和兼容审核结果；不再生成用于新项目开发的第二份框架发行清单。

发布前先拉取镜像和检查备份；迁移是独立单目标步骤，不能在分批 play 中错误使用 run_once 导致每批都迁移。当前入口要求维护窗口：每批先拉取所选镜像，再优雅停止选定容器（30 秒）→ 替换 → readiness（最多 180 秒）→ 下一批；全部所选实例成功后再从管理机做有效 TLS 的入口烟测。服务生命周期负责注销/停止接收；主动调整外部负载均衡器与无损排空不由这组 playbook 自动完成。第二台失败停止后续批次，保留每台实际版本。单副本需要维护窗口，不能承诺无停机。

每项目/环境在唯一管理机和目标主机分别持操作锁，证书更新也使用入口锁。管理进程中断先核对实际远程进程与结果，不能因超时抢锁重复写入；迁移另有数据库锁。管理机切换先撤销旧执行凭证并核实原任务。记录 operation_id、目标范围、原/目标版本、逐主机结果和脱敏日志，归档到受控存储；不新增发布数据库/页面/调度服务。

修改 Nacos 参数只发布选中 Data ID 并按字段规则生效；修改业务镜像只发布该业务；改变数据库实例版本使用基础设施维护。发布入口不以整个 Compose down/up 作为更新策略，不删除卷。基础设施启动和应用发布共享环境标识，但不共享“全部重建”动作。

执行方式（从部署包根目录、Linux/WSL 管理机；真实多机验收状态另见实施计划）：

```bash
ansible-playbook -i config/environments/test/hosts.yaml tools/deploy/ansible/infra.yaml -e operation_id=sample-001-infra
ansible-playbook -i config/environments/test/hosts.yaml tools/deploy/ansible/initialize.yaml -e operation_id=sample-001-initialize
ansible-playbook -i config/environments/test/hosts.yaml tools/deploy/ansible/migrate.yaml -e operation_id=sample-001-migrate
ansible-playbook -i config/environments/test/hosts.yaml tools/deploy/ansible/deploy.yaml -e operation_id=sample-001-deploy
```

首次部署的 migrate.yaml 按依赖迁移所选数据库（身份库先于需要其合同的应用步骤）；它不发布权限或启动常驻服务。deploy.yaml 对明确选中的应用按身份、网关、业务、入口排序；bootstrap_identity 仅在选中身份服务的初始维护阶段启用。新环境分两次选择范围：先基础服务可用，再完成客户端登记和运行秘密，最后同步权限并启动业务；不能用自动创建高权限客户端绕过。migrate.yaml 全部成功后生成与发行清单摘要绑定的凭据；包含迁移的 deploy 必须核对该凭据。正常升级已具备登记时无需重复人工配置。

各环境实际 environment.env 由清单引用，从受控主机文件读取，不通过命令行传密码。首次部署中 identity bootstrap 只在缺少初始资源时执行；资源已经存在则校验，不覆盖。后续发布默认只使用受影响的 migrate/deploy，不重新执行组件安装。最终是否可用以真实域名的认证/业务烟测为准。[Ansible 分批执行](https://docs.ansible.com/projects/ansible/latest/playbook_guide/playbooks_strategies.html)

部署以 inventory 的实际主机/服务映射作为范围，禁止 --limit 绕过控制阶段。所有主机先预检；实例更新只要求自己的 readiness，不要求尚未部署的入口已可达。所有所选实例完成后，控制机才统一检查 HTTPS 公开入口并写成功记录。首次基础部署可在 app01 启动身份/网关，在 app02 启动 Nginx；登记业务身份后才把两个业务服务加入下一次发布范围。

在变更任何实例前记录 operation-attempt（实际 targets、成功基线、schema 来源、恢复期限）。每台主机另记录开始与 readiness 结果，不能在停止旧容器后就标 ready。成功记录的 images 只含本次所选服务，deployments 按主机累计；失败不会覆盖最后成功记录。未完成尝试必须现场核对，明确 recovery_operation 和 recovery_reviewed 才可接续，且范围覆盖前次可能变更的实例；恢复判定见[回退合同](10-数据库迁移与升级设计.md#rollback-window)。

## 5. Nginx 与 Gateway 的分工和路由

生产默认链路为 `浏览器/外部客户端 → Nginx:443 → api-gateway → identity-service/业务 API`。项目业务 Web 的构建产物可由同一个 Nginx 托管；身份管理资源仍位于 identity-service 镜像，由 Gateway 转发，不能复制到业务 Web。Nginx 是 deploy 中的运行组件，不增加 Java/Python 模块。

生产 Nginx upstream 由环境清单声明 Gateway 的固定私网 IP:映射端口；本地同 external network 使用明确 Gateway 别名。Nginx 不订阅 Nacos；Gateway 再通过 Nacos 选择业务实例。跨宿主机不使用 Compose 服务名或 bridge IP。Gateway 多副本可在 upstream 中列出多个已验活端点；发布摘除某 Gateway 时先更新入口 upstream 并排空连接。默认一个入口节点仍是单点，不以 Gateway 多副本声称入口高可用；项目接入已有负载均衡器时需验证可信代理链和 SSE 行为。

| 外部路径 | 目标与规则 |
| --- | --- |
| `/identity/admin/` 及其子路径 | 原样交给 Gateway → identity-service；由身份服务处理已知页面 fallback，业务 SPA 不接管 |
| `/bff/identity/platform/`、`/bff/identity/tenant/` 及业务 BFF 的固定命名空间 | 原样转发 Gateway 的会话、登录、回调及接口；不缓存，不重写 Cookie 主体边界 |
| `/api/v1/` | 原样转发 Gateway 显式注册的公开 API；不存在的 API 保留 404，不能回退业务 index |
| 业务明确声明的 SSE 路径 | 单独的 SSE location，保持事件流和 Last-Event-ID；不得被普通 API location 覆盖 |
| `/oauth2/authorize`、`/oauth2/token`、`/oauth2/revoke`、`/oauth2/jwks`、`/userinfo`、`/connect/logout`、`/.well-known/openid-configuration`、`/.well-known/oauth-authorization-server` | 经 Gateway 显式路由到身份服务；各端点按 OAuth/OIDC 自身规则处理，不能统一套“先有用户会话”拦住机器换 token |
| `/login`、`/logout`、`/oauth2/authorization/{registrationId}`、`/login/oauth2/code/{registrationId}`、`/identity/external`、`/identity/session` | 身份服务的登录、第三方跳转/回调及已交付账号维护模板；本计划无公开注册；仅放行已登记流程，写请求按适用规则验证 CSRF/state |
| `/oauth2/introspect` | 默认仅私网/VPN 中的已登记资源服务可达并验证其独立凭证；公网拒绝；资源服务可直接访问固定内部身份入口 |
| `/actuator/`、内部任务/委托/目录同步端点 | 不发布公共路由；私网来源限制与技术客户端认证并用，隐藏 URL 不能替代认证 |
| `/assets/`、项目已登记的业务页面路径 | 业务静态制品存在时启用；带内容 hash 资源长缓存，index 不缓存；缺失资源返回 404，只有页面路由允许 SPA fallback |
| 其他路径或未知 Host | 默认拒绝或 404；无业务 Web 时根路径只跳转管理入口，不返回构建失败页面 |

入口与 Gateway 路由来自同版声明，按精确端点/受限前缀匹配；账号公共 API 中仅 registrations 和 account-actions:consume 允许匿名访问且执行 [多租户与权限体系设计·注册、激活、禁用与业务资料初始化](04-多租户与权限体系设计.md#registration) 的策略/令牌验证，其余身份 API 均受保护。内部端点集合由发行包列明，禁止用无条件泛转发暴露它们。OAuth 上游状态、Location、WWW-Authenticate 和标准响应不包装成业务 JSON；不使用错误页把 401/403/404 变为 200。

## 6. TLS、代理头与证书维护

本节适用于测试/生产 HTTPS 环境；本地 loopback 的绑定与开发例外以 [本地运行与地址规则](03-基础设施与环境设计.md#local-development) 为准，不能把 local 的 HTTP/内部明文设置用于服务器。

| 环境输入 | 固定含义 / 校验 |
| --- | --- |
| `PUBLIC_ORIGIN`、`EDGE_SERVER_NAME` | 如 https://app.example.com 与 app.example.com；必须匹配，生产不允许 HTTP；issuer、redirect_uri、退出地址按同一来源生成并精确登记 |
| `GATEWAY_UPSTREAMS` | 已验证可达的私网 IP:映射端口列表，不允许任意外部 URL；变更纳入发布 |
| `GATEWAY_UPSTREAM_SERVER_NAME`、`INTERNAL_CA_FILE` | 内部 TLS 校验的服务名与 CA；Gateway 证书 SAN 匹配，Nginx 校验 CA/名称，不关闭 verify |
| `TLS_CERT_FILE`、`TLS_KEY_FILE` | 宿主机证书完整链与私钥路径，容器只读挂载；私钥仅运行账号可读，不入 Git、镜像或 Nacos |
| `CERT_MODE` | `acme` 或 `provided`；前者使用 Certbot webroot，后者由企业证书系统交付，二者都执行到期监测与校验后 reload |
| `WEB_RELEASE_DIR` | 可选、固定版本的已构建业务静态目录，只读挂载；未提供时仍能访问身份管理 |
| `TRUSTED_PROXY_CIDRS` | Gateway 只信任入口的实际受限网络来源；不能直接设为整个互联网 |
| 请求体与超时设置 | 默认值按 [应用部署与运维设计·SSE、上传、超时与排空](09-应用部署与运维设计.md#proxy)；项目仅通过已声明环境配置调整并同步应用限制，不修改模板中隐含常量 |

首次上线顺序：确认 DNS A/AAAA 指向实际入口（没有 IPv6 接入就不发布不可达 AAAA）→ 设置防火墙 → 准备证书及内部信任 → 启动依赖和应用 → 测试入口配置 → 开放 HTTPS。acme 模式先启用只提供 `/.well-known/acme-challenge/` 的 HTTP 引导配置，获得证书后切换完整 HTTPS 配置；没有证书时不启动引用不存在文件的 TLS 配置。80 端口仅保留 ACME challenge 与其他请求跳转 HTTPS，443 为业务入口。

Certbot 由宿主机定时任务运行，使用 certonly/webroot，不自动修改版本化 Nginx 配置；首次配置做续期 dry-run。deploy hook 在成功续期后将证书复制到只读的版本化证书目录，容器只读挂载证书父目录；校验证书/私钥匹配和配置，再切换目录内 current 引用、reload 并核验对外证书；保留上一版有效证书用于受控恢复。provided 模式由证书提供方负责更新文件，Ansible 执行相同校验/加载步骤；发布检查记录责任方。剩余有效期低于 30 天告警，7 天升级告警；失败不得静默继续到过期。具体续期计划与告警接收方必须在环境清单填写。[Certbot 官方使用及续期说明](https://eff-certbot.readthedocs.io/en/stable/using.html)

边缘 Nginx 默认直接面对公网，丢弃客户端伪造的 Forwarded/X-Forwarded-*，根据真实连接重新设置 Host、X-Forwarded-Proto/Host/For；Gateway 仅接受受信任代理提供的值。若前置其他负载均衡器，必须单独登记其地址及 real-IP 信任规则。Nginx/Gateway 均不接受外部 user_id、tenant_id、X-Service-Authorization 作为内部身份；真实客户端 IP 用于限流和审计，不作为登录凭据。固定 issuer 不从任意 Host 推导。

主机只将入口 80/443 暴露公网；Gateway、identity、业务 API、Actuator、DB、Redis、Rabbit 与 Nacos 绑定私网并设白名单。跨主机认证链路使用校验通过的 TLS；同宿主机的内部网络也不能据此免鉴权。Docker 发布端口的防火墙效果必须从外部主机验证，不能只看宿主机规则列表。

## 7. SSE、上传、超时与排空

普通同步 API 的 SDK 连接与响应预算只在[HTTP 合同](07-Java与Python协作设计.md#http)定义；Gateway 总处理上限 15 秒，Nginx 连接上限 2 秒、普通/流式读写空闲上限统一 60 秒；不能把长算法塞进同步接口，长任务按异步提交。Nginx 的 proxy_read_timeout 限制相邻读取的等待，不能代替服务端总执行 deadline。[Nginx proxy 模块](https://nginx.org/en/docs/http/ngx_http_proxy_module.html)

默认请求体上限 10 MiB，Nginx、Gateway 与应用均一致执行并返回 413；项目确需更大上传时按显式路径提高限制。大文件使用对象存储上传流程，由项目校验对象归属、大小和完成状态；不能以取消所有限制解决上传问题。业务 API、OAuth、BFF、管理 API 一律不做代理缓存，身份静态资源遵循 [身份管理界面设计·升级、缓存与兼容](06-身份管理界面设计.md#upgrade) 的缓存合同。入口不自动重试 API 写入或流式请求；示例统一关闭 API upstream 自动重放，安全 GET 的有限重试由 SDK 控制。

SSE location 显式关闭 proxy_buffering、proxy_cache、gzip，不聚合响应或整段重试；保留事件类型和 Last-Event-ID。通用默认：应用心跳不超过 15 秒、Gateway 空闲 45 秒、入口读/发送空闲 60 秒，应用单连接最长 10 分钟；项目必须声明并验证心跳/空闲预算关系。框架只提供转发与断连处理，不负责业务事件持久化、回放、Run 取消或恢复。

仅证书续期或明确的纯配置维护可在 nginx -t 后 reload；应用发行按维护窗口重建入口容器。入口排空上限 11 分钟，停止宽限大于排空期限；超时允许断开，业务决定重连语义。一般业务 API 退出先摘除发现再排空请求；不引入 Agent Worker drain 状态机，不承诺 TCP 跨节点迁移。

访问日志只记录方法、无查询参数的路径、状态、字节数、请求/上游耗时与 request_id，不记录 Authorization、Cookie、请求体或完整 URL。OAuth code、state、邀请/重置 token 可能出现在 query，禁止使用默认含 request URI 的访问格式；认证回调和凭证消费路由的 error log 也须验证脱敏，关闭 debug，必要时仅保留应用脱敏事件。日志轮转/保留量写入部署配置，避免磁盘耗尽。

## 8. 应用配置与入口配置变更

交付 `deploy/nginx/server.conf.j2`、`local.conf`、`acme.conf`、`deploy/compose.yaml` / `compose.server.yaml`、`tools/deploy/ansible/tasks/edge.yaml`、`tests/deploy/test_release_operations.py`。声明的框架来源统一在 `template/deploy/`；Java/Python 业务骨架在 `template/services/`，工具实现与测试分别在 `tools/` 和 `tests/`。入口镜像 digest、模板与静态制品摘要写进项目发行清单，候选配置先经 Nginx -t 再替换。

新项目由创建器生成 deploy 声明，填写环境清单中的域名/上游/证书/静态目录，打包后运行本文定义的 Ansible initialize/migrate/deploy 入口；无需从零写 Nginx。项目新增服务主要改 Gateway 显式路由；只有新增公开路径类型、上传策略或静态应用时才修改版本化入口声明。框架升级时比较原版与新版模板，通过环境值重新渲染并查看差异，不能覆盖项目私钥、业务源码或未审阅的本地定制。

入口更新使用项目/环境发布锁与明确维护窗口：渲染 candidate.conf → 校验证书/域名/上游及目标镜像 nginx -t → 备份 default.conf → 记录旧镜像和备份路径 → 停止并重建入口容器 → 等待 readiness → 全批次公开 HTTPS 烟测。当前是单文件只读挂载，因此采用容器重建加载新文件，不宣称原子无损切换。运行失败保留现场、锁和备份，由运维核对后恢复旧配置与兼容镜像并重新建容器；不自动回退应用。证书续期的 current 原子切换属于独立证书工具，不能混同为应用发布的自动恢复。回退证书必须仍有效且未撤销。

烟测必须从外部客户端走真实域名/TLS，覆盖管理页在业务 Web 缺席时可用、OAuth 登录及机器换 token、普通 API 错误、SSE 首事件/心跳/重连、未知路由、跨租户拒绝、内部端点不可达和实际证书有效期。证书更新走同一入口锁，避免与配置发布竞态。只有这些检查通过才把发布标记成功；Ansible 触发或容器 running 不等于上线完成。

## 9. 监控、告警和日常处置

| 观察对象 | 关键指标/日志 | 处置方向 |
| --- | --- | --- |
| HTTP/Gateway/identity | 成功率、延迟、401/403 与 5xx 分开、内省失败、会话存储错误 | 先区分权限拒绝与依赖故障；不通过关闭鉴权恢复 |
| Nacos/网络 | 实例注册数量、续约、摘除、客户端配置版本、连接失败 | 对照目标清单核对注册地址/端口和实例真实存活 |
| PG/Redis/Rabbit | 连接池、磁盘、复制/备份状态（如启用）、内存淘汰、队列积压、死信 | 按基础设施维护流程处理；不靠重启业务解决满盘 |
| 可选 Outbox/Inbox | 最老未投递时间、重试次数、隔离消息 | 业务提供告警接收与受控恢复；框架无算法任务平台 |
| 发布 | 主机实际 digest、readiness、配置/迁移摘要、失败批次 | 先 reconcile 确认事实，再续发或兼容回退 |
| 证书和备份 | 到期时间、最近成功备份、最近恢复演练结果 | 提前维护；“有备份文件”不等于能恢复 |

日志至少关联 project/environment/service/instance/trace；业务请求按需关联 tenant、脱敏主体、task/run/attempt。禁止 token、Cookie、密码、密钥和完整聊天正文默认入日志。生产日志有访问权限、保留时间和删除机制。

readiness 表示当前实例是否可以接收其负责的工作；liveness 不因短暂外部依赖故障引发全体重启风暴。对外健康端点不泄露连接串、组件版本和内部拓扑。具体阈值按环境配置，在发布验收中冻结，不能把未经测量的阈值当容量承诺。

## 10. 运维权限与交接清单

生产发布由受控 Linux/WSL 控制机和指定操作者执行固定 playbook，不要求开发人员登录所有主机逐台手工修改。CI/CD 后续可调用相同入口；本设计不新增发布平台。

SSH 部署权限、组件初始化权限、迁移权限、应用运行权限分开。运行容器只获得其服务的最小权限；生产秘密放在受控宿主文件/秘密存储，通过文件注入，不提交仓库、不写命令行。操作记录包含执行者、operation_id、环境、目标主机、版本、配置摘要、开始结束时间及结果。

交付项目运维时须包含：部署拓扑与访问范围、主机清单、端口、凭据保管与轮换责任、发行清单、首次安装记录、最近迁移和备份恢复记录、告警联系人、故障排查入口。项目负责域名、服务器、生产秘密和实际运维；框架负责可复用入口、合同及维护文档。
