# 工程检查与监控指南

> 对应 D-20261029-01。本页随新项目交付；权限、采集和部署操作见第5～7节。框架已有本地运行证据，但每个项目仍须在自己的环境验证；不把框架的运行结果当作该项目的部署或容量验收。

## 1. 新项目拿到什么

生成项目包含 SDK、服务自身测试、三份共享协议 JSON（内省、路由、通用错误）、`tests/acceptance/smoke.cjs`，以及 `.github/workflows/checks.yml`、`security.yml` 和 Dependabot 配置。不会带上框架的 scripts 导出/固定来源/打包维护测试，也不会带历史验收脚本。checks 的 maintenance job 仅留在框架仓库。

`create.py --ref` 只导出固定提交；请选择包含所需能力且已核对的提交，不会导出工作区未提交变更。新项目按自己的 README 创建依赖、初始化账号、启动双语服务；工程检查不替代首次登录和双租户运行验收。

## 2. 本地检查和 GitHub Actions

先在项目根 `uv sync --frozen`；Java 使用 JDK 21，管理页使用 Node 24.13.0 / pnpm 11.12.0。Java 构建会执行管理页检查，必须先安装对应 Node/pnpm。SDK 的完整类型检查要先执行 `uv sync --frozen --all-extras --project sdk/python`。安装可选依赖不意味着启动 PG、Redis 或 RabbitMQ。

```bash
uv run --frozen ruff check scripts
uv run --frozen --all-extras --project sdk/python mypy --config-file sdk/python/pyproject.toml sdk/python/src
uv run --frozen --all-extras --project sdk/python pytest -c sdk/python/pyproject.toml --confcutdir=sdk/python sdk/python/tests/test_http.py sdk/python/tests/test_typed_http.py sdk/python/tests/test_circuit.py
```

Java/Python 在 workflow 的 `strategy.matrix.include` 中显式列出 `module` 与 `tests`；前端沿用指定文件。创建项目时初始服务名自动替换。新增/替换业务后维护矩阵中的模块和定向测试；scope job 将其与 config/services.yaml 对照，漏登记、重复或测试文件不存在均失败。每个 Java 模块先构建依赖，再单独运行定向测试，零匹配失败。不要把“过滤器未匹配任何用例”当测试通过。新服务 submodule 必须固定到提交；CI checkout 使用 recursive，私有仓库需项目配置只读访问。缺少凭据时应失败并报告，不跳过子仓后报绿。

现有矩阵包含浏览器回调 CSP、网关 token 预检、指标绑定和 Python 访问日志脱敏回归。修改这些行为时同时维护相应用例和清单；Windows scope 检查显式读取/输出 UTF-8，无需额外设置 PYTHONUTF8。

维护仓库 root pytest 默认禁止 Docker 子进程；需要 local_env 的用例只有显式 `--run-integration` 才准备真实环境，选中之后环境不可用必须失败。日常按改动选择定向测试，未显式选择不启动集成环境。生成项目没有维护仓库的 conftest，业务集成测试应由项目显式选择；默认 workflow 只运行列出的非集成用例。

security 使用 Gitleaks CLI、OWASP Dependency-Check、pip-audit、pnpm audit；Dependabot 只建议升级。Java 从 [OWASP 官方维护的 NVD JSON 2.0 镜像](https://dependency-check.github.io/DependencyCheck/data/mirrornvd.html) 批量下载年度数据并增量更新，避免无 API Key 的 REST 全库分页超时；镜像通常每日更新，实时性受上游发布影响。数据库缓存按扫描器版本隔离，更新成功后立即保存；下载或扫描失败仍失败，CVSS ≥ 7 阻断。Python 不自动忽略缺少严重性标记的公告。不能用 continue-on-error 或整目录排除绕过发现。分支保护、仓库告警和 GitHub 真实执行记录需要项目管理员实际启用，提交 YAML 不代表这些设置已生效。

本仓库未配置 Sonatype 凭据，经维护者确认停用额外的 OSS Index 分析器（匿名请求返回 401）。Java 继续以 NVD 为漏洞数据源；这减少了一份补充漏洞来源，不等于关闭 Java 依赖审计。恢复 OSS Index 前应配置认证并验证其 API 可用性。

已核实的组件误识别记录在 `.github/dependency-check-suppressions.xml`，仅匹配确切包版本和具体 CVE，并附上游依据；当前涉及将 Java 客户端/适配库误识别为 Nacos 或 Prometheus 服务端。它随源码导出，不能扩大为整包或整类漏洞忽略。真实依赖漏洞通过[项目父 POM](../../pom.xml) 的固定安全补丁版本解决。

## 3. 类型化跨语言调用

Java 服务 Client 使用 SDK `request(..., new ParameterizedTypeReference<ApiResponse<ItemPage>>() {})`，Python 服务 Client 使用 `runtime.http.request_model(service, "GET", path, PeerResponse)`。参考两个 sample 服务的 `client/PeerClient.java` 和 `clients/peer.py`；新项目生成时路径和服务名一起改名。

DTO 留在各业务服务内。Java 必填构造字段声明 `@JsonProperty(required=true)`，不可空字段声明 `@JsonSetter(nulls=Nulls.FAIL)`；Python 用 Pydantic 明确必填、默认和可空字段。允许对端增加未知字段，禁止把字符串数字默默转换为整数。Java 类型化结果重新生成响应实体，只保留 JSON 类型和有界 Retry-After，不沿用已改变实体的 Content-Length、压缩或 Cookie 头。

非成功 HTTP 保留状态与合法协议 code，消息不回显上游正文；畸形 JSON、缺失必填或错误类型返回 DEPENDENCY_INVALID_RESPONSE/502。它仍是运行时契约校验；OpenAPI 自动生成 client、跨仓编译期兼容检查不在本轮。写操作不增加重试。

### Swagger 浏览器授权复验

Swagger 的公开客户端仍需本人完成组织登录和应用同意：用 `dev.py <服务> --tenant-code <组织编码>` 启动，Authorize 选择 scope；登录页选择租户账号并输入真实组织编码、账号和密码，在“应用授权”页勾选权限后点击“同意授权”。点击“拒绝”应返回授权拒绝，不能取得访问令牌。页面使用同源静态样式；复验时应从同意页自身提交表单，不从其他页面或测试后门补取安全字段。

登录及同意页应始终停留在 `PUBLIC_ORIGIN`，不能跳到内部身份端口。local 的表单 CSP 仅额外允许已登记的准确 localhost Swagger 回调；test/prod 保持同源限制。浏览器若报 `form-action`，先检查跳转来源与客户端回调登记，不关闭 CSP。

token 的 POST 预检经 Gateway 沿既有身份路由交由身份服务校验；精确允许来源应带回 `Access-Control-Allow-Origin`，未登记来源应拒绝。只有空的 HTTP 200 不能证明预检可用，必须继续核对真实 token 交换和 Try it out。

## 4. Python 出站熔断

在调用方 `config/nacos/<服务>.yaml` 的 http 下配置（service 是登记的逻辑依赖名）：

```yaml
http:
  circuit_breakers:
    equipment-service:
      enabled: true
      failure_threshold: 5
      recovery_timeout_seconds: 30
```

没有规则就不启用；配置发布后重启调用方。生成的 Python 示例已经启用其 Java 对端规则。`runtime.http` 自动使用，不在业务重复包一层重试。一次逻辑请求最终远端连接/读取故障或 5xx 计一次；4xx/429 表示远端可达，取消、池满、无实例、入场预算耗尽不计远端失败。打开时快速返回 DEPENDENCY_CIRCUIT_OPEN/503，恢复后最多一个探测。状态按进程独立，不存 Redis。

## 5. 可选本地监控的操作顺序

以下步骤供 Docker 验收恢复后执行。默认 `COMPOSE_PROFILES` 不含 monitoring，业务不依赖 Prometheus/Grafana。若仅开发业务，不需要启用。

1. 先按新项目 README 完成不带监控的本地初始化和服务启动。准备 Prometheus v3.15.1、Grafana 13.3.0 的实际镜像摘要；目前仓库没有伪造/未核实的 digest。启用校验要求完整 `repository:version@sha256:...`，只有版本标签会被入口拒绝。
2. 全新项目已登记该 scope；旧项目先保持 monitoring 关闭，用原有受控身份维护绑定运行 `java -jar identity-service.jar bootstrap-monitoring`（local 复用基础 Compose：`docker compose --env-file .local/runtime/compose.env -f deploy/compose.yaml run --rm identity-bootstrap bootstrap-monitoring`）。该命令只允许受保护平台客户端增加一个 scope，同事务校验原摘要和秘密、CAS 更新协议/策略版本/登记摘要并审计；任何其他漂移拒绝。普通 bootstrap 不自动扩权。
3. 在 `.local/environment.env` 增加 `COMPOSE_PROFILES=monitoring`（同时需 MQ 时用 `mq,monitoring`，不带空格）、`PROMETHEUS_IMAGE`、`GRAFANA_IMAGE`。local 的 `MONITORING_PROXY_CIDRS` 由 init 自动从当前项目唯一网关取得并写回此文件，无需手工查容器 IP；找不到默认环境或唯一网关时停止，不扩大可信网段。
4. 本地 `GRAFANA_BIND_HOST` 默认 127.0.0.1，端口 13000；没有匿名访问，也没有默认账号密码登录入口。容器间 BFF 默认使用 `http://grafana:3000`。保护依赖受控的主机/容器网络，其他业务容器不能伪装成可信网关；不能将任何来源都列入代理白名单。
5. 重跑 `uv run --frozen python scripts/init.py --env local --services all`（原环境使用演示账号时仍带 `--with-demo`）。目标生成至 `.local/runtime/monitoring-targets.json`：基础服务走容器地址，宿主业务走固定 DEV_HOST；指标端口为服务端口 +1000。只包含本次所选服务。重启相应业务进程后采集才存在。
6. 网关重建后重跑同一 init；它会在启动前后核对来源 IP，变化时自动刷新单 IP 白名单和 Grafana。不可扩大到整个子网解决 403。手工改动的派生文件会停止而不覆盖；旧项目缺少派生哈希时先核对备份和实际内容，不删 `.local` 或数据卷强行重来。
7. 完成启用后，退出平台入口重新登录授权，使 token 取得 platform.monitoring scope 和 platform:monitoring:read 权限。租户管理员不能看监控；原平台会话不会自动扩权。管理页出现“服务监控”，每次 Grafana 页面/API 请求仍重新核对有效身份权限。

Java 初始化和容器就绪探测统一使用主端口 `/readyz`（存活 `/livez`），开启独立指标端口不改变此入口。Python 仍使用已有 `/actuator/health/readiness`。Java 的私网 `/actuator/prometheus` 使用独立 management 端口；Python 使用生命周期管理的独立 prometheus_client 监听 `/metrics`。两个端口均不得通过 Nginx/公网开放。开发宿主防火墙只允许采集容器来源访问。未知或暂无采集数据时，面板显示无数据，不显示虚构的零。

入口排障先查看 `docker compose logs nginx` 的安全 JSON 日志：`uri` 不含查询参数，`status`、`upstream_status`、`upstream_addr` 和耗时用于判断失败位置，再按关联字段查询网关和业务结构化日志。Nginx 原生 HTTP 请求错误日志会保留完整 URI，因此在这三个入口配置中关闭；主进程启动诊断和 `nginx -t` 配置检查仍保留。不要为排障临时开启包含查询、Referer、认证头或请求体的日志。

Python 入口的 `configure_logging` 在 `uvicorn.access` 日志源过滤查询串，再交给已有 JSON 或自定义 handler；方法、路径、协议、状态及上下文字段保留。未知访问记录形状不输出，避免 Uvicorn 日志格式变化后把授权码等查询值带入日志。业务收到的查询参数不变；Swagger 回调检查须覆盖 `/docs/oauth2-redirect?code=...`，不能只扫描 BFF 的 `/callback`。

## 6. test/prod 和多机环境

沿用项目的包外 environment.env / 每服务运行 env / hosts.yaml，不新增配置管理系统：

- 组件环境中持久化相同 COMPOSE_PROFILES、固定镜像摘要、Grafana 只监听的私网 IP、真实网关来源 IP 白名单和 MONITORING_TARGETS_FILE 绝对路径。
- 在 inventory 的每个 apps 主机下补 metrics_ports，例如 `{identity-service: 9081, api-gateway: 9080}`；只有 app_services 中选中的服务会生成目标，nginx 不作应用指标端点。目标来自该主机 ansible_host 的私网地址和上述真实端口；禁止公有、loopback、重复端口及未登记服务。
- Java 服务运行 env 设置 MANAGEMENT_SERVER_PORT、MANAGEMENT_SERVER_ADDRESS（容器内通常为 0.0.0.0，不能填宿主私网 IP）、MANAGEMENT_ENDPOINTS_WEB_EXPOSURE_INCLUDE=health,prometheus、MANAGEMENT_METRICS_DISTRIBUTION_PERCENTILESHISTOGRAM_HTTP_SERVER_REQUESTS=true。环境变量中的连字符必须移除，不能把 percentiles-histogram 写成 PERCENTILES_HISTOGRAM。Python 设置 METRICS_BIND_HOST（容器内通常为 0.0.0.0）和 METRICS_PORT。服务端口与指标端口不能相同。
- 将组件环境中的 COMPOSE_PROFILES 原样带到应用 compose.env；Compose 将其传入网关，发布预检拒绝与源环境不一致的值。不另设 MONITORING_ENABLED 开关。GRAFANA_INTERNAL_ORIGIN 是受控服务端内网地址，多机填 Grafana 主机私网地址/端口，浏览器不能选择上游。
- infra inventory 的 infra_services 增加 prometheus/grafana 后，infra.yaml 收集已有 apps 主机的最小非敏感采集绑定，交给 infra/up.py 生成目标。组件启动与应用滚动发布仍走已有 Ansible 流程。仅启动组件不能替代服务运行绑定更新和相应服务重启。
- 多机 Docker 应用在项目已有 Compose override 中把实际指标端口只映射到宿主私网 IP（例如 `10.20.0.11:9081:9081`），不能只声明容器内监听却假定跨机可达。该端口要与 inventory 的 metrics_ports 一致。
- 防火墙只允许 Prometheus 主机访问指标端口、网关主机访问 Grafana。代理 IP 白名单必须按 Grafana 实际看到的 NAT 后来源核对；不以“都是内网”代替边界验证。

关闭监控时移除 profile 并按现有发布流程停掉两个组件，同时撤销应用指标绑定，保留数据卷供后续决定。不要执行 down -v。可选组件故障不影响身份和业务 readiness。

## 7. 已知验证边界

静态 YAML、生成项目、权限/同源策略单测、指标文本和生命周期测试均属于 A 层。Grafana 的真实脚本 CSP/iframe、真实撤权、NAT 白名单、面板 PromQL、镜像摘要拉取、跨主机防火墙属于 B 层；恢复 Docker 后逐项验证。备份恢复、压测数字和正式 tag 另需真实证据；当前不能据此宣布生产可用。

## 变更范围的 Python 检查

从项目根执行 `uv run --frozen python scripts/check_python.py --paths <文件...>`，或 `--base REF --head REF`。入口按所属 pyproject 调用 Ruff lint/format，源码与测试都覆盖；无范围参数拒绝执行。PR 的基线取 merge-base，首次 push 取提交中全部 Python 文件。每个受影响业务模块和 SDK 在自身环境执行 mypy。规则强度见[Python 规范](../standards/03-Python编码规范.md)，真实租户事务验证另按隔离测试绑定执行。


## 最小源码发行验收（D-20261029-01）

维护脚手架时，在包含验收入口的固定提交执行 `uv run --frozen python scripts/verify_scaffold.py --ref <固定提交> --output <不存在目录> --project <唯一项目名> --port-offset 4000 --dev-host <容器可达宿主地址>`。需Git、uv、JDK、Node/pnpm、Docker/Compose及可下载的依赖；Windows默认示例宿主名仅在双方可解析时使用，不修改hosts或防火墙。入口从空目录生成、准备依赖、with-demo初始化并运行浏览器；它会修改隔离候选中的演示数据和初始密码。

结果写入候选 `.local/release-check/report.json`；关联确切源码SHA与锁摘要，成功退出0，任何阶段/清理失败非零。应用和基础设施容器仅停止，保留卷/候选/失败证据。重跑换新目录及项目名，不删除其他环境。手动CI工作流Scaffold release check运行同一入口；仅可信维护者触发，不自动发行。维护者须核对待发行SHA的成功报告；普通单元CI、旧候选报告或当前健康状态不能替代冷启动验收。

生成项目只带业务smoke，不带维护验收入口和维护工作流。最小验收不覆盖生产容量、HA、镜像推送或多机发布；具体合同见[源码交付设计](../design/11-源码脚手架交付与开发体验设计.md#release-check)。
