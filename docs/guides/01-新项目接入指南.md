# 新项目接入指南

> 文档版本：1.6；基线：D-20261027-03；更新：2026-10-27。本文只展开操作步骤，当前修正及验证见[计划 05](../plans/2026-10-27-混合项目接入与审查修正-plan.md)。真实双机和外部身份提供方尚未验收。

<a id="preparation"></a>
## 1. 取得同版混合项目发行包

使用一个同时包含 Java、Python 的项目。发行包提供基础镜像、Maven parent/foundation、Python SDK wheel、运维材料与摘要；不复制身份、网关、SDK 的源码。仓库示例位于 framework/examples/services，打包后位于新项目根 services；演示业务前端在根 web。身份管理页面随 identity-service 镜像交付，业务 web 不依赖其 npm 包。

准备 Docker Engine/Compose、Python 3.12、uv、JDK 21；服务器 Ansible 控制端使用 Linux/WSL，Windows 可以本地开发。以下工作目录均为**独立项目根**。完整命令、参数与排错见[混合示例 README](../../framework/examples/README.md)。

<a id="create-project"></a>
## 2. 解压到新目录，明确文件归属

解压到框架仓库之外的新目录，先保留两个 sample 服务名跑通，再改领域名称。无需手工拼接两套示例。

| 目录 | 新项目如何使用 |
| --- | --- |
| services/sample-java-service | Java 普通资源服务；独立 POM、权限清单、迁移、Dockerfile |
| services/sample-python-service | Python 普通资源服务；独立依赖、权限清单、迁移、Dockerfile |
| web | 两服务共用的业务演示页，后续替换为项目自己的前端 |
| config | 环境绑定、Nacos 配置源和开发启动登记 |
| infra | PG/Redis/Nacos 等组件与项目资源，独立生命周期 |
| deploy | 应用 Compose、Nginx、迁移与 Ansible，不包含业务源码 |
| examples | 接入说明、业务 Compose/配置样例和验证工具，没有第二份 services |
| artifacts | 固定 Java/Python 制品和从身份 JAR 提取的迁移 |

保留根 pyproject.toml/uv.lock、Maven wrapper、.gitignore、release-manifest.json 和 framework-baseline.json。初始化 Git 后运行 `git check-ignore .local/environment.env .local/runtime/compose.env`，两项应命中。业务源码、依赖锁、非敏感样例提交；实际环境、秘密和构建缓存不提交。目录权威见[总体设计](../design/01-总体架构与工程结构设计.md#project-layout)。

<a id="configure"></a>
## 3. 准备本地环境

在项目根创建 .local，复制 config/environments/local.env.example 为 .local/environment.env，执行 `uv sync --frozen`。填写 PROJECT_CODE、APP_ENV=local、PUBLIC_ORIGIN 与映射端口。另一个项目使用独立标识、端口、卷、数据库和 namespace，不复制已有秘密；Nacos API/gRPC 映射端口相差 1000。

环境地址放 env，密码通过 *_SECRET_FILE 注入；运行参数放服务 Nacos 文件。业务自己的参数放 business mapping，由业务模型校验，新增字段不用修改框架白名单。例如两服务的 business.max_page_size 演示分页上限；这是示例领域参数，不是框架统一业务策略。business 变化重启生效。规则见[配置设计](../design/02-配置与服务发现设计.md#schema)。

<a id="startup"></a>
## 4. 从空环境到混合服务

按 examples README 的命令逐步执行，失败停止在当前阶段：

| 阶段 | 操作 | 成功结果 |
| --- | --- | --- |
| 基础依赖 | prepare-local → infra/up → resources → config/publish | PG/Redis/Nacos 健康，独立资源及配置就绪 |
| 身份初始化 | artifacts/identity-migrations 完整迁移 → examples/prepare_local → identity-bootstrap | 初始管理员、管理 BFF、受限发布身份就绪 |
| 基础应用 | 启动 identity-service、api-gateway、nginx | /identity/admin/ 可访问，首次改密后登录 |
| 业务构建 | Java 引用发行 Maven 制品；Python 引用发行 SDK wheel；各自构建镜像 | 两镜像独立，不依赖框架源码路径 |
| 业务数据 | 初始化两份 resources.yaml，执行各自 Flyway/Alembic | 各自数据库、受限运行账号、RLS 与迁移正确 |
| 业务接入 | 发布权限清单，登记 audience/客户端，填写运行秘密与路由 | 内省、BFF、目录及授权关系一致 |
| 业务应用 | 同一 Compose 项目启动两个服务，更新 Gateway 后校验并 reload 本地 Nginx | 两服务 ready，浏览器登录及双向调用成功 |

当前身份历史为 V1—V9；以后按同版 artifacts 中完整迁移执行，不固定只跑前八个。独立项目使用 Compose 的 identity-bootstrap，不执行框架源码 target 路径。重复 bootstrap 只核对，不重置密码、密钥或角色。

默认 8 个常驻容器：PG、Redis、Nacos、identity-service、api-gateway、nginx、Java 业务、Python 业务。迁移/bootstrap 是短期进程；需要消息再加 RabbitMQ。外部组件不启动对应本地容器，地址、资源归属及凭据由环境绑定。

<a id="identity"></a>
## 5. 用内置页面完成身份与权限接入

1. 平台管理员首次改密后，在租户页创建租户和初始管理员，记录租户 ID。不同租户的同名账号完全独立。
2. 应用与机器身份页先登记两个服务 audience；服务权限经受限发布凭据同步 permissions.yaml，不能在页面随意编造编码。
3. 为每个资源服务、Gateway 分别创建内省客户端：service 类型，identity-service audience，仅 internal.introspect:<目标 audience> scope，无租户绑定，不共用管理员凭据。
4. 创建 web-bff：机密 user 客户端，明确允许租户、两服务 audiences、业务 scopes，精确回调 /bff/web/callback、退出回调 /bff/web/logged-out。详细字段表见 examples README。
5. 将只显示一次的 client_secret 保存到调用方受控秘密文件；关闭页面后不再读取。轮换使旧秘密及旧授权版本失效，需同步调用方；固定管理客户端只由维护入口管理。
6. 租户管理员创建业务角色，选择已发布权限及支持的数据范围，将角色分配给普通用户。没有管理委派、授权模拟或 INVITE/OPEN 自注册流程。
7. 安全策略页维护全项目密码、登录限制与会话策略，租户不单独覆盖。版本冲突或结果未知先重新查询，不能重复提交覆盖。

管理页面无需按项目修改源码。新增资源只需发布权限清单并保护业务接口；业务前端自行控制按钮可见性，后端始终最终判定。完整页面范围见[管理界面设计](../design/06-身份管理界面设计.md#features)。

<a id="business"></a>
## 6. 开发自己的业务

先验证两服务的创建、查询及双向 peer 调用，再改为领域服务。业务团队维护表/迁移、API、权限编码、对象归属和业务页面；框架提供配置发现、身份/权限内省、可信主体、租户事务、HTTP 与可选消息适配。不能信任客户端自报 tenant_id，不能用机器账号绕过用户限制，也不需要先搭 Agent 平台。

<a id="add-service"></a>
## 7. 增加服务与混合调试

在同一 services 下新增独立工程，同步服务启动声明、资源/迁移、权限 owner/audience、Nacos Data ID、路由、Compose 和 config/development.yaml。每服务有独立运行秘密；新增目录发布身份按 bootstrap 受控声明核对，不能借用其他服务 owner。

IDE 操作见[混合调试](../../framework/examples/README.md#混合调试)：先跑全容器，停止一个待调试容器，再通过 dev.ps1/dev.sh 启动宿主进程。身份与对端实例的发现地址也必须从宿主可达，不能只改当前服务。框架包仍使用固定制品。

<a id="deployment"></a>
## 8. 进入测试和生产环境

准备获准镜像仓库的不可变摘要、hosts.yaml、release.yaml、各主机环境和秘密、TLS、防火墙与备份。操作入口见[Ansible 说明](../../framework/deploy/ansible/README.md)。顺序为 infra（仅自建依赖）→ initialize → migrate → deploy。首次先部署身份/网关/入口，完成登记后将两业务加入下一次范围。

实例更新检查自身 readiness，全部所选实例成功后才统一检查公开入口。发布需要维护窗口，失败保留锁、尝试范围和旧配置/镜像证据；核对现场后显式恢复，不自动数据库降级。真实双机与公网 OAuth 提供方仍需专门验收。

<a id="upgrade"></a>
## 9. 框架升级

新包解压到另一目录，对比旧 framework-baseline、新包与项目当前改动。业务源码、业务配置、资源、秘密和数据归项目，不能整体覆盖。升级 foundation/SDK 后重建业务；管理页面随身份镜像更新。运维脚本与根 pyproject.toml/uv.lock 同步合并，再 uv sync --frozen。

先兼容检查、备份及恢复验证，再迁移、更新应用。不重置账号、不删除卷。应用回退必须兼容实际 schema，包含部分失败时的实例范围；见[回退合同](../design/10-数据库迁移与升级设计.md#rollback-window)。

<a id="diagnostics"></a>
## 10. 最小验收与排错

- 普通用户允许动作成功、拒绝动作 403；停用后新请求拒绝。
- 两租户同名用户和数据相互隔离，直接访问另一租户 ID 失败。
- Java→Python、Python→Java 均经过发现与鉴权，不串入另一项目实例。
- 重复初始化不改密码；错误配置或缺客户端阻止 ready；业务配置重启后生效。
- 401 检查登录/应用范围/撤销，403 检查角色/数据范围，503 检查身份/发现/Redis。
- Gateway 重建后检查本地 Nginx 解析并 reload；服务器发行按维护窗口重建入口。

本地通过不代表真实双机、外部提供方或生产恢复已验证，逐项以计划证据为准。

流量保护接入和 rc.2→rc.3 配置迁移见[流量保护接入指南](03-流量保护接入指南.md)。复制服务配置时一并包含启用 Sentinel 的两份 JSON，不能只复制 YAML。
