# 新项目接入指南

> 基线 D-20261027-07；操作指南引用权威设计，不另外定义安全与部署合同。

<a id="preparation"></a>

## 1. 前提

准备 Git、Python 3.12、uv、JDK 21、Docker Engine/Compose；发行 Git 标签/提交必须包含 tools/create.py。当前未提交改动不是远程可获取版本。框架四个职责模块不变，Java/Python 业务同在 services。

<a id="create-project"></a>

## 2. 从固定源码创建

工作目录：检出所选版本的框架仓库。目标目录必须不存在。

```powershell
python manage.py create --output ../equipment-platform --ref <已发布标签或完整提交> --project equipment-platform --java-service equipment-service --java-package com.acme.equipment --python-service inspection-service --python-package inspection --port-offset 0
cd ../equipment-platform
git check-ignore .local/environment.env services/inspection-service/.venv
git add .
git commit -m "初始化混合项目"
```

创建器只生成文件和固定 submodule，不创建远程或自动 push；团队自行添加业务仓库远程。新机器递归 clone；缺引用运行 git submodule update --init --recursive。Windows 深路径的 Git 长路径设置仅作用于新建仓库。创建失败保留临时目录供检查，不覆盖用户目录。目录权威见[总体设计](../design/01-总体架构与工程结构设计.md#project-layout)。

<a id="configure"></a>

## 3. 环境与文件归属

vendor 固定框架版本；services/web/config/infra/deploy 的项目声明归业务项目。工具只在 vendor，运行状态和秘密在项目 .local，Python 每服务独立锁和环境。创建时 port-offset 同时偏移入口、PG、Redis、Nacos 和两业务端口。第一次 init 前若冲突，调整 config/development.yaml 中 local.port_offset 和两服务 port；已有环境改址必须人工审核，不删除卷重建。

<a id="startup"></a>

## 4. 初始化和运行

在项目根执行：

```powershell
python manage.py init --local
python manage.py dev equipment-service
# 另一个终端
python manage.py dev inspection-service
```

宿主不能解析 host.docker.internal，或 Linux 环境：init 增加 --dev-host <本机私网IP>。工具检查已有容器归属；不修改防火墙/hosts。初次依赖下载和基础镜像构建需网络。初始化阶段与失败合同见[基础设施设计](../design/03-基础设施与环境设计.md#local-development)。业务由宿主启动，首次运行不要求先构建业务镜像；工具探测宿主与容器两个方向。

<a id="identity"></a>

## 5. 账号、权限和管理页

打开 http://localhost:18080/identity/admin/。平台用户名 admin；初始密码在 .local/runtime/identity-bootstrap-secrets/admin-initial.password。开发租户 alpha/beta 各有 admin/writer/denied，密码在同目录 <租户>-<用户>.password；首次全部改密。writer 有双语示例权限，denied 无权限。先登录业务页创建/查询/访问 peer，再切租户和 denied 验证隔离。重复 init 不恢复人工修改的角色和密码；它不是生产开户或授权同步器。生产开户与授权使用管理页。

<a id="business"></a>

## 6. 编码与检查

业务改 services，Java 根 reactor + java-sdk，Python 独立 uv.lock + 固定源码 SDK；不手工 install-file，不准备 wheelhouse。定向检查、IDE 和规范链接见[开发升级指南](04-新项目开发与规范升级指南.md)。业务域、Agent、算法状态均不进入 identity-service。

<a id="add-service"></a>

## 7. 增加服务

运行 python manage.py add-service --language python --name scoring-service --package scoring --port 48085。Java 改 language/java 包名。按生成的服务 README 执行资源初始化/迁移、平台 audience 与客户端登记、权限发布、BFF 范围/租户角色设置和独立秘密绑定后启动。服务名派生唯一权限/路由；不修改框架。首次 init 不自动接管新增服务或给已有角色扩权。

<a id="deployment"></a>

## 8. 构建与发布

在项目根 build --release <版本> --output <新目录> 构建完整镜像；单服务用 --service，只是开发产物。项目运维提交固定输入、推镜像到获准仓库，填 deploy/release.yaml 负责人/确认记录/回退窗口；package-only 接受 --images、--env-file 和可选 --web-root，核对同次构建再收集部署包。完整参数见[开发升级指南](04-新项目开发与规范升级指南.md)。在 Linux/WSL 按包内 tools/deploy/ansible/README.md 初始化、迁移、发布；没有新增离线预载或发布平台。两台真实主机未验证。

<a id="upgrade"></a>

## 9. 升级与存量转换

gitlink 是框架源码唯一版本锚点。切换固定提交，调整必要 POM/SDK 约束并重锁，保留业务文件，验收后提交。旧制品项目人工加入源码引用和聚合入口，保留原服务名、权限、audience、账号、库/卷；不运行新项目 init。数据库迁移、兼容回退见[升级设计](../design/10-数据库迁移与升级设计.md#framework-upgrade)。

已有 rc.3 项目在独立分支/副本中转换，不能对原运行目录执行创建器：

1. 记录原 Git/发行摘要、环境文件、PROJECT_CODE、服务名、数据库名、Compose 项目名、卷名、Nacos namespace 以及账号/角色快照；备份与秘密留在受控目录，不复制进新仓库。
2. 加入 `vendor/micro-service` submodule 并 checkout 明确提交。根 POM 聚合 `vendor/micro-service` 和已有 Java 服务；只将业务 POM 的 parent relativePath 改为 `../../vendor/micro-service/pom.xml`，不改 artifactId、包名或 API。
3. Python pyproject 加入 `[tool.uv.sources]` 的 `ken-platform-sdk = { path = "../../vendor/micro-service/python-sdk", editable = true }`。删除旧 `uv.toml` 中只为 artifacts/wheels 设置的 find-links 选项；保留项目自己的索引策略。每服务执行 `uv lock`、`uv sync --frozen`，审查依赖变化。
4. 项目入口使用固定版本 `tools/generation.py` 中的薄入口约定，或直接调用 `vendor/micro-service/tools/cli.py --project-root .`。补齐 development.yaml 每服务的 language、directory、entry、package、port、peer；local.project 使用原 PROJECT_CODE，local.port_offset 仅记录开发端口组，local.initial_services 记原双语服务。该登记不授权执行首次 init，原运行绑定继续保留。
5. 按当前服务清单维护 `deploy/business.compose.yaml`，保留现有名字、运行 env/秘密目录和网络。原 config/infra/deploy 声明与 Web 保留；同名 Python 工具改为调用 vendor 固定实现。对不再引用的复制工具、旧 wrapper、artifacts 和 framework-baseline.json 做引用检查后再移除；旧发行清单归档保留。
6. 在副本进行定向构建，再用隔离恢复的数据库验证登录、角色、跨语言调用及旧数据读写。不能以“未改 SQL”代替数据验收；当前源码框架带 V10 新迁移，运行升级须单独执行身份迁移。
7. 只有上述验收通过后才提交 gitlink、POM、锁和工具入口，并构建新发行。原环境按正常兼容升级流程部署，不改库/卷名，不重新 bootstrap。

当前本轮尚未完成 rc.3 的隔离恢复运行验收，因此这份清单不是存量项目可直接上线的证明。

<a id="diagnostics"></a>

## 10. 排错和交付检查

缺 vendor 恢复 submodule；端口冲突换预先规划的端口组；ready 失败查 Nacos/DB/内省；容器不能访问宿主查注册地址/监听/防火墙。生成文件人工改动冲突时先比较，不删除秘密；迁移未知状态先核查。真实环境、运行与容量验收分开，详见当前实施计划。
