<a id="preparation"></a>

## 1. 开始前：交付物、角色和项目组合

本指南以聊天项目 `chat-assistant` 为主线，最后说明 Java/Python 文档分析组合。所有操作在新项目中完成，框架源码仓库用于维护和发行公共能力，不作为每个业务项目的工作目录。

| 项目类型 | 复制的业务示例 | 常驻应用 | 依赖 |
| --- | --- | --- | --- |
| 同步 HTTP 项目 | 一个 Java 或 Python API 示例 | identity、gateway、nginx、一个业务 API | PG、Redis、Nacos |
| 文档分析项目 | Java document-service、Python analysis-service，可选 web | 基础应用、document API、analysis API/Worker | 另加 Rabbit；对象存储可用外部服务 |
| 聊天项目 | Python agent-service，可选 web | 基础应用、agent API/Worker | PG、Redis、Nacos、Rabbit；文件能力再配对象存储 |

框架维护者提供同一发行标签的 Maven 包、Python 包、基础镜像、示例与运行材料归档、兼容说明和升级差异。项目负责人选择组合并维护复制文件；开发者实现业务；运维负责人提供服务器、域名、生产凭据和备份。没有可安装的发行物时不能用相对源码引用假装完成新项目接入。

本地前提：Docker Desktop 的 Linux 容器模式、Python 3.12、锁定版本 uv、制品仓库及镜像仓库可访问。纯全容器启动不要求宿主机安装 Java/Node。磁盘和内存按所选组件实际测试，不把某个固定机器规格当全部项目的最低承诺。

<a id="create-project"></a>

## 2. 创建项目并确认文件归属

下载经校验的同标签运行材料，将选定示例复制到独立项目目录：

| 发行材料 | 新项目位置 | 后续归属 |
| --- | --- | --- |
| examples/python/agent-service | agent-service | 项目自己的算法、工具、提示词和业务接口 |
| examples/web | web（可选） | 项目聊天界面；无需复制身份管理页 |
| config | config | 环境绑定、Nacos 参数与发布工具 |
| infra | infra | 选用的依赖组件、资源声明、初始化入口 |
| deploy | deploy | 选用的应用组合、Nginx 与发布入口 |
| 根工具 pyproject.toml、uv.lock | 项目根目录 | config/infra/deploy 共用的工具环境 |
| 发行基线清单 | 框架基线记录 | 为后续三方升级比较保留原始版本 |

将项目代码改为 chat-assistant，包名、镜像名、数据库名、namespace、vhost 按样例标注的项目字段修改；依赖版本仍用发行锁定值。删减组合必须按发行的选型清单完成，不手工猜测一个脚本是否还能删除。示例业务改名后同步服务逻辑名、路由、权限所属应用和发布清单。

**结果检查：** 项目没有 foundation/identity-service/api-gateway/python-sdk 的源码副本；Java 使用制品依赖，Python 使用包版本；管理页来自 identity 镜像。业务源码无指向框架开发目录的相对路径。若示例构建只能在原框架仓库完成，接入验收失败。

<a id="configure"></a>

## 3. 填写环境与秘密引用

以下步骤均在新项目根目录。先复制样例，不把真实值写回 example：

```powershell
New-Item -ItemType Directory -Force .local
Copy-Item config/environments/local.env.example .local/environment.env
uv sync --frozen
```

填写 PROJECT_CODE、APP_ENV=local、PUBLIC_ORIGIN（如 http://localhost:18080）、所选服务/数据库/namespace/vhost 名称、端口和依赖模式。全容器内使用服务名或约定网络地址；不能把宿主机的 localhost 写成其他容器的地址。各服务秘密通过独立 *_SECRET_FILE 引用。

`infra/resources.yaml` 声明本项目要创建/校验的数据库、角色、namespace 和 vhost；组件本身是自建还是外部实例在环境绑定中确定。外部依赖由管理员预建时记录资源归属，初始化只验证，不能把第三方的集群超级管理员秘密分发给业务容器。

**结果检查：** 实际环境和秘密被版本控制忽略；未填写的必要字段有明确错误；所选组合没有无关服务的秘密挂载。锁文件安装失败先检查仓库凭证和版本可达性，不临时取消 --frozen 绕过发行基线。

<a id="startup"></a>

## 4. 首次启动操作步骤

以下命令展开[首次安装设计](../design/09-应用部署与运维设计.md#first-install)；服务名和参数来自[固定入口](../design/09-应用部署与运维设计.md#execution-entrypoints)，不在本指南另定合同。

以 chat-assistant 为例，从同一发行标签复制 examples/python/agent-service、所需 examples/web 和 config/infra/deploy 基线。examples/README 提供同步 HTTP、文档分析、聊天三种已验证组合及必选文件清单；不让开发者从全套组件中猜依赖。复制后项目自己建仓库；框架源码不进入项目。

准备 Docker Desktop（Linux 容器）、Python 3.12、uv 和可访问的制品/镜像仓库；首次全容器运行不要求宿主机 Java/Node，IDE 开发对应语言时再安装锁定版本。修改项目编码、Python 包名、SDK 固定版本、数据库名/账号名、namespace、Rabbit vhost、基础镜像和示例镜像引用；复制示例已带 uv.lock，改依赖后重新锁定并审阅差异。框架发布的运行示例镜像用于首次冒烟，业务开发后改用项目自己构建的同角色镜像。

目录位置与分层规则见[工程目录](../design/01-总体架构与工程结构设计.md#project-layout)和[编码规范](../standards/01-项目编码规范.md#structure)。示例按所选组合复制，不在指南维护第二份目录规范。

| 步骤 | 谁执行 / 输入 | 成功后的可观察结果 |
| --- | --- | --- |
| 1. 准备本地文件 | 开发者复制环境样例到 .local，选择项目组合 | APP_ENV=local、端口、卷名前缀与项目对应；无其他环境凭据 |
| 2. 准备网络与秘密 | infra/init 的 prepare-local 固定阶段 | 创建该项目 external network 和本地随机凭据；已有凭据保留，重复执行安全 |
| 3. 启动第三方依赖 | Docker Compose 启动 infra | 所选依赖健康；持久卷存在，连接可用 |
| 4. 初始化环境资源 | infra/init 使用管理凭证 | identity/agent 库与各级账号、Nacos namespace、Rabbit vhost/账号可用 |
| 5. 发布 Nacos 配置 | config/publish.py 校验 config/nacos | 目标 Data ID 存在并记录摘要，不改其他环境 |
| 6. 所选数据库迁移与身份 bootstrap | identity-migrate、agent-migrate、identity-bootstrap 一次性容器 | schema/RLS、平台账号、固定管理客户端及发布身份已建立 |
| 7. 启动基础应用 | identity-service、api-gateway、nginx | 本地入口能打开管理页并登录；业务 Web 未运行也可管理 |
| 8. 业务权限目录同步 | sync-permissions.py | 目录可见但未授予；所选数据库迁移已在步骤 6 完成 |
| 9. 管理员配置 | 创建租户/账号/角色及业务客户端；填写对应秘密和模型配置 | 账号和权限可查询；假模型模式不要求真实模型密钥 |
| 10. 启动与验证 | 同版 agent-api、agent-worker、可选业务 Web | 完成一次提交、执行、流式输出、取消和越权拒绝 |

身份相关资源发布必须在 identity-service 已 ready 后进行；不能先调用不存在的权限 API。基础角色、用户创建与注册都是身份服务职责，业务项目不直接向身份表插数据。

拟提供的 Windows 操作形态如下；文件、脚本和镜像均由实施计划交付，本指南命令尚未运行：

```powershell
New-Item -ItemType Directory -Force .local
Copy-Item config/environments/local.env.example .local/environment.env
uv sync --frozen
uv run --frozen python infra/init/run.py --env-file .local/environment.env --phase prepare-local
docker compose --env-file .local/environment.env -f infra/compose.yaml up -d
uv run --frozen python infra/init/run.py --env-file .local/environment.env --phase resources
uv run --frozen python config/publish.py --env-file .local/environment.env --source config/nacos
docker compose --env-file .local/environment.env -f deploy/compose.yaml run --rm identity-migrate
docker compose --env-file .local/environment.env -f deploy/compose.yaml run --rm agent-migrate
docker compose --env-file .local/environment.env -f deploy/compose.yaml run --rm identity-bootstrap
docker compose --env-file .local/environment.env -f deploy/compose.yaml up -d identity-service api-gateway nginx
uv run --frozen python deploy/scripts/sync-permissions.py --env-file .local/environment.env --manifest deploy/release.yaml
# 暂停：按本指南第 6 节完成租户、角色、用户和业务客户端登记，再启动业务。
docker compose --env-file .local/environment.env -f deploy/compose.yaml up -d agent-api agent-worker
```

顺序中的固定入口都必须先等待健康/就绪、核对项目和环境再执行；失败停止并保留阶段结果，不能让操作者盲目复制下一条命令。配置/infra/deploy 辅助工具共用项目根 pyproject.toml/uv.lock 的工具环境，不分别建立三个工具包；业务服务和 SDK 仍各自锁依赖。Ansible 依赖仅在 Linux/WSL 管理环境安装并冻结，不让 Windows 日常启动依赖它。Compose 的 migrate/bootstrap 等维护角色不随普通 up 自动运行。这里是少量固定任务入口，不建设通用命令平台。

<a id="diagnostics"></a>

## 5. 逐阶段判断成功与排查失败

上一节命令必须逐步执行，任何阶段失败停止后续步骤。实现交付必须提供等价的受控自动执行入口和清晰阶段结果；文档中分步列出是为了可诊断，不要求每次发布都手工逐机操作。

| 步骤 | 执行位置与前提 | 完成标志 | 失败检查 |
| --- | --- | --- | --- |
| prepare-local | 项目根目录；local 环境文件已校验 | external network 存在，所需秘密文件已生成或验证，已有秘密未改写 | 路径权限、已有网络归属、端口冲突；不删除其他项目网络 |
| infra up | 本地 Docker；依赖模式已选 | 所选自建组件健康、卷正确，外部组件没有被重复创建 | compose logs、端口和挂载；up 返回不等于全部 ready |
| resources | 组件已就绪；仅此入口拥有初始化权限 | 逐项 CREATED/VERIFIED 或明确 CONFLICT/FAILED，业务运行角色可连接 | DB 名/owner、namespace、vhost、外部预建资源权限 |
| publish | namespace 已存在；非敏感配置通过 schema 校验 | Data ID、版本与内容摘要入记录 | 秘密误入、来源错误、漂移；不强制覆盖线上改动 |
| identity-migrate | 空库或可升级旧库；迁移账号可用 | 迁移历史/摘要/schema/RLS 正确 | 锁、历史校验、DDL；不能启动应用自动 repair |
| identity-bootstrap | 迁移已成功；初始化秘密就绪 | 平台初始账号、固定客户端及目录建立；重复执行只校验 | 冲突资源、缺秘密、管理员初始口令流程 |
| 基础应用 up | schema/配置/客户端已就绪 | identity/gateway ready；公开入口可访问管理登录 | 网络、issuer、BFF 内部地址、Cookie/CSRF |
| agent-migrate | agent 数据库与迁移账号已建 | runtime 后 app 迁移成功，兼容组合有效 | 双锁/双 head、SDK 与业务 schema 不兼容 |
| sync-permissions | identity ready；release 清单和服务权限清单匹配 | 本项目资源操作可在管理页查看，新项未自动授出 | 控制面身份、应用所属租户范围、目录版本冲突 |
| 业务应用 up | 用户/角色/客户端和模拟模型已配置 | API ready、Worker 可领取，完成一次完整 Run | 模型配置、Rabbit、Worker 版本、未授权用户 |

辅助观察命令同样在项目根目录：

```powershell
docker compose --env-file .local/environment.env -f infra/compose.yaml ps
docker compose --env-file .local/environment.env -f deploy/compose.yaml ps
docker compose --env-file .local/environment.env -f deploy/compose.yaml logs --tail 100 identity-service api-gateway
docker compose --env-file .local/environment.env -f deploy/compose.yaml logs --tail 100 agent-api agent-worker
```

日志可能含项目数据，分享前脱敏；不能以打印 environment.env 或全部秘密来检查配置。

## 6. 在管理页面初始化租户、用户、角色和应用

1. 用 bootstrap 产生的受控初始凭据进入 `/identity/admin/` 的平台入口；按首次改密流程完成初始化。平台管理员创建租户并设置租户管理员，不自动取得该租户业务数据访问权。
2. 从租户入口登录。确认本租户的权限目录已由发布步骤同步，选择 agent 应用对应的资源/操作创建业务角色，设置其支持的数据范围。示例具体权限编码以示例 permissions.yaml 为准，不能只在页面新写一个编码当作接口已保护。
3. 创建普通业务用户并分配角色。管理委派属于 R-01 待确认；确认纳入后分别配置可分配角色、可编辑范围和授权上限；避免直接给业务用户全局管理员角色。
4. 通过应用页校验业务 Web 的 confidential BFF 客户端，精确登记 PUBLIC_ORIGIN 下的回调、允许 scopes 和 audiences。按示例登记说明由管理页面（调用身份 API）创建业务 BFF、机器及每个资源服务的内省客户端；将一次性秘密写入对应受控文件，再加载到调用方。重复安装核对已有登记，不生成新秘密覆盖。sync-permissions.py 只发布权限目录，不承担这一步；不人工写身份数据库。
5. 按需配置机器客户端、第三方登录提供方和注册策略。默认 ADMIN_ONLY；INVITE/OPEN 须先确认 R-02 纳入，之后开启前先配置邮件，明确初始角色和激活流程。外部 OAuth 应用需独立登记并走授权同意。
6. 使用普通用户登录业务页，检查 /me、一个允许动作和一个拒绝动作；然后禁用账号，验证新请求拒绝和长连接按设计撤权。
7. 创建另一个租户及同名账号，确认两者独立。主动尝试跨租户文档/会话 ID，必须被拒绝。

**成功标准：** 新项目的管理界面不改源码就能管理上述对象；业务团队只开发自己的聊天/文档页面。若给项目增加一个资源就要改管理前端，说明权限目录接入没有按合同实现。

<a id="business"></a>

## 7. 开发业务与完成聊天验收

项目自行实现 Agent 图/流程、Prompt、模型/工具适配、业务数据、业务权限和用户体验；框架承接身份、隔离、发现、消息、Run 状态、事件、租约和检查点。修改工具副作用或恢复策略属于业务合同变化，不能只改提示词。

先使用示例模拟模型验证：提交一次消息取得 Run；收到有序流式事件；断开重连后从游标续读且不重复执行；从另一 API 节点读取同一 Run；取消后不再发起新工具；工具需确认时旧版本批准不能用于新输入。再接真实模型验证输出质量、超时、配额和费用。

扩容 API/Worker 使用同一镜像不同运行角色；容器数量、数据库权威状态和恢复约束见[聊天 Agent 多节点设计](../design/08-聊天Agent多节点设计.md)。单机多进程通过不等于真实多机验收，必须另外验证跨主机发现与故障恢复。

<a id="add-service"></a>

## 8. 增加 Java 或 Python 服务

以增加文档分析为例：

1. 从同版 examples 选取 document-service / analysis-service，改包名和项目领域逻辑；不另建通用业务网关。
2. 给每个服务登记逻辑名、数据库/运行与迁移账号、秘密引用；在资源声明中增加资源，重新执行 resources 只创建新增项。
3. 在 config/nacos 新增该服务技术参数；在服务自身维护 permissions.yaml、Flyway/Alembic 和事件 schema；权限和迁移不移动到 deploy。
4. 更新 deploy/release.yaml 的应用、镜像、迁移入口、健康检查、主机角色；同步 Compose 与显式 Gateway 路由。若使用 Rabbit/对象存储，先补依赖与受控权限。
5. 先迁移新服务，再登记权限/客户端并配置角色，最后启动新服务做跨语言验证。
6. Java 提交文档任务，Python 执行分析，Java 接受结果；验证重复消息、迟到结果和跨租户拒绝。详见[Java 与 Python 协作设计](../design/07-Java与Python协作设计.md)。

新增服务不要求修改 identity 管理页面，不允许复用另一个业务服务的数据库账号，也不能依靠直接跨库读取减少 API 设计。

<a id="deployment"></a>

## 9. 从本地进入测试和生产

测试/生产使用独立环境、数据库、namespace、vhost、OAuth 客户端及秘密。选择测试环境的 config/environments/test/hosts.yaml，填写 Linux 主机角色与内网地址；PUBLIC_ORIGIN 换成真实 HTTPS 入口，禁止复用 local HTTP Cookie 策略。通过实际域名校验回调、代理头和证书。

构建业务镜像并固定 digest，形成 release 清单；同一产物逐环境晋级，不在生产机器重新构建。Linux/WSL 控制机按[应用部署与运维设计](../design/09-应用部署与运维设计.md#releases)执行基础设施安装、资源初始化、迁移、分阶段应用部署。首次安装必须先启动 identity 并等待 ready，再执行业务目录同步；四个 playbook 的粗粒度名称不能掩盖这个依赖。

生产前确认数据备份可恢复、入口/秘密访问范围、两台主机的注册可达性、实际镜像摘要和监控。普通应用更新只发布受影响应用；需要基础设施维护时另开明确维护范围。没有服务器和真实提供方凭据时，只能标记相应验证未执行。

## 10. 升级框架与接入责任核对

| 需求 | 直接复用 | 项目开发内容 |
| --- | --- | --- |
| 用户/租户/角色/邀请注册 | identity 镜像及管理页 | 配置注册模式/初始角色；业务档案用激活事件幂等初始化 |
| Java API | foundation 的身份/租户/HTTP/DB/MQ 适配 | DTO、controller、service、DAL、业务迁移及权限校验落点 |
| Python Agent | SDK 的 Run、租约、事件、检查点和工具账本 | Graph、提示词、领域工具、上下文、业务会话/消息与页面 |
| 新业务权限 | 通用资源操作管理页 | 服务自带 permissions.yaml 与 scope 映射；发布后管理员明确授权 |
| 服务间调用 | 官方 HTTP 客户端与 SDK 发现/身份/超时 | 领域客户端和输入输出；不传 JVM/Python 对象 |
| 业务前端 | BFF 登录/退出和按应用过滤的 /me | 页面和按钮状态；服务器权限不由前端代替 |
| 运维接入 | config/infra/deploy 的同版材料 | 环境和秘密、主机/容量、业务烟测、备份责任人 |

新增 Java 服务从 examples/java 复制独立 Maven 工程，依赖固定 platform-parent/foundation，关闭 parent 本地 relativePath；Python 服务依赖 ken-platform-sdk 及所需 extras。不引用框架源码绝对路径，不增加每实体一个微服务。

新增持久化服务先通过 infra/init 增量建库/账号，再迁移表；有消息则登记本服务拓扑和账号；在 config/nacos 增加本服务参数，在 Gateway 配置增加受限公开路由，发布其权限并登记 audience/scopes/内省身份，最后启动服务。不为每个新服务重新部署 PG，不复制用户权限源码。已有系统按[存量数据接入与 RLS 切换](../design/10-数据库迁移与升级设计.md#legacy-tenancy)另行迁移；新项目创建不自动迁入旧系统。

升级依赖、基础镜像和复制运行材料是三个动作：业务代码不会被示例覆盖；身份页随身份镜像升级；配置/infra/deploy 根据原基线、新基线、项目现状三方比较。迁移、测试、分批发布及回退步骤统一执行[数据库迁移与升级设计](../design/10-数据库迁移与升级设计.md#project-upgrade)。

接入交付时保留：项目组合、基线版本、独立制品安装记录、首次启动记录、两租户隔离结果、管理页零改动证据、业务成功/失败链路、部署环境说明。以上不是要求业务重新开发基础功能，而是证明这一个项目正确使用了框架。
