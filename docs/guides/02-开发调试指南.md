## 1. 调试前提与两种模式

先按[新项目接入指南](01-新项目接入指南.md)完成一次全容器启动，再切 IDE。全容器是发行基准；IDE 只替换当前调试的业务进程，PG/Redis/Nacos、identity、gateway、nginx 仍可保留容器运行。

每个开发者默认独立 local 依赖和 namespace。共享测试环境不得注册个人 IDE 实例；否则 Gateway 可能把其他人的请求路由到个人电脑。调试某个基础服务属于框架维护场景，必须使用框架对应模块，不要求普通项目复制它的源码。

下面的命令使用[部署设计定义的固定入口与参数](../design/09-应用部署与运维设计.md#execution-entrypoints)，使用发行包内实际存在的 dev.py / dev.ps1 / dev.sh；先构建对应业务，随后启动，不自动迁移或安装依赖。

<a id="addressing"></a>

## 2. 地址、issuer、回调和容器连通

地址与模式规则由[基础设施设计](../design/03-基础设施与环境设计.md#local-development)定义，Cookie/issuer 的 local 例外由[认证设计](../design/05-认证与OAuth2设计.md#origins)定义。此处按规则操作，不另定义安全例外。

先从 `.local/environment.env` 核对 PUBLIC_ORIGIN 和 IDENTITY_INTERNAL_ORIGIN。浏览器打开前者；从 Gateway 容器验证后者可达。切 IDE 时只修改 local-host 文件中允许的宿主地址、监听及注册地址；登录回调仍以原 PUBLIC_ORIGIN 为准。随后分别验证容器到 IDE、IDE 到依赖、浏览器经入口到业务三条路径，不能以本机 curl 成功代替。

<a id="switching"></a>

## 3. 准备宿主机覆盖与切换步骤

从 config/environments/local-host.env.example 复制服务专属 `.local/<service>-host.env`。EnvFile 指向 `.local/runtime/<service>.env`，不用组件管理员 environment.env。填该服务宿主秘密文件的绝对路径、PG/Nacos 映射地址、监听及发布端口；不可覆盖项目、租户 namespace、数据库名/用户或 PUBLIC_ORIGIN。

混合调试先按 [examples 的宿主说明](../../framework/examples/README.md#混合调试)准备 compose.host.yaml 与 DEV_HOST；身份与被调业务的发现地址都必须能从宿主和容器到达。Docker Desktop 的 host.docker.internal 不能假设在 Windows DNS 中也有效。先从两侧验证解析与端口，不自动改系统 hosts/防火墙，不复制生产秘密。

切换步骤：停止目标容器 → 等待 Nacos 摘除 → 启动 IDE 进程 → 确认登记地址可从 Gateway 到达 → 经 PUBLIC_ORIGIN 实际调用。恢复容器时反向执行，避免两个实例同时收到调试流量。

本地入口输出 service、local 环境和注册地址；不打印密码、token 或 secret 文件正文。环境文件有冲突或覆盖白名单外字段时拒绝启动，而不是“后面那个覆盖前面那个”。

## 4. Java 服务调试

先在 config/development.yaml 登记自己的服务目录、Java JAR 相对路径或 Python console entry。Java 使用 JDK 21，先按 examples 编译；Python 使用业务自己的虚拟环境。工作目录为独立项目根：

```powershell
# 组合文件及端口以当前项目为准；先完成混合网络准备。
docker compose --env-file .local/runtime/compose.env -f deploy/compose.yaml -f examples/compose.yaml --profile java stop sample-java-service
./deploy/scripts/dev.ps1 -Service sample-java-service -Role api -EnvFile .local/runtime/sample-java-service.env -HostEnvFile .local/java-host.env -Check
./deploy/scripts/dev.ps1 -Service sample-java-service -Role api -EnvFile .local/runtime/sample-java-service.env -HostEnvFile .local/java-host.env
```

IDE 可以使用同一套运行字段；需要 Java 远程断点时在本地服务运行绑定显式配置 JDWP，再从 IDE attach。固定入口不包含通用命令解释器；数据库仍由迁移入口维护。

断点验证 Controller → Service → DAL，以及 Java 调用 Python 时的 trace/主体/租户/错误码；数据库连接池复用后再次发送另一个租户的请求，检查上下文没有泄漏。IDE 命中断点会导致请求超时，不能据此把生产所有超时改成无限。

### JDBC 服务进程绑定

依照[配置来源](../design/02-配置与服务发现设计.md#sources)和[初始化资源与数据库身份](../design/03-基础设施与环境设计.md)为每个 JDBC 服务单独注入 `PG_HOST/PG_PORT/DB_NAME/DB_USER/DB_PASSWORD_SECRET_FILE`；名称取资源初始化的解析结果，密码引用使用该服务 runtime 账号秘密文件的绝对路径。不能把初始化环境中的管理员、迁移账号或发布凭据整份传给应用。Gateway 不引入 JDBC，也不要求这些数据库字段。

当前 Java 装配会从上述引用建立受控 PG 连接，关闭运行时 Flyway、SQL 初始化及 JPA 自动 DDL；不接受额外 `spring.datasource.*`、`JDBC_URL` 或明文 `DB_PASSWORD` 作为第二来源。local 使用本地 PG 连接；test/prod 的实际 TLS 证书、JVM 信任及网络需按部署阶段验证，配置检查通过不能替代真实握手。

启动前核对实际连接的数据库、会话身份及最小权限，身份不符或持有建库、建角色、绕过 RLS、schema/table 所有者等权限时停止启动。排错先检查资源解析结果、runtime 秘密文件权限及初始化/迁移结果，不能改用管理员恢复启动。已就绪进程可检查 `/actuator/health/liveness` 与 `/actuator/health/readiness` 的最小状态响应；实际验证见当前精简实施计划，不能引用冻结计划批次作为本次发行验收。

重新打包仅有依赖变化的可执行 JAR 时使用 `'-Dmaven.jar.forceCreation=true'`，并核对嵌套依赖与本轮构建内容，避免增量打包继续保留旧公共包。该参数不跳过格式、编译或测试要求。

### 身份签名秘密文件

本节操作落实[认证设计的持久密钥与轮换规则](../design/05-认证与OAuth2设计.md#failures)。工作目录为 `framework`，前提为 JDK 21、已打包的 `identity-service/target/identity-service.jar` 和仅运维/身份服务账户可读的秘密目录。下面用 Windows 绝对路径示意，执行时替换为已配置 ACL 的真实目录；Linux 同样使用绝对路径，工具创建文件时权限为 0600。秘密文件仅挂载给身份进程，不提交 Git 或上传 Nacos。

```powershell
# 首次离线生成；不启动 Spring，也不连接数据库/Nacos。
java '-Dstdout.encoding=UTF-8' '-Dstderr.encoding=UTF-8' '-Dloader.main=com.ken.platform.identity.service.oauth.SigningKeyTool' -cp identity-service/target/identity-service.jar org.springframework.boot.loader.launch.PropertiesLauncher create C:/controlled-secrets/identity-signing.json
# 轮换写到新的文件，原文件不会覆盖；保留原有公钥，只携带新私钥。
java '-Dstdout.encoding=UTF-8' '-Dstderr.encoding=UTF-8' '-Dloader.main=com.ken.platform.identity.service.oauth.SigningKeyTool' -cp identity-service/target/identity-service.jar org.springframework.boot.loader.launch.PropertiesLauncher rotate C:/controlled-secrets/identity-signing.json C:/controlled-secrets/identity-signing-next.json
```

在身份服务环境中设置 `IDENTITY_SIGNING_JWK_SECRET_FILE` 为最终受控文件的绝对路径；经环境文件解析的相对引用会规范为绝对路径。运行时只读一次完整快照，不自动生成或在请求中刷新。文件是带 `active_kid` 的 JWK Set：`keys` 中当前条目包含 RSA 私钥，其余条目仅有公钥，每条有唯一 `kid`、`use=sig`、`alg=RS256`；工具生成 RSA 3072，加载最低 2048 位，文件最大 64 KiB。不得把示意或占位内容当密钥使用。

轮换时先交付保留旧公钥的新文件，再按项目维护流程将身份实例切换到该文件并重启；核对 `/oauth2/jwks` 的新旧公钥及新签名 `kid`。旧验证公钥的保留时长按权威设计执行，不由工具自行删减；旧私钥文件按秘密保管流程留在离线受控存储。多实例必须先部署同一密钥集，跨主机/滚动轮换仍需部署阶段验收。缺失、重复 `kid`、未知类型、弱密钥、公私钥不匹配或退役私钥残留均拒绝加载；错误只返回稳定提示。生成失败退出码 2，不输出路径/密钥；检查输出是否已存在、源文件是否合法及目录权限，禁止为恢复启动而生成临时替代密钥。

## 5. Python 服务调试

先在全容器组合确认业务能调用，再停止选中的业务 API 容器，使用该服务自己的 uv 环境启动同一入口。只覆盖监听、发布和连接地址；project/env/issuer/权限配置不随调试修改。固定 dev 入口和参数以[部署设计](../design/09-应用部署与运维设计.md#execution-entrypoints)为准，实际可用命令以示例验证记录为准。

Windows psycopg 3 异步 DB 使用 SDK 的 database_loop_factory；不在导入 SDK 时更改全局事件循环。Java 子进程用例仍保留支持子进程的循环。根工具环境仅供运维脚本，不能混作业务环境。

一般 HTTP 服务只有 API 角色。多个实例使用不同端口/instance_id；退出注销并清理上下文。具体业务若自建 Worker/Agent，由该项目决定执行组件与调试方法，不属于框架接入前提。

## 6. 业务前端热更新与身份页维护

业务项目在 web 目录按 pnpm-lock 安装并启动 Vite；local Nginx 将业务页面及明确的 HMR 路径代理到 DEV_HOST。浏览器仍从 PUBLIC_ORIGIN 打开页面，BFF/API/identity 路径继续走 Gateway，避免端口变化破坏 OAuth 精确回调和 Cookie。

修改身份管理页面是框架维护工作：在 identity-service/admin 中安装/检查/构建，验证产物被 Java 镜像打包。项目自己的 web 不引入管理 npm 包，也不复制管理员用户/角色页面。

框架维护者使用 Node **24.13.0**、pnpm **11.12.0**；依赖版本与完整性锁定在 package.json/pnpm-lock.yaml，安装不运行依赖生命周期脚本。在 `framework/identity-service/admin/` 的 PowerShell 执行（测试文件按当前改动选择，下面是个人账号范围）：

```powershell
pnpm.cmd install --frozen-lockfile --ignore-scripts
pnpm.cmd exec vitest run tests/identity-api.test.ts tests/account-page.test.ts
pnpm.cmd run verify:build
```

`verify:build` 执行 vue-tsc、零警告 ESLint/Prettier 和 Vite 生产构建；输出位于 `identity-service/target/generated-resources/static/identity/admin/`，生成文件不提交。完成本次 Java 定向测试后，在 `framework/` 打包可用 `./mvnw.cmd -B -pl identity-service -am package '-Dmaven.jar.forceCreation=true' '-DskipTests'`；这个命令只打包，不代表 Java 测试通过。Maven 会再次核对冻结安装、前端检查/构建，并要求生成首页存在。身份镜像先用固定 Node 镜像构建界面，再在 Java 构建阶段复制产物；最终 JRE 不需要 Node/pnpm，业务项目使用已验证发行镜像即可。

通过同一 PUBLIC_ORIGIN 打开 `/identity/admin/` 或 `/identity/admin/account`。选择平台或租户入口，租户填写组织代码；账号密码、首次改密在身份服务模板内完成，再回到管理界面。个人页管理显示名、密码、本人会话和应用同意；写入使用当前 BFF CSRF，401 重新登录，403 显示拒绝，409 保留草稿并对比当前资料，结果未知不自动重试。页面路径之外的未知静态文件和 API 不回退成首页。调试 Vite 时也必须保留同源 Gateway/BFF 路径，不能用开发端口替换已登记回调。

验收包括：热更新可用；登录、刷新、退出可用；业务 SPA fallback 不吞 identity/API 路由；普通用户调用无权管理的接口仍被服务端拒绝。匿名入口和个人账号页面不授予管理权限。仅页面显示“登录成功”不能替代会话和后端授权检查。

## 7. 测试数据与定向验证

本地数据通过身份管理 API/页面和业务 API 建立，示例提供可重复的开发数据入口。数据只能写入声明的 local 环境，必须有明显保护；不允许给生产自动建立测试租户。开发数据不改变迁移历史，也不包含真实用户隐私。

定向验证按改动选择：Java 服务执行其模块/测试过滤；Python 在该服务目录执行对应 pytest 文件；前端执行受影响组件/流程检查。完成当前实现后集中运行相关测试及适用 lint/typecheck/build，不默认跑整个框架套件。

身份/租户变更必须验证失败路径。只运行受影响定向测试，不以 mock 代替真实依赖验证；规则见[编码规范](../standards/01-项目编码规范.md)。

## 8. 故障定位对照

| 现象 | 首先检查 | 不能采取的捷径 |
| --- | --- | --- |
| Gateway 502，但 IDE 本机可访问 | Nacos advertised 地址、容器到宿主端口、防火墙、旧实例 | 把注册地址固定为 127.0.0.1 |
| 登录后回调失败 | PUBLIC_ORIGIN、精确回调、可信代理头、state、Cookie | 开启任意回调通配 |
| BFF 换 token 失败 | IDENTITY_INTERNAL_ORIGIN 在容器内是否可达、issuer 校验 | 关闭 issuer 校验 |
| Nacos 修改未生效 | 字段归属、发布摘要、热更新白名单、是否需要重启 | 重复放入 env/Nacos 试覆盖 |
| 403 | 用户角色、客户端 scope/audience、租户能力 | 临时移除后端鉴权 |
| 可选消息未消费 | Outbox、broker、业务消费者、隔离队列 | 无限重投掩盖业务失败 |
| SSE 卡住 | 业务事件来源、代理缓冲、心跳与超时 | 无条件重发有副作用请求 |
| 修改后数据库报错 | 已执行迁移、schema 兼容、迁移账号/运行账号 | 修改历史迁移或开启自动建表 |
| 切换租户后数据混杂 | principal、事务租户上下文、连接 reset、缓存 key | 前端过滤掩盖后端泄漏 |

排查顺序沿 trace/request 从入口到实际写入；区分已证实事实、候选原因和缺失证据。共享日志前移除凭据及业务敏感内容。

<a id="reset"></a>

## 9. 停止、恢复和明确重置

日常结束使用 Compose stop 或停止 IDE，保留卷和本地秘密；恢复时沿初始化检查点核对，不需要重建租户。切回容器先关闭 IDE 进程、确认实例摘除，再对指定服务 up -d。

只有明确要删除本地数据才执行重置维护流程：核对 PROJECT_CODE/APP_ENV=local、实际网络/卷/目录清单、备份需要，明确列出将删除的数据并确认；使用具体资源名操作。测试/生产环境不开放 local reset。禁止把 `down -v` 写进普通启动、调试或升级命令。

新增业务数据库使用 resources 的增量初始化；丢失本地秘密不能自动生成新密码后假装旧数据库可用，应核对现有资源并执行明确的凭据轮换或受控重置。
