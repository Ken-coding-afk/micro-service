## 1. 调试前提与两种模式

先按[新项目接入指南](01-新项目接入指南.md)完成一次全容器启动，再切 IDE。全容器是发行基准；IDE 只替换当前调试的业务进程，PG/Redis/Nacos、identity、gateway、nginx 仍可保留容器运行。

每个开发者默认独立 local 依赖和 namespace。共享测试环境不得注册个人 IDE 实例；否则 Gateway 可能把其他人的请求路由到个人电脑。调试某个基础服务属于框架维护场景，必须使用框架对应模块，不要求普通项目复制它的源码。

下面的命令使用[部署设计定义的固定入口与参数](../design/09-应用部署与运维设计.md#execution-entrypoints)，均为待实现的操作示例。

## 2. 地址、issuer、回调和容器连通

地址与模式规则由[基础设施设计](../design/03-基础设施与环境设计.md#local-development)定义，Cookie/issuer 的 local 例外由[认证设计](../design/05-认证与OAuth2设计.md#origins)定义。此处按规则操作，不另定义安全例外。

先从 `.local/environment.env` 核对 PUBLIC_ORIGIN 和 IDENTITY_INTERNAL_ORIGIN。浏览器打开前者；从 Gateway 容器验证后者可达。切 IDE 时只修改 local-host 文件中允许的宿主地址、监听及注册地址；登录回调仍以原 PUBLIC_ORIGIN 为准。随后分别验证容器到 IDE、IDE 到依赖、浏览器经入口到业务三条路径，不能以本机 curl 成功代替。

<a id="switching"></a>

## 3. 准备宿主机覆盖与切换步骤

从 config/environments/local-host.env.example 复制 `.local/local-host.env`，仅覆盖宿主运行服务的地址字段。设置 DEV_HOST 为容器可达的宿主地址，配置 SERVICE_BIND_HOST/PORT 与 SERVICE_ADVERTISE_HOST/PORT；连接本机组件用其映射端口。先验证容器能连接 DEV_HOST 对应端口，再启动注册。不要把生产秘密复制到本机排错。

切换步骤：停止目标容器 → 等待 Nacos 摘除 → 启动 IDE 进程 → 确认登记地址可从 Gateway 到达 → 经 PUBLIC_ORIGIN 实际调用。恢复容器时反向执行，避免两个实例同时收到调试流量。

SDK/启动入口必须打印脱敏后的 service/instance、有效地址、配置摘要和运行角色；不打印密码、token 或 secret 文件正文。环境文件有冲突或覆盖白名单外字段时拒绝启动，而不是“后面那个覆盖前面那个”。

## 4. Java 服务调试

以新项目中的 document-service 为例，先停止 Compose 对应实例，再使用固定入口或同等 IDE Run Configuration：

```powershell
docker compose --env-file .local/environment.env -f deploy/compose.yaml stop document-service
./deploy/scripts/dev.ps1 -Service document-service -Role api -EnvFile .local/environment.env -HostEnvFile .local/local-host.env
```

前提是 Java 21 与 Maven Wrapper 就绪，固定入口从发布清单找到服务目录，执行该服务约定的 Spring Boot 开发入口并注入环境；IDE 运行配置使用同一加载逻辑。数据库迁移仍由独立入口完成，不能打开自动 DDL“方便调试”。

断点验证 Controller → Service → DAL，以及 Java 调用 Python 时的 trace/主体/租户/错误码；数据库连接池复用后再次发送另一个租户的请求，检查上下文没有泄漏。IDE 命中断点会导致请求超时，不能据此把生产所有超时改成无限。

## 5. Python API、Worker 与模型调试

Agent 图或工具代码变更时同时替换 API/Worker：

```powershell
docker compose --env-file .local/environment.env -f deploy/compose.yaml stop agent-api agent-worker
./deploy/scripts/dev.ps1 -Service agent-service -Role api -EnvFile .local/environment.env -HostEnvFile .local/local-host.env
```

在第二个终端运行：

```powershell
./deploy/scripts/dev.ps1 -Service agent-service -Role worker -EnvFile .local/environment.env -HostEnvFile .local/local-host.env
```

入口进入 agent-service 自己的 uv 环境执行固定模块；根目录 uv 环境只给运维工具用。角色名映射到发行清单的启动命令，Worker 不注册成 HTTP 实例。常规 Python HTTP 服务只启用 api 角色，不为没有任务的服务强制创建 Worker。

调试时保留 Run/attempt/graph_version。暂停 Worker 超过租约后，其恢复写入应被拒绝，这是正确行为，不能禁用 fencing 来迁就断点。需要观察完整成功链路时使用可控模拟模型和较短步骤；需要验证失联时有意暂停进程并记录新旧 attempt。

只调普通 HTTP 且合同版本未变时，可仅替换 API；涉及 Graph、检查点、工具输入版本时必须确保 API/Worker 兼容。多 API 调试使用不同 instance_id/端口，普通会话状态仍在 PG 中。

## 6. 业务前端热更新与身份页维护

业务项目在 web 目录按 pnpm-lock 安装并启动 Vite；local Nginx 将业务页面及明确的 HMR 路径代理到 DEV_HOST。浏览器仍从 PUBLIC_ORIGIN 打开页面，BFF/API/identity 路径继续走 Gateway，避免端口变化破坏 OAuth 精确回调和 Cookie。

修改身份管理页面是框架维护工作：在 identity-service/admin 中安装/检查/构建，验证产物被 Java 镜像打包。项目自己的 web 不引入管理 npm 包，也不复制管理员用户/角色页面。

验收包括：热更新可用；登录、刷新、退出可用；业务 SPA fallback 不吞 identity/API 路由；普通用户访问管理入口仍被服务端拒绝。仅页面显示“登录成功”不能替代会话和后端授权检查。

## 7. 测试数据、模拟模型与定向验证

本地数据通过身份管理 API/页面和业务 API 建立，示例提供可重复的开发数据入口。数据只能写入声明的 local 环境，必须有明显保护；不允许给生产自动建立测试租户。开发数据不改变迁移历史，也不包含真实用户隐私。

定向验证按改动选择：Java 服务执行其模块/测试过滤；Python 在该服务目录执行对应 pytest 文件；前端执行受影响组件/流程检查。完成当前实现后集中运行相关测试及适用 lint/typecheck/build，不默认跑整个框架套件。

身份、租户或 Agent 改动必须包含失败路径；普通界面样式改动不强加无关多节点测试。模拟模型测试调度/状态，真实模型评估质量，两种报告分开。详细规则见[项目编码规范](../standards/01-项目编码规范.md)。

## 8. 故障定位对照

| 现象 | 首先检查 | 不能采取的捷径 |
| --- | --- | --- |
| Gateway 502，但 IDE 本机可访问 | Nacos advertised 地址、容器到宿主端口、防火墙、旧实例 | 把注册地址固定为 127.0.0.1 |
| 登录后回调失败 | PUBLIC_ORIGIN、精确回调、可信代理头、state、Cookie | 开启任意回调通配 |
| BFF 换 token 失败 | IDENTITY_INTERNAL_ORIGIN 在容器内是否可达、issuer 校验 | 关闭 issuer 校验 |
| Nacos 修改未生效 | 字段归属、发布摘要、热更新白名单、是否需要重启 | 重复放入 env/Nacos 试覆盖 |
| 403 | 用户角色、客户端 scope/audience、租户能力、委派限制 | 临时移除后端鉴权 |
| 已提交任务没处理 | Outbox、队列、Worker 兼容版本、租约和预算 | 重复创建新任务冒充重试 |
| SSE 卡住 | 事件是否落 PG、游标、代理缓冲、心跳与超时 | 直接重新调用模型 |
| 修改后数据库报错 | 已执行迁移、schema 兼容、迁移账号/运行账号 | 修改历史迁移或开启自动建表 |
| 切换租户后数据混杂 | principal、事务租户上下文、连接 reset、缓存 key | 前端过滤掩盖后端泄漏 |

排查顺序沿 trace/request/run 从入口到实际写入；区分已证实事实、候选原因和缺失证据。共享日志前移除凭据及业务敏感内容。

## 9. 停止、恢复和明确重置

日常结束使用 Compose stop 或停止 IDE，保留卷和本地秘密；恢复时沿初始化检查点核对，不需要重建租户。切回容器先关闭 IDE 进程、确认实例摘除，再对指定服务 up -d。

只有明确要删除本地数据才执行重置维护流程：核对 PROJECT_CODE/APP_ENV=local、实际网络/卷/目录清单、备份需要，明确列出将删除的数据并确认；使用具体资源名操作。测试/生产环境不开放 local reset。禁止把 `down -v` 写进普通启动、调试或升级命令。

新增业务数据库使用 resources 的增量初始化；丢失本地秘密不能自动生成新密码后假装旧数据库可用，应核对现有资源并执行明确的凭据轮换或受控重置。
