# 新项目开发与规范升级指南

> D-20261027-10 实施目标；运行状态见[计划](../plans/2026-10-27-源码微服务脚手架改造-plan.md)。首次创建和登录见[接入指南](01-新项目接入指南.md)，不在本页维护第二份流程。

## 1. 日常开发

从项目根打开 VS Code；Java 根 Maven reactor，Python 各服务 .venv。只修改所属业务服务；共用源码在 sdk，身份/网关不承载业务功能。依赖变更在该服务修改并重锁，不影响其他服务锁。规范位于项目自己的 docs/standards，公共源码升级需审查差异。

新增 API 同步权限目录、响应模型、OpenAPI 与相关测试；新增权限发布后仍需租户管理员授权。修改配置使用项目 scripts/config/publish.py --env-file .local/environment.env --source config/nacos --data-id <服务名>.yaml，可调运行参数在 Nacos，秘密与地址绑定在环境材料。新增服务见接入指南 §5。

## 2. SQL 作者与本地验证

Java 在服务 src/main/resources/db/migration 新增 V<递增整数>__<动作>.sql。Python 在服务目录执行：

```bash
uv run --frozen --group migration alembic -c migrations/alembic.ini revision -m "add equipment status"
```

编写并审查 upgrade；不把自动生成当数据删除授权。回到项目根：

```bash
uv run --frozen python scripts/migrate.py --env local --service inspection-service --check
uv run --frozen python scripts/migrate.py --env local --service inspection-service --apply
```

check 不写库；apply 失败停止。删除/改名需核对旧代码与数据；具体规则唯一归[SQL 设计](../design/10-数据库迁移与升级设计.md#compatibility)。只用专属测试库验证破坏性操作。

## 3. 定向检查

Java 在根通过 mvnw.cmd（Linux ./mvnw）-pl :<服务> -am 运行相关测试过滤、Spotless 和构建。Python 在自身目录 uv run --frozen pytest <相关文件>、ruff、mypy；不默认跑全仓。README 命令、独立 clone、跨语言调用和权限场景随本次改动验证；构建成功不代替运行验收。

## 4. 镜像与部署

源码工作目录为项目根。先完成发布策略 deploy/release.yaml、业务代码、配置、迁移和锁并提交所有构建输入；新增子仓先提交/push 再固定主仓 gitlink。正式构建要求干净、来源可取回。

```bash
uv run --frozen python scripts/build.py --release 0.1.0 --services all --output dist/0.1.0
```

局部发布使用 --services inspection-service --base-release <已部署发行清单>，基础源码指纹不同则要求完整构建；不能冒充首次完整环境。按输出镜像列表使用 Docker/CI push，记录真实 repository@sha256 映射到 .local/images-production.json；不要手填虚构 digest。源码/策略变更后重新构建。随后：

```bash
uv run --frozen python scripts/package.py --build-record dist/0.1.0/build-record.json --images .local/images-production.json --output dist/0.1.0-package
```

自定义业务 Web 先构建静态产物并在发布输入声明，缺产物停止。包内执行代码和锁齐全，身份管理页在身份镜像内；包不包含 .local、真实秘密或完整业务源码。部署包内容见[交付合同](../design/11-源码脚手架交付与开发体验设计.md#deployment)。

Linux/WSL 控制机解包后，在包根 uv sync --frozen；按 deploy/ansible/README.md 复制 config/environments/test/hosts.yaml.example 为 hosts.yaml 并填写实际主机，另准备包外环境变量文件和每机秘密/TLS。单机 inventory 只列一台。材料包括地址/端口、组件模式、镜像仓库权限、域名证书、资源归属、备份及恢复记录。

首次安装命令（变量文件路径替换成受控绝对路径）：

```bash
ansible-playbook -i config/environments/test/hosts.yaml deploy/ansible/infra.yaml --extra-vars @/secure/equipment-prod.yaml
ansible-playbook -i config/environments/test/hosts.yaml deploy/ansible/initialize.yaml --extra-vars @/secure/equipment-prod.yaml
ansible-playbook -i config/environments/test/hosts.yaml deploy/ansible/migrate.yaml --extra-vars @/secure/equipment-prod.yaml
ansible-playbook -i config/environments/test/hosts.yaml deploy/ansible/deploy.yaml --extra-vars @/secure/equipment-prod.yaml
```

阶段和停止条件见[首次安装](../design/09-应用部署与运维设计.md#first-install)。首次平台管理员创建业务租户/用户并授权后，再做普通用户真实登录/业务烟测。仅容器 running 不算安装成功。日常使用包内 README 提供的精确 Compose ps/logs/stop 参数。

## 5. 升级与恢复

在升级分支合并 SDK/基础服务的明确源码补丁，或更新所选业务 submodule；不重建覆盖项目、不同时更新全部子仓。规范变更也审查差异。验证空库和支持的旧数据升级，再提交、构建、打包。

两种路径均先拉取校验镜像和环境材料。兼容迁移可以先执行再替换应用；破坏性变更必须在维护窗口先停流量、旧应用与所有相关写入者，填写 maintenance_writers_stopped=true 和 maintenance_evidence 后迁移，启动新版本、验收，再恢复流量。停止范围和外部任务由发布说明列明，不能仅运行 migrate 就算维护。

失败用同版 reconcile.yaml 核对，不自动清库/repair/stamp。回退仅限已验证兼容旧镜像；数据库误删需备份恢复，不能靠 checkout 或 downgrade 恢复数据。细则见[恢复边界](../design/10-数据库迁移与升级设计.md#recovery)。

旧 vendor 项目仅提供转换清单；真实转换需单独确认与隔离验证，不宣称本次已完成所有存量兼容。
