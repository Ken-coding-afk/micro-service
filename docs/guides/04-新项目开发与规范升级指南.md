# 新项目开发与规范升级指南

> 版本：1.0；基线：D-20261027-05；更新：2026-10-27。  
> 面向展开后的独立混合项目。文件是否已交付以当前 release-manifest.json 为准；旧 rc.3 发行未包含完整开发基线，不能只靠下载本文补齐能力。

规范：[通用](../standards/01-项目编码规范.md)、[Java](../standards/02-Java编码规范.md)、[Python](../standards/03-Python编码规范.md)。本文说明操作，不另定义身份、事务或协议合同。

## 1. 展开发行并建立仓库

工作目录始终是新项目根。先按发行说明核对 release-manifest.json 的文件摘要和镜像来源，再展开到新目录，避免覆盖已有项目。检查存在以下材料：

```text
项目根/
├── README.md / AGENTS.md / CLAUDE.md / .cursor/rules/project.mdc
├── .editorconfig / .gitattributes / .gitignore
├── docs/standards/01、02、03-*.md
├── docs/guides/04-新项目开发与规范升级指南.md
├── services/sample-java-service/       # src/main、src/test、独立 POM
├── services/sample-python-service/     # src、tests、独立 pyproject/uv.lock
├── config/ + infra/ + deploy/ + examples/ + web/
├── artifacts/                         # parent、foundation、wheel、身份迁移
└── framework-baseline.json / release-manifest.json
```

根 uv 环境是运维工具环境；业务服务各有自己的环境。框架身份/网关以镜像复用，不复制其源码。AGENTS 只链接项目规范，不要求个人技能或 CodeGraph。按需使用 CLAUDE/Cursor 入口。

```powershell
git init
git check-ignore .local/environment.env services/sample-java-service/target/private.jar services/sample-python-service/.venv/pyvenv.cfg
```

预期三条路径都被忽略。不要在验证该条件前提交 .local/。发行基线保存原始摘要，项目正常修改不回写基线。

## 2. 安装开发依赖

前提：JDK 21、Python 3.12、uv；能访问依赖仓库或有完整缓存。Maven wrapper 随发行提供；Windows 用 mvnw.cmd，Linux 用 ./mvnw。业务单元测试和静态检查不需要 Docker/PG/Nacos。

从项目根将本次附带的 parent/foundation 安装到 Maven 仓库；有团队制品仓库时使用对应固定版本即可。下列版本对应当前 SDK 基线，升级时以新发行清单为准：

```powershell
./mvnw.cmd org.apache.maven.plugins:maven-install-plugin:3.1.4:install-file '-Dfile=artifacts/java/platform-parent-1.0.0-rc.3.pom' '-DpomFile=artifacts/java/platform-parent-1.0.0-rc.3.pom'
./mvnw.cmd org.apache.maven.plugins:maven-install-plugin:3.1.4:install-file '-Dfile=artifacts/java/foundation-1.0.0-rc.3.jar' '-DpomFile=artifacts/java/foundation-1.0.0-rc.3.pom'
cd services/sample-python-service
uv sync --frozen --group dev
```

Python 锁文件中的 SDK wheel 指向项目自己的 artifacts/python。预期 .venv 中安装本服务、固定 SDK 和 dev 工具；不能回到框架源码联编替代。缺 wheel/摘要不符则检查发行包，缺网络依赖则修复仓库访问，不取消 frozen 或全局 pip install。

## 3. 先通过最小检查

Java 从项目根执行，Python 从服务根执行。具体命令见语言规范：Spotless/Ruff/mypy 是静态检查，JUnit/pytest 是行为测试。默认 check 不改文件；format/apply 必须显式运行。

```powershell
# 项目根
./mvnw.cmd -f services/sample-java-service/pom.xml -Dtest=BusinessSettingsTest,ItemServiceTest,ItemControllerTest test
# Python 服务根
uv run --frozen ruff check src tests
uv run --frozen ruff format --check src tests
uv run --frozen mypy src
uv run --frozen pytest tests/test_business_config.py tests/test_items.py tests/test_application.py
```

这些示例测试无需运行基础设施。SQL/RLS 或远程实际合同改动另做对应集成验证；不能凭上述测试宣称租户数据库或生产环境已经验收。Windows 临时目录异常时可指定 pytest --basetemp 为本项目 .local 下的专用目录，不清理别人目录。

## 4. 改成自己的业务服务

先跑通现有混合项目，再逐项替换 sample 名称，核对这些位置：

| 范围 | 同步修改 |
| --- | --- |
| Java | 服务目录、groupId/artifactId、包与启动类、PlatformService 名、application.yml、测试与 Docker 构建路径 |
| Python | 服务目录、project.name、src 包、wheel packages、脚本入口、PlatformSettings 服务名、测试导入 |
| 身份/权限 | 各服务 permissions.yaml、audience、权限 code/scope、客户端登记与运行绑定；不得复用另一项目秘密 |
| 配置/资源 | Nacos 服务 YAML/规则 JSON 的 Data ID 与资源名、gateway routes、业务 resources.yaml 和项目 infra/resources.yaml |
| 部署/协作 | examples Compose 覆盖、Dockerfile、镜像引用、service registry 名、PEER_SERVICE 和 Client 的目标/API |
| 文档/检查 | README 中命令、构建与测试过滤器、项目补充规范 |

不存在自动重命名脚手架。修改是明确的项目初始化工作；只改文件夹名会导致配置/发现错配。删除不需要的服务时，同步移除其路由、资源和凭据声明，不能留下失效依赖。

## 5. 第一个有持久化的用例

以“给记录增加备注”为例：先决定可公开的字段和校验范围，再新增向后兼容迁移；不要编辑已经应用的 V1。业务表保留 tenant/owner 约束和 RLS。权限清单按用例声明，发布目录后由管理员配置角色，不写硬编码超级权限。

Java controller 校验 DTO，service 确定用例/主体/事务，dal 用参数化 SQL，client 经 SDK 访问远端。Python 的 api/schemas/services/repositories/clients 职责对应，main 只装配。简单只读业务投影允许共享；无需每层复制相同对象。

同时补非法输入、成功、失败传播测试。涉及权限和数据范围时增加无权限、跨租户、SELF；改 SQL/RLS 时使用真实受限 PG。资源初始化、迁移、登录与双向调用完整步骤在项目根 README，不重新发明启动脚本。

## 6. 提交与构建

按改动选择检查，先完成实现，再集中写/跑关联测试。只改 Python 用例不跑整个 Java 框架；只改文档不启动容器。失败只重跑受影响部分。报告运行命令、cwd、结果和未验证边界，跳过不是通过。

Java 测试通过后执行 clean package，确认嵌套 foundation 与锁定制品一致；不要覆盖已发布版本。Python 构建 wheel 前先测试，生产 requirements.lock 用 --no-dev 导出并保留 SDK wheel hash，参见根 README；不能把 pytest/mypy/ruff 装进业务镜像。

未修改的 identity-admin 保持现有前端检查，不要求业务 web 选同一框架。项目 CI 可复用上述命令，本发行不安装 hook、不绑定 CI 平台，也不会自动推送。

## 7. 升级规范与工具

规范和配置已在 release-manifest/framework-baseline 中记录；项目补充文件由自己创建 `docs/standards/04-项目补充规范.md`，框架不生成或覆盖。比如业务要求所有时间展示指定时区，应说明显示层转换，不能改变服务 UTC 存储合同。

升级准备三份文件：旧发行原件（摘要对应旧 baseline）、新发行原件、项目当前文件。逐文件比较；不要用新包覆盖整个项目。例：新 Ruff 基线新增 I 导入排序，项目 pyproject 中同时增加某业务开发依赖——保留该依赖、合并规则，再更新自己的 uv.lock 和运行定向检查，不能直接替换 pyproject 或锁文件。工具/规范变更是开发基线升级，不自动执行数据库迁移或启动容器。

冲突无法判断时保留两边并记录差异，暂停该文件合并；合并确认、定向验证和项目提交完成后才记录新发行基线。旧基线和原件保留供追溯。框架新规则不能静默删除项目约束，项目补充也不能放宽租户/认证底线。

## 8. 常见失败

- Maven 找不到 parent/foundation：检查仓库、版本和制品安装，不修改 relativePath 指向框架源码。
- uv frozen 失败：区分 pyproject/lock 不一致和 artifacts wheel 缺失；修正来源后再锁定，不临时改用浮动 SDK。
- 规范文档不存在：确认包是否包含开发基线；旧包只拷一篇文档不等于完成升级。
- mypy/Ruff 不存在：确认当前目录、服务 dev 组和 .venv，不能借用全局工具。
- 容器不可用：静态/单元检查仍可执行，但真实租户/跨服务验证保留未完成；不得将重复重启其他项目作为默认恢复动作。
