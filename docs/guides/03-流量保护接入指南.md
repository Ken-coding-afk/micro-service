# 流量保护接入指南

> 适用：rc.3 候选及之后兼容发行。能力与边界以[协作设计](../design/07-Java与Python协作设计.md#gateway)、[配置与刷新设计](../design/02-配置与服务发现设计.md#refresh)为准；验收状态见[实施计划](../plans/2026-10-27-限流熔断与并发保护-plan.md)。下列工作目录均为创建器生成的**新项目根目录**。

## 1. 先跑通混合项目

按[新项目接入指南](01-新项目接入指南.md)准备环境、数据库迁移、身份初始化、服务 audience、独立内省凭据和角色。仍然复用 identity-service、api-gateway、PG、Redis、Nacos；不用部署 Sentinel Server、Dashboard、集群限流服务器或另一套 Redis。基础身份功能不会因接入保护而改变。

新项目在 services/ 下开发 Java/Python 服务，使用项目内 sdk/java、sdk/python 与 scripts，按项目接入指南生成基础镜像和配置；业务功能不放入 identity-service。下文的流量保护参数及运行行为不因源码引用方式变化而改变。

## 2. 网关只配置原生路由

修改项目 config/nacos/api-gateway.yaml 中已生成的原生路由，service、Path、audience 必须匹配本项目登记值。示例使用 RequestRateLimiter，key-resolver 与 rate-limiter 指向框架已装配的两个固定 Bean；项目无需编写过滤器或 Redis Lua。

```yaml
spring:
  cloud:
    gateway:
      server:
        webflux:
          routes:
            - id: python-items
              uri: lb://sample-python-service
              predicates: [Path=/api/v1/python-items/**]
              metadata:
                platform.audience: sample-python-service
              filters:
                - name: RequestRateLimiter
                  args:
                    key-resolver: '#{@tenantOrClientKeyResolver}'
                    rate-limiter: '#{@platformRedisRateLimiter}'
                    redis-rate-limiter.replenishRate: 20
                    redis-rate-limiter.burstCapacity: 40
                    redis-rate-limiter.requestedTokens: 1
```

例中 20 是每秒补充令牌数，40 是突发容量；不是容量承诺。按项目压测调整。BFF 的 `/bff/web/api/v1/python-items/**` 从这个原生定义派生，与普通 API 共用额度，不需要再配置一条路由。没有声明该过滤器的路由没有业务配额。身份协议及管理 BFF 使用框架既有固定入口。

额度只根据内省/BFF 校验过的主体计算。不要传 X-Tenant-Id 来选择限流桶。Redis 故障返回 503，额度不足返回 429 和 Retry-After；业务不要把它们统一当登录失效。

## 3. Java 服务接入 Sentinel

sample-java-service 的 POM 已显式包含 `com.alibaba.csp:sentinel-core` 与 `sentinel-datasource-nacos`；版本由框架 parent/BOM 管理。新建服务时保留这两个依赖。java-sdk 将它们声明为可选依赖，**只引入 java-sdk 不会自动把 Sentinel 带到所有服务**。

在 `config/nacos/<服务名>.yaml` 启用：

```yaml
spring:
  cloud:
    sentinel:
      enabled: true
http:
  max_connections: 64
```

同时复制并改名两个原生 JSON 文件：

| 文件 | 修改内容 |
| --- | --- |
| `<服务名>-sentinel-flow.json` | `http.inbound` 的入站并发；`http.outbound/<目标服务名>` 的出站并发 |
| `<服务名>-sentinel-degrade.json` | 目标依赖的异常比例熔断；不需要任何熔断时保留明确的 `[]` |

例中 count=64/32 只是起点；Sentinel 并发流控遵循其统计语义，不承诺严格原子信号量。不要加第二套 @SentinelResource 或自动 WebClient 埋点去重复统计同一次框架调用。

入站 HTTP 自动保护。出站使用注入的 `ServiceHttpClient`，保留原来的调用方式：

```java
return serviceHttpClient.request(
    "sample-python-service", "GET", "/api/v1/python-items", null, CallContexts.current());
```

此代码适用于已有 Servlet 可信上下文；WebFlux 从 Reactor Context 取得 CallContext 后显式传入。使用自己创建的 HTTP 客户端不会自动获得这层保护。框架返回真实下游响应，不替业务伪造熔断降级结果；业务自行决定显示繁忙、延后操作或采用已确认的缓存策略。

## 4. Python 服务接入

合并公共 SDK 源码补丁与必要版本约束，执行服务 uv lock 并审查 uv.lock；SDK 来源是项目 sdk/python 源码。服务创建应用时先 `runtime.install(app)`，再 `install_resource_security(app, introspector)`；生命周期调用原有 `runtime.start()` / `runtime.stop()`。示例已装配这一顺序，不需要逐个端点添加并发装饰器。

```yaml
concurrency:
  inbound_limit: 64
  outbound_limits:
    sample-java-service: 32
http:
  max_connections: 64
  max_keepalive_connections: 32
```

业务继续 `await runtime.http.request("sample-java-service", "GET", "/api/v1/java-items")`。runtime 持有并关闭 HTTPX 客户端及各 limiter；不要每个请求重建 runtime/client。外部注入的客户端仍由注入方关闭。

Python 提供 AnyIO 并发许可、连接池及 deadline，**没有默认通用熔断器**。同步算法即使客户端断开仍可能执行，不能用 abandon_on_cancel=True 提前释放它实际占用的名额。长流从开始直到结束持有入站许可；CPU/GPU 调度仍由业务项目选择。

## 5. 发布、检查、调参与回退

全新示例需将 config/nacos 中的 **YAML 和 JSON 一并**合入 config/nacos。已有项目逐文件比较，不能覆盖本项目其他服务的配置。

```powershell
uv run --frozen python scripts/config/publish.py --env-file .local/environment.env --source config/nacos --dry-run
uv run --frozen python scripts/config/publish.py --env-file .local/environment.env --source config/nacos
```

发布工具校验全目录、识别未知远端漂移、先发布 JSON 再发布 YAML。Java 首次启动必须成功从网络读取有效的两份规则，缺失时不注册；`[]` 才是明确清空，删除配置或发送空文本不是清空。

Sentinel JSON 的有效变更动态生效。检查每个实例日志 `Sentinel rule accepted dataId=... sha256=...`，按 Data ID 比对本地源 SHA-256；发布成功只证明 Nacos 接受，不代表所有节点同时收敛。flow/degrade 两文件分别生效，不作为跨文件事务。无效变更保留上次有效值，修正 Git 源后重发。回退同样发布已保存的旧有效文件；变更可能重置组件的熔断状态。

网关路由/额度、连接池、Python 并发参数为重启字段。按已有 Compose/发布流程更新对应实例，并核对 readiness；不要求重启 PG/Redis，不清空 Redis 桶。全部请求写入的重试语义保持不变，不能为了“恢复”重复 POST/PUT/PATCH/DELETE。

## 6. rc.2 项目迁移

1. 保存当前发行基线、镜像摘要及 Nacos 配置摘要，确认回退清单。
2. 将旧 `gateway.routes` 的 id 原样保留，path 改为原生 Path，service 改为 lb:// URI，audience 移到 metadata。删除旧块，不能同时保留两种格式；固定身份协议路由不再由项目重复声明。
3. 按源码接入指南升级固定框架引用及相应 parent/java-sdk/SDK 约束，重建 api-gateway 与业务镜像；Java 服务补齐可选依赖及两份 JSON，Python 服务按第 4 节安装 runtime。新配置与旧网关不兼容，按维护窗口或同版分批切换，不能把旧二进制直接用于新路由配置。
4. 发布配置并更新对应服务；验证登录、权限拒绝、Java↔Python 调用、429/503/504、Redis 故障以及各实例规则摘要。回退镜像时一并恢复对应配置和旧 SDK 制品；数据库没有因本项增加新表或迁移。

## 7. 排错与观测

| 现象 | 先检查 |
| --- | --- |
| Java 启动失败、不注册 | 两份规则文件存在且有效、官方依赖已进入制品、Nacos 运行身份读权限；不要改成管理员凭据 |
| 更新 JSON 没生效 | 所有节点的 dataId/sha256 日志、配置错误和 Nacos 连接；日志不得打印密码 |
| 更新路由/Python 参数没生效 | 重启所选服务；启动快照不自动热替换 |
| 429 | 同租户共享额度、BFF 与普通入口共桶；按 Retry-After 延迟且不自动重放写操作 |
| RATE_LIMIT_UNAVAILABLE | 网关 Redis 地址、秘密、TLS、连接及存储状态 |
| SERVICE_BUSY/DEPENDENCY_BUSY | 实际请求/流占用、并发参数和连接池；勿无限排队掩盖问题 |
| DEPENDENCY_CIRCUIT_OPEN | 依赖失败与 Sentinel 原生状态变化；半开取消不等同于业务恢复 |

Java 沿用 Actuator/Micrometer：`platform.protection.active/rejected/failures`、`platform.circuit.transitions`、`platform.http.pool.rejected`、`platform.http.cancelled`、`platform.gateway.rejected`，连接池统计使用 Reactor Netty 原生指标。Python `runtime.metrics.render()` 返回 Prometheus 文本，由项目受控的内部观测入口导出；框架不新增公开 metrics API。标签不放租户、用户或原始 URL。Sentinel 的完成样本不是业务成功数。
