# 项目编码规范

> 版本：2.0；设计基线：D-20261027-05；更新：2026-10-27。  
> 本文规定框架维护与业务开发的共同工程要求；不是全仓代码已合规或生产验收通过的声明。

阅读：[Java 规范](02-Java编码规范.md)、[Python 规范](03-Python编码规范.md)、[新项目开发与规范升级](../guides/04-新项目开发与规范升级指南.md)。

<a id="general"></a>
## 1. 适用范围与规则强度

- **必须**：直接约束正确性、安全、兼容或可维护性的要求。工具能够判断的由检查命令执行，其他要求必须在代码审查中核对。
- **建议**：通常有利于理解的写法；有具体理由可以采用更合适的实现。
- **按需**：只有真实业务需要才引入；不为符合目录树创建空包、接口或服务。

框架维护者维护公共 SDK、身份、网关和发行材料；业务项目依赖固定版本制品，在自己的 services 中开发业务。基础库按 config/security/http/data 等能力组织，不强制套 Controller/Service/Repository。业务服务按实际用例分层，不复制基础服务源码。

新代码及本次修改范围必须符合要求。存量欠缺单独记录，逐步处理；不得用全仓重排制造无关差异，也不得因存量欠缺全局关闭检查。规范不会自动授权代码修改、部署、提交或推送。

<a id="structure"></a>
## 2. 组织、命名与注释

必须使用职责明确的名称：服务名小写连字符，Java/Python 内部名称见语言规范。两语言业务在同一项目 services/ 下，web 是可选业务前端；config 管理配置源，infra 管理组件/资源，deploy 管理应用部署。身份管理页由框架镜像提供。

业务调用方向：API → Service → Repository/Client。API 转换协议，Service 负责用例、可信主体和事务，Repository 只操作所属服务的数据，Client 使用框架 SDK 访问远端。不得通过 utils、静态全局状态或循环依赖绕开职责。

按需建立目录。JDBC Repository 不必假装成 Mapper；简单查询不必引入 ORM；只有多实现或确需替换的边界才建接口。禁止机械的 Service/ServiceImpl、万能 BaseService 和为每个分层新增部署单元。不设函数行数或抽象数量指标，以职责是否清楚和是否可验证为判断依据。

文档与解释业务原因的注释以中文为主，标识符、命令和技术术语使用惯用英文。公共 SDK/API 说明输入、输出、失败方式与资源所有权；安全、事务和并发的关键限制解释原因。不要重复代码字面含义，不写机械的作者/日期/修订历史头。

<a id="java"></a>
## 3. Java 要求

执行[Java 编码规范](02-Java编码规范.md)。格式由 parent 中的 Spotless 固定；业务事务、数据库隔离和响应式安全仍需针对性测试/审查，格式通过不证明这些行为正确。

<a id="python"></a>
## 4. Python 要求

执行[Python 编码规范](03-Python编码规范.md)。业务服务拥有自己的虚拟环境、锁文件及 dev 工具，不借用根运维环境。SDK 不提供 Agent/Run 运行时；算法、模型与 Agent 编排属于业务项目，按需设计，不要求每个服务有 agents/tasks。

<a id="contracts"></a>
## 5. 类型、接口与错误

- 必须在边界校验输入，并使用明确的请求、结果类型。不要让任意 Map/dict 从接口贯穿所有层；允许局部第三方协议转换使用动态数据，但必须在边界收窄。
- API 类型不得无差别绑定 tenant/owner/角色等安全字段；持久化结果不等同于可完整公开的响应。简单不可变结果可复用，不机械创建内容完全相同的多层对象。
- 保持已有协议中的字段、HTTP 状态及错误码；修改公共合同必须单独说明兼容方案。金额/高精度值不依赖浮点隐式转换，时间采用 UTC。
- 错误必须可定位，不能吞异常返回成功或空数据。对外给稳定错误码，内部记录脱敏事件、失败阶段和 request_id；第三方异常消息可能含凭据，不能直接打印 cause、请求 URL 或环境字典。
- 远程调用走已有 SDK，显式预算、取消和重试边界由 SDK 执行；不要重复叠加重试/熔断。业务负责幂等与明确降级，不用假成功掩盖依赖失败。
- 使用 MQ 时遵守既有事件协议、去重和事务边界；没有消息需求不建立消息层。规范不重新定义协议状态机。

<a id="security"></a>
## 6. 权限、租户与数据

后端必须执行权限及对象数据范围检查。身份只来自认证后的 principal/context，不相信请求头或 JSON 中自报的 tenant。受控内网和机器调用也要认证；隐藏按钮不构成授权。

租户表必须包含 tenant_id、适当复合约束/索引和 RLS，运行身份不得有 DDL/BYPASSRLS。事务租户上下文由 SDK 管理；异常/取消不能串租户。缓存、文件和事件同样遵守租户归属。禁止跨服务直接查询业务库，禁止共享业务实体 JAR。

凭据通过现有受控配置注入。不得提交 .env、密钥、真实用户资料、测试 Cookie、模型权重或本地运行状态；配置样例不能带可用的生产密码。日志不记录令牌、完整请求/响应或用户内容。新增诊断信息也遵守相同要求。

<a id="verification"></a>
## 7. 测试与变更

先明确输入、预期和必要失败路径，完成当前实现后集中补写并运行相关测试。无明确授权不跑全仓；失败仅重跑相关部分，不删断言、改正确预期或静默跳过以获得绿灯。

| 改动 | 必须核对的证据 |
| --- | --- |
| 文档/格式 | 链接、格式和示例命令；不新增无意义单测 |
| 用例/输入/错误 | 正常、非法输入、异常传播和现有响应合同 |
| 权限/租户/SQL | 无权限、跨租户、SELF；涉及 RLS 用真实受限数据库账号 |
| HTTP/取消/池 | 请求次数、总预算、资源释放、错误分类；按改动选场景 |
| 打包/依赖 | 新目录安装、交付清单、生产依赖不混入 dev、版本和摘要 |

迁移一旦应用不得修改，修复写新迁移；不让 Flyway/Alembic 同管一批表。不在本地事务内等待长远程工作。算法 mock 只证明流程，真实模型质量必须另给证据。

<a id="maintenance"></a>
## 8. 工具、提交与升级

格式、lint、typecheck、测试和 build 分别说明结果，不把 build/skipTests 当测试通过。只读 check 与修改文件的 format/apply 分开；没有默认安装 hook，不要求额外的 MCP/CodeGraph。

依赖按固定基线和锁文件安装；禁止生产 latest、SNAPSHOT 或无锁浮动解析。已发布版本不可覆盖。候选重新构建使用干净打包并核对嵌套依赖，避免增量产物保留旧内容。

框架规范快照、工具配置和示例随发行清单记录。项目自定义要求放 `docs/standards/04-项目补充规范.md`（按需自建，框架不覆盖）。升级按旧发行原件、新发行原件和项目工作区三方比较，不整目录覆盖；详见[开发与升级指南](../guides/04-新项目开发与规范升级指南.md)。更严格的检查也是开发基线变更，必须说明修正步骤；不得靠项目补充规则默默放宽安全合同。
